# R5.5.0 - Designer integration reconnaissance

Status: **reconnaissance delivered**. This document reports what Designer is
today, who owns its state, where its source of truth lives, and how it can
attach to the unified workspace. **No application code, contracts, routes, state
or UI were modified.** The only repository change is this document.

Companion reading: `docs/phase-5-roadmap.md` (R5.5 intent),
`docs/r5.1-workspace-decisions.md` (ADR Decisions 4 and 5),
`docs/r5.4.7-composer-legacy-retirement.md` (the completed Composer pattern this
milestone mirrors), and the visual/design docs listed in section 4.

---

## 1. Answers to the Definition of Done

> **What exactly is Designer today?**

A project-scoped, proposal-first creative surface. The `Designer` view
(`apps/web/src/views/Designer.tsx`) collects a natural-language intent, submits
it to a durable server run (`POST /projects/:id/designer/runs`), polls the run,
and renders the returned `DesignerProposal` as either a creation proposal (never
applied) or an edit proposal reviewed against a *separately fetched* stored
document. It is mounted as a body inside `ProjectWorkspaceShell` but is passed
only `projectId` and `role` (`apps/web/src/workspace/ProjectWorkspaceShell.tsx:347`),
so it is a *compatibility body*, not a native workspace mode.

A second, older entry surface - the **editor-native embedded agent**
(`apps/web/src/components/content/workspace/EmbeddedAgentEntry.tsx`, mounted in
`EditorMode.tsx:146`) - talks to the *same* durable run endpoint but interprets
the result as a contextual insertion/operation and applies it client-side
through `EditorContext`.

> **Who owns its state?**

- The shell owns the workspace session (identity, loader, autosave, lifecycle,
  document boundary). Designer does **not** read it.
- The `Designer` view owns all Designer-local state: `mode` (create/edit),
  `selectedId`, `instruction`, `applyState`, `applyError` (`Designer.tsx:95-101`).
- `useDesignerRun` owns run lifecycle + a `localStorage` bookmark
  (`seo.designer.run.<projectId>`), never document identity.
- The server (`AgentRunService`, `seo_agent_runs`) owns run lifecycle and the
  persisted proposal.

> **What is the source of truth?**

`DesignerProposal.document`, a complete `CanonicalDocument`
(`packages/contracts/src/designer.ts:301-337`). `apply` depends only on
`document`; review and `visual` are provenance. The server re-reads stored
content and refuses a proposal whose `baseRevision` no longer matches
(`apps/api/src/services/designerService.ts:437-475`).

> **How does DesignPackage relate to the canonical document?**

`DesignPackage` (`packages/contracts/src/designPackage.ts:94-103`) is a
*portable artifact* that embeds a `CanonicalDocument` plus a `CosmosDesign`,
plan provenance and media refs. It is **not used at runtime anywhere**: only its
own contract test imports it (`designPackage` appears in no `apps/*` source).
It is a serialization/transport format, not document state.

> **How does Designer generate and apply changes?**

Generate: intent -> `DesignerPlanner` (deterministic or LLM)
(`apps/api/src/agents/designer/planner.ts`) -> `DesignerPlan` ->
`executeDesignerPlan` (`apps/api/src/agents/designer/executor.ts:308-445`) ->
`DesignerService.execute` builds a `DesignerProposal` with a `baseRevision`.
Apply: **whole-document replacement** through the existing
`ContentService.update` choke point, guarded by a revision re-check
(`designerService.ts:463-474`). Operation/insertion/acquisition proposals are
explicitly refused by server apply (`designerService.ts:441-461`).

> **What can be reused from Composer?**

The unified workspace session, the single mutation pipeline
(`applyExternalDocument` / `applyDocumentOperations` via `EditorContext`), the
`CompositionApplyBridge` staging pattern, the shared chrome
(`WorkspaceChrome`/`DocumentHeader`), the review-dialog pattern, and the
identical revision hash (`documentRevisionOf` == server `contentRevisionOf`).

> **What conflicts must be resolved?**

Two Designer run clients over one endpoint (ADR Decision 4); Designer's
out-of-band stored-document read/apply versus the live shared document;
whole-document replacement versus the operation-batch pipeline; a duplicated
Designer `PageHeader`; and the `designer` project-view route. See section 16.

shell owns one document, but Designer reads and writes `seo_content`
independently of it.

## 4. Designer document ownership (section 4)

1. **Project identification:** `projectId` prop from the shell
   (`ProjectWorkspaceShell.tsx:347`); the embedded agent reads it from
   `useEditorContext` (`EmbeddedAgentEntry.tsx:46`).
2. **Document/ page identification:** Designer uses its **own**
   `mode`/`selectedId` selector and fetches `/projects/:id/content` and
   `/content/:id` (`Designer.tsx:109-121`), or the `contentId` carried by a
   restored run. It does not read the shell's `session.identity.documentId`.
3. **Reads the canonical workspace document?** No. It reads stored
   `content_json` over HTTP, independent of the live (possibly dirty) document.
4. **Separate document representation?** It holds `proposal.document`
   (server-built `CanonicalDocument`) and a `storedCanonical(...)` projection of
   the fetched row (`Designer.tsx:74-81`). It never touches the editor document.
5. **DesignPackage from the current document?** No. `DesignPackage` is not
   constructed at runtime at all.
6. **Applies changes directly to the document?** Yes - by whole-document
   replacement on the server; there is no client mutation of the live document.
7. **Uses `DocumentOperation` / `DocumentOperationBatch`?** Not on apply. The
   `DesignerProposal.operations?: DocumentOperationBatch` field exists
   (`contracts/src/designer.ts:329-336`) but server apply **refuses** it
   (`designerService.ts:455-461`, `422 designer_operations_require_editor`).
   Operation batches are produced/consumed only by the *editor-native* path
   (`useEmbeddedAgent.applyOperations` -> `EditorContext.applyDocumentOperations`).
8. **Own revision/version concept?** It reads `contentRevisionOf(row.content_json)`
   (`Designer.tsx:125-128`) and compares it to `proposal.baseRevision`. This is
   the *same* hash as the workspace `documentRevisionOf` (both delegate to
   `contentRevisionOf`), so the two are compatible - see
   `apps/web/src/components/content/documentRevision.ts:27-29`.
9. **Own save/persistence?** Apply writes immediately through
   `POST /content/:contentId/designer/apply` -> `ContentService.update`; it does
   not go through the workspace autosave/save barrier.

**Competing source of truth:** the live workspace document (shell) versus the
independently fetched stored document (Designer). They can diverge whenever the
open document is dirty or unsaved, and Designer's apply can overwrite content
the workspace still holds as unsaved.

## 5. DesignPackage architecture (section 5)

- **Created where:** nowhere at runtime. `designPackageFromProposal`
  (`designPackage.ts:402`), `toPortableDesignPackage`, `exportDesignPackage`,
  `importDesignPackage` have no non-test callers.
- **Contains:** `{ kind, version, metadata, document: CanonicalDocument,
  designSystem: CosmosDesign, plan?, assets? }` (`designPackage.ts:94-103`).
- **Owner:** the contracts package; intended producer would be a future
  Designer/workspace export path.
- **Persisted:** no migration/table references it. Not persisted.
- **References a document:** it *embeds* the full `CanonicalDocument`.
- **References visual assets:** `DesignAssetRef[]` is project-agnostic (target
  block id + kind + alt/caption); `portableDesignDocument` strips `mediaId`/`src`
  and CMS `source` (`designPackage.ts:243-280`).
- **References design tokens:** embeds a `CosmosDesign`.
- **Layout/responsive behaviour:** no separate model; carried inside the
  canonical document blocks.
- **Transformed into document changes / applied:** no transform exists. It is a
  snapshot, not an operation source.
- **Immutable or mutable:** the exported functions return new validated copies
  and never mutate input, but there is no runtime owner enforcing immutability.

**Proposal or document state?** Evidence supports keeping `DesignPackage` a
**portable proposal/artifact** (export/import round-trip), not document state:
it duplicates the document and has no revision/dirty semantics, while the
workspace already has one canonical document. The decision is deliberately left
open for R5.5 (this note records the direction, it does not make it).

## 6. Designer proposal architecture (section 6)

Actual flow:

```
intent (instruction [+ contentId | baseRevision])
  -> DesignerPlanner.plan  (deterministic or LLM; planner.ts)
  -> DesignerPlan (steps)
  -> executeDesignerPlan   (executor.ts; mutates an ExecutionState.document)
  -> DesignerService.execute -> DesignerProposal { baseRevision, document, review?, visual? }
  -> durable run result_json (seo_agent_runs)
  -> client review (EditReview / ProposalResult)
  -> POST /content/:id/designer/apply -> revision re-check -> ContentService.update
```

- **Proposal types:** one envelope, `DesignerProposal`
  (`contracts/src/designer.ts:301-337`); mutually-exclusive extras `insertion`,
  `acquisition`, `operations` are editor-bound and refused by server apply.
- **Creation:** no `contentId`; anchors to a client `base_revision` (the
  empty-document revision, `useDesignerRun.ts:60`); proposal-only, never applied.
- **Storage:** validated proposal persisted in `seo_agent_runs.result_json`
  (`agentRunService.ts:329-337`; migration `20260101000029_agent_runs.sql`).
- **Rendering/review:** `EditReview` side-by-side (`Designer.tsx:408-544`) using
  `CanonicalRenderer`; creation via `ProposalResult` (`Designer.tsx:618-636`).
- **Apply/reject:** apply -> server route; reject is local-only
  (`Designer.tsx:199-203`), never touches saved content.
- **Document-operation generation:** the executor evolves a mutable
  `CanonicalDocument`; it never emits a top-level `DocumentOperationBatch`
  (confirmed in section 14/agent report). The proposal's `operations` field is
  populated by other (editor-native) paths, not by `executeDesignerPlan`.
- **Existing stale/revision protection:** `revisionMatches` client guard
  (`Designer.tsx:129-130`) plus the server 409 `stale_proposal` re-check.

**Reusable vs structurally different (vs Composer):**

- Reusable: `DesignerProposal.baseRevision` is the same hash as the workspace
  document revision; the review/apply split and the "refuse stale" principle;
  the durable run pattern already used by both clients.
- Structurally different: Composer emits **operations relative to a document**
  (`CompositionOperationBatch`), whereas Designer emits a **whole new
  `CanonicalDocument`**. Composer applies through the workspace mutation
  pipeline; Designer applies through a server whole-document write. Composer's
  review surface is shared; Designer's is local.

## 7. Visual domain (section 7)

- **Entities:** `VisualDesignProposal`, operations `select_asset`/`set_variant`,
  `VisualNoSuitableAsset`, `VisualAssetRef` (`contracts/src/visualDesign.ts`);
  vocabulary `VisualAssetRole`/`VisualIntent`/`VisualPlacement`
  (`visualVocabulary.ts`); `VisualDesignIntent` (`visualIntent.ts`).
- **Layout representation:** not a separate layout model; visuals are applied
  into the canonical document by `applyVisualDesignProposal`
  (`visualDesign.ts:359`).
- **Style representation / design tokens:** `DesignSystem` / `CosmosDesign`
  (`contracts/src/designSystem.ts`), resolved from project Cosmos settings
  (`apps/web/src/lib/designSystem.tsx`, `apps/api/src/services/cosmosService.ts`).
- **Sections / heroes:** `resolveSectionVisual` / `resolveHeroVisual`
  (`contracts/src/sectionVisual.ts`, `heroVisual.ts`), used by the image
  insertion service.
- **Assets:** `seo_media` rows (metadata only) + `seo_content_media` reference
  index (`20260101000015_media.sql`) with provenance columns added by
  `20260101000030_media_provenance.sql`.
- **Responsive rules / visual metadata / canvas model:** none found beyond the
  canonical document block attrs; there is no separate canvas layout model.

**Which state owns visual state?** The *composed* visual result is document
state (inside `proposal.document` / the saved document). The *provenance*
(`proposal.visual`) is proposal state, shown read-only. There is **no
Designer-owned persisted visual state**. The `visual.apply` plan step and its
asset selection run server-side inside `DesignerService.dependencies`
(`designerService.ts:263-336`).

## 8. Visual asset selection (section 8)

- **How assets are selected:** deterministically, server-side, via
  `selectVisualAssets(document, candidates, request)` /
  `rankVisualAssetCandidates` (`contracts/src/visualAssetSelection.ts`), driven by
  a plan `visual.apply` step's `selection` request.
- **`seo_media` contents:** metadata only - filename, mime_type, size,
  storage_key, width/height, alt_text, caption, source/source_meta; bytes live in
  object storage (`20260101000015_media.sql`, `..._media_provenance.sql`).
- **How selected assets reach Designer:** `DesignerService.dependencies.visual`
  maps `MediaService.list(projectId)` rows to `VisualAssetCandidate`s, selects
  metadata-only candidates, builds a `VisualDesignProposal`, resolves
  `VisualAssetRef`s (id/url/alt/caption/dimensions) from the library, then calls
  `applyVisualDesignProposal` to place them into `proposal.document`
  (`designerService.ts:263-336`). Bytes are never read.
- **Metadata-only:** yes - the selection gates on metadata only; the Designer
  view renders `proposal.visual` as explanation and never applies it separately.
- **Qdrant/media search involved?** Not for asset selection. Selection is
  deterministic lexical/metadata ranking; there is no vector search over media in
  this path.
- **Can Designer apply an asset to the canonical document?** Only by including
  the composed image in `proposal.document`; server apply then writes that
  document. The separate `insert_image` path is editor-native.
- **Intentionally unsupported:** no image generation inside the Visual domain
  asset selection (generation is a separate, confirmation-gated editor-native
  capability, R4.5B). This document preserves the metadata-only decision.

Distinction to keep: **asset selection** (metadata-only, server Designer plan)
is not **image acquisition/insertion** (editor-native `ImageInsertionContext`,
stock search / confirmed generation, applied through `EditorContext`).

## 9. Design system integration (section 9)

- **Token source:** project Cosmos settings, read via
  `cosmosService.getCosmosContext` (`apps/api/src/services/cosmosService.ts:47`);
  `cosmosDesignSystemRef` derives the reference attached to a document.
- **Theme source / vocabulary:** `resolveDesignSystem` / `effectiveDesignSystem`
  (`contracts/src/designSystem.ts`); `DEFAULT_DESIGN_SYSTEM` fallback.
- **How tokens enter a DesignPackage:** `DesignPackage.designSystem: CosmosDesign`.
- **How Designer consumes them:** server-side via `getCosmosContext` (planner
  context text, and `withDesignSystemRef` on the proposal document,
  `designerService.ts:361-381`).
- **How Editor/rendering consumes them:** `DesignSystemProvider` resolves the
  project design system once and shares it; `CanonicalRenderer` and the editor
  canvas read it from context (`apps/web/src/lib/designSystem.tsx`,
  `App.tsx` wraps the whole project area in `DesignSystemProvider`).
- **Multiple competing token sources?** No. One contract
  (`effectiveDesignSystem`), one provider, Cosmos as the project source. The
  Designer needs no new token bridge; it already shares the provider because the
  shell is mounted inside `DesignSystemProvider`.

## 10. Agent integration (section 10)

- **How a run starts:** `POST /projects/:id/designer/runs` (editor+),
  `AgentRunService.submitDesignRun` inserts `seo_agent_runs` and enqueues the
  `agent_design` job (`designer.ts:259-292`, `agentRunService.ts:197-258`).
- **Input:** validated `AgentRunInput` (plan or intent with optional
  `contentId`/`baseRevision`/`brief`; intent may carry `editor_context`).
- **Output:** a validated `DesignerProposal` persisted on `running -> succeeded`.
- **Sync/async:** asynchronous (202 + worker), polled via
  `GET /designer/runs/:runId`.
- **Stored where:** `seo_agent_runs.result_json`.
- **Result a proposal?** Yes.
- **Document-scoped or project-scoped?** **Project-scoped.** `contentId` is
  optional; a run can be a content-less creation. The run is bound to
  `project_id` (+ `created_by`).
- **Cost/metering attached?** No: no cost/token/usage fields in the service or
  the migration (R5.10 will address this).
- **Can the unified workspace invoke it directly?** Yes - the endpoints are
  project-scoped and already used by two clients; the workspace can invoke the
  same service boundary.

## 11. Existing workspace integration (section 11)

- **Current mode:** `designer` exists in `WorkspaceModeSwitcher`
  (`WorkspaceModeSwitcher.tsx`), but the shell renders
  `{activeMode === 'designer' && <Designer projectId={projectId} role={role} />}`
  (`ProjectWorkspaceShell.tsx:347`) and describes it as a "compatibility body"
  (`ProjectWorkspaceShell.tsx:11`, `:140`).
- **Route:** canonical `/p/:id/workspace/designer`; legacy `/p/:id/designer`
  maps through `App` to the same shell mode.
- **Mount/unmount:** conditionally rendered per active mode (same as Composer).
- **Chrome/header:** `showChrome` is `editor || composer` only
  (`ProjectWorkspaceShell.tsx:141`), so the shared chrome is hidden in Designer;
  Designer renders its **own** `PageHeader` (`Designer.tsx:220-223`).
- **Document/session context:** none consumed. Designer receives only identity.
- **Project/session context:** `projectId`/`role` props.
- **Navigation:** none of its own; local create/edit mode only.
- **State providers:** none added; it does not mount editor infrastructure
  (verified by `ProjectWorkspaceShell.isolation.test.tsx`).
- **Preview/canvas:** uses `CanonicalRenderer` in its own review blocks; no
  shared canvas.
- **Existing apply bridge:** none. Designer has no `CompositionApplyBridge`
  equivalent; apply is the server route.

## 14. Architectural comparison with Composer (section 14)

### What Composer solved that Designer still needs

- **Workspace entry:** Composer is a session-aware native mode; Designer is a
  compatibility body receiving only identity.
- **Shared document identity:** Composer reads the one open document; Designer
  reads/writes stored content out-of-band.
- **Proposal boundary + revision binding:** Composer binds its batch to the live
  `documentRevisionOf` and the document boundary; Designer binds to a
  separately fetched stored revision.
- **Review/apply:** Composer has a shared review dialog and applies through the
  single mutation pipeline; Designer reviews locally and applies server-side.
- **Workspace chrome:** Composer shares `WorkspaceChrome` (R5.4.6); Designer
  hides the chrome and renders its own header.

### What Designer already has that Composer did not need

- `DesignerProposal` with `review`, `visual`, `insertion`, `acquisition`,
  `operations` extras.
- The `visual` domain (vocabulary, intent resolution, asset selection, composed
  visual provenance).
- The `designer.review` deterministic review and `writer.revise` revision path.
- The `DesignerPlan`/executor specialist pipeline and the durable run engine
  (plus MCP tools and the editor-native embedded agent).
- The `DesignPackage` portable artifact contract (currently unused).
- `DesignSystem`/Cosmos token resolution (already shared via the provider).

### What must NOT be duplicated

- The workspace document session / loader / autosave / lifecycle.
- The workspace mutation pipeline (`applyExternalDocument` /
  `applyDocumentOperations`).
- The durable run engine (`AgentRunService` + `agent_design` + `seo_agent_runs`)
  - do not add a third run client.
- The `AgentRunService.submitDesignRun` revision semantics.
- The `DesignSystemProvider` token resolution.
- The media library / `MediaService` as the single asset system.

## 15. Proposed R5.5 decomposition (G)

Smallest coherent sequence. Each milestone is integration, not a rewrite; the
existing server run engine and contracts are reused.

### R5.5.1 - Designer workspace binding (integration)

- **Objective:** make the Designer mode read the shared open document instead of
  its own selector, and render under the shell without a second document read.
- **Reuse:** `useWorkspaceSessionContext`, `Designer`, `useDesignerRun`,
  `session.identity.documentId`, `documentRevisionOf`.
- **Files/areas:** `apps/web/src/workspace/ProjectWorkspaceShell.tsx`,

## 16. Risks and architectural conflicts (H)

1. **Competing document ownership.** Evidence: shell owns the live document;
   Designer reads/writes stored `seo_content` independently
   (`Designer.tsx:109-121`, `:168-197`). Impact: applying a Designer proposal can
   overwrite unsaved workspace edits. Direction: bind Designer to the shared
   session and route apply through the mutation pipeline (R5.5.1/R5.5.2).
2. **Competing revision models.** Evidence: two revisions computed the same way
   but over different inputs (live `ws.doc` vs fetched `content_json`). Impact:
   false matches/stale gaps. Direction: reuse the one hash and compare against
   the live document; keep the server re-check only for out-of-band writes.
3. **DesignPackage vs CanonicalDocument authority.** Evidence: `DesignPackage`
   embeds a full document but has no runtime owner or revision/dirty semantics.
   Impact: risk of a second document representation if adopted naively.
   Direction: keep it a portable artifact, decided in R5.5.5.
4. **Duplicate apply paths.** Evidence: server whole-document write
   (`designerService.apply`) versus the workspace mutation pipeline
   (`CompositionApplyBridge`). Impact: two write authorities. Direction:
   converge on the workspace pipeline (R5.5.2); keep the server route for MCP.
5. **Two Designer run clients (ADR Decision 4).** Evidence: `useDesignerRun` and
   `useEmbeddedAgent` both drive `/designer/runs` with separate epoch/poll logic.
   Impact: drift and double maintenance. Direction: one controller (R5.5.4).
6. **Designer-specific state leaking into workspace state.** Evidence: none yet
   (Designer keeps only local state). Impact: future risk if the proposal is
   staged without a clear owner. Direction: stage proposals the R5.4 way (shell
   owns the pending proposal; mode owns workflow).
7. **Duplicate navigation/header.** Evidence: Designer hides shell chrome and
   renders its own `PageHeader`. Impact: two top layers. Direction: R5.5.3.
8. **Stale proposals.** Evidence: client `revisionMatches` plus server 409. With
   a live shared document the existing guard must move to
   `documentRevisionOf(live doc)`. Direction: R5.5.2.
9. **Visual state persistence ambiguity.** Evidence: composed visuals live in the
   document; provenance is proposal-only; no Designer visual persistence exists.
   Impact: low today; must not be promoted to a separate store. Direction:
   keep as-is.
10. **Responsive state ownership.** Evidence: no responsive model exists; layout
    is inside canonical blocks. Impact: R5.7 will need a decision. Direction:
    out of scope for R5.5.
11. **Asset identity mismatch.** Evidence: `DesignPackage` strips media ids and
    re-resolves by block target; the live document stores `mediaId`/`src`;
    external assets are `seo_media` rows with provenance. Impact: portable
    packages need re-resolution semantics. Direction: keep package assets
    project-agnostic; decide in R5.5.5.
12. **Legacy routes.** Evidence: `/p/:id/designer` still maps to the shell.
    Impact: low. Direction: retire in R5.5.5.
