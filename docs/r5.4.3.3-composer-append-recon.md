# R5.4.3.3 - Composer append reconnaissance

Status: **reconnaissance only**. No production behavior changed. This document
maps the path for applying Composer output to an **already non-empty** document
through the existing operation-batch / proposal model without silently losing
unsupported structure, and recommends the R5.4.3.4 implementation boundary.

Scope: R5.4.3.2 already handles the empty/new current document
(`CanonicalDocument -> DesignerProposal.document -> applyExternalDocument`).
This recon investigates the non-empty case only.

## 1. Current operation-batch lifecycle

The operation-batch model already has a complete, single production pipeline. It
is worth stating that there is exactly **one creator** and **one executor**.

```text
editor_context + "add a section" instruction
   -> POST /designer/runs                         apps/api/src/http/routes/designer.ts:259
   -> worker executeDesignRun                    apps/api/src/services/agentRunService.ts:296
   -> DesignerService.executeIntent              apps/api/src/services/designerService.ts:405
   -> SectionCreationService.buildProposal       apps/api/src/services/sectionCreationService.ts:75
        -> DocumentOperationBatch                sectionCreationService.ts:195
        -> DesignerProposal{ document, operations }   sectionCreationService.ts:200
   -> persisted as AgentRun.result               agentRunService.ts ~334
   -> useEmbeddedAgent polls                     apps/web/.../workspace/useEmbeddedAgent.ts
   -> embeddedAgentOutcomeFromRun -> {kind:'operations'}   embeddedAgent.ts:408, :430
   -> review surface "Apply to document"         EmbeddedAgentStatus.tsx:137-178
   -> useEmbeddedAgent.applyOperations           useEmbeddedAgent.ts:329-354
   -> EditorContext.applyDocumentOperations      EditorContext.tsx:163-203
   -> applyDocumentOperations (contract)         documentOperations.ts:388-442
   -> one editor.commands.setContent transaction
   -> onDocChange -> autosave boundary -> seo_content
```

Exact entry points and guards:

- **Types**: `documentOperations.ts` - `InsertSectionOperation` (`:85-95`),
  `InsertTextOperation` (`:110-114`), `InsertImageDocumentOperation` (`:121-127`),
  `DocumentOperationBatch` (`:131-135`). `DOCUMENT_OPERATION_SECTION_KINDS =
  ['hero','section']` (`:55`); `DOCUMENT_OPERATION_MAX_OPS = 32` (`:50`).
- **Validation**: `isValidDocumentOperationBatch` (`:275-288`) plus per-op
  `isValidDocumentOperation` (`:238-269`). Only backward `ref` targets; unknown
  keys rejected; `insert_image` requires a string `assetId` (`:259`).
- **Execution**: `applyDocumentOperations(base, batch)` (`:388-442`). Pure:
  deep-clones base, applies ops in order, tracks batch-local `refs` (`:394`),
  and finally rejects any created container with no children as
  `result_incomplete` (`:428-436`) before `isValidCanonicalDoc` (`:438-440`). It
  throws `DocumentOperationError` (`:294-328`) and never returns a partial
  result - apply is atomic.
- **Client apply boundary**: `EditorContext.applyDocumentOperations`
  (`EditorContext.tsx:163-203`). Guards: `not-ready`, `no-editor`, then a
  **double revision check** - live `documentRevisionOf(current)` **and**
  `batch.baseRevision` must both equal `expectedRevision` (`:167-170`);
  `canonicalFromEditorDocument` may yield `unrepresentable` (`:171-176`); the
  contract executor may throw -> `apply-failed` (`:177-182`); application is one
  `setContent` transaction (`:183-191`), so undo + autosave are reused unchanged.
- **Server apply refuses batches**: `DesignerService.apply`
  (`designerService.ts:437-475`) returns `422
  designer_operations_require_editor` when `proposal.operations` is present
  (`:455-461`) and `409 stale_proposal` on a `baseRevision` mismatch (`:463-471`).
  Operations are therefore **editor-applied only**, by design.
- **Review/apply UI precedent**: `EmbeddedAgentStatus.tsx:137-178` renders the
  batch summary (kind, title, image) with "Apply to document" / "Cancel";
  `useEmbeddedAgent.applyOperations` (`:329-354`) is guarded by `applyingRef` and
  reports `stale-revision` in product language. Cancel is local-only.

Takeaway: the batch lifecycle is complete and reusable. The append path needs a
**producer** of operations and a **review surface**, not a new mechanism.

## 2. `CompositionApplyBridge` analysis (R5.4.3.2)

`apps/web/src/workspace/CompositionApplyBridge.tsx`:

- `pendingCompositionOf(document, baseRevision, boundary)` (`:34-40`) wraps the
  composed `CanonicalDocument` in the existing `DesignerProposal` envelope
  (`document` only) and captures the session boundary string.
- The base revision is obtained by the **shell**, not the bridge:
  `documentRevisionOf(ws.live.current.doc)` at staging time
  (`ProjectWorkspaceShell.tsx:193`).
- `expectedRevision` is enforced by `applyExternalDocument`
  (`EditorContext.tsx:131-133`).
- `session.boundary` guard (`CompositionApplyBridge.tsx:67-71`): if the session
  document moved between staging and apply, the bridge reports
  `stale-document` and never writes.
- The apply is `context.applyExternalDocument({ canonical, expectedRevision,
  source:'composer' })` (`:76-80`), once per staged value via a `handled` ref
  (`:60, :63, :75`). It waits while the editor is not `ready` and `snapshot.ready`
  is false (`:73`).
- Composition output enters the workspace via the shell `applyComposition`
  (`ProjectWorkspaceShell.tsx:179-195`): re-check emptiness, set pending, switch
  to editor mode. Composer owns generation; the shell owns eligibility/staging;
  the bridge owns the single apply; `EditorContext` owns the mutation.

**`useOperationBoundary` is not used by the apply bridge.** R5.4.3.2 needs no
`begin/isStale` operation guard because the apply is synchronous inside the
editor and the mode switch is synchronous; the raw `session.boundary` plus the
revision check is sufficient. `useOperationBoundary` *is* used by the **R5.4.2**
handoff (async `POST /content`) in `ComposerMode.tsx:59-70`.

Reusable for append: the `DesignerProposal` staging envelope, the captured
`baseRevision` + `boundary`, the one-shot guard, and the outcome/notice handling.
**Not** reusable as-is: the bridge is hardcoded to `pending.proposal.document`
and `applyExternalDocument`; an append proposal carries `operations` and must
call `applyDocumentOperations`. This is a small, concrete extension - not an
architectural blocker.

## 3. Definition of append

The canonical document is a plain ordered tree: `CanonicalDocument.blocks:
CanonicalBlock[]` (`canonical.ts:283-286`), where a block is
`{ id?, type, attrs?, content?, children?, source?, rawHtml? }`
(`canonical.ts:258-274`). Section order is array order; nesting is `children`.
"Append" here means: **insert new top-level blocks after the existing last
top-level block**, using the existing operation vocabulary - not concatenating
JSON and not replacing the document.

Smallest deterministic transformation from a Composer `CanonicalDocument` to
operations against an existing document:

- Walk the composed **top-level** blocks in order.
- For a block `B` whose type is `hero` or `section` and whose direct children are
  only `heading` or `paragraph` blocks:
  - emit `insert_section { ref, section: { kind: B.type, variant?, layout? },
    position: { mode: 'document_end' } }`, where `variant`/`layout` are copied
    from `B.attrs` (both are already canonical and accepted by
    `sectionAttrs`, `documentOperations.ts:358-364`);
  - then emit one `insert_text` per child **in document order**, targeting
    `{ mode: 'ref', ref }` (default `at: 'end'`, so sequential pushes preserve
    order), with `{ type:'heading', level: attrs.level, text }` or
    `{ type:'paragraph', text }` (`documentOperations.ts:110-114, :366-371`).
- Any other top-level block, and any container whose child is not a
  heading/paragraph, is recorded as a **gap** (see section 7) - never dropped and
  never flattened.

There is no option to append a container with zero mapped children: the executor
rejects empty containers as `result_incomplete` (`:428-436`), which correctly
matches "do not invent empty structure".

## 4. Composer -> operation mapping matrix

Composer vocabulary: `COMPOSITION_CONTAINER_TYPES` = hero, section, featureGrid,
featureCard, cta, callout, testimonial, stats, mediaText, footer; content types =
heading, paragraph, list, image, quote, code; leaf requiredContent = badge,
button, statItem (`compositionPlan.ts:74-78`, `canonical.ts:38-52`). A realistic
landing page (fixture `compositionPlanFixtures.ts:26-85`) is: hero(title, intro,
media image, primaryCta button) + section(title, body) + featureGrid(3
featureCards) + testimonial(quote, author) + cta(title, body, button) + footer.

| Composer structure | Canonical representation | Existing operation | Transformation needed | Safe in R5.4.3.4? |
| --- | --- | --- | --- | --- |
| hero (container) | `hero` + `children`, `attrs.variant/layout` | `insert_section {kind:'hero'}` | copy variant/layout; map each heading/paragraph child | only if every child is heading/paragraph |
| section (container) | `section` + `children`, `attrs.variant/layout` | `insert_section {kind:'section'}` | same as hero | only if every child is heading/paragraph |
| heading | `heading`, `attrs.level`, text `content` | `insert_text` heading (level 1..6) | copy level + concatenated text | yes |
| paragraph | `paragraph`, text `content` | `insert_text` paragraph | copy text | yes |
| image (composed) | `image` with **no** `attrs`/`mediaId` (`compositionWriter` never sets it) | `insert_image` requires string `assetId` (`documentOperations.ts:259`) | impossible without a real asset | no - honest gap |
| list | `list` + `listItem` children with text | none (`insert_text` is heading/paragraph only) | needs a new op type | no - gap |
| quote | `quote` + text | none | needs a new op type | no - gap |
| code | `code` + text | none | needs a new op type | no - gap |
| featureGrid / featureCard | container / leaf-only node | none | needs new op + nested container creation | no - gap |
| cta | container | none | needs a new op type | no - gap |
| callout / testimonial / stats / mediaText / footer | container | none | needs a new op type | no - gap |
| badge / button / statItem | leaf | none | needs a new op type | no - gap |

Net representable subset in R5.4.3.4: `hero`/`section` containers whose children
are exclusively `heading`/`paragraph`. Because the realistic fixture's hero
carries a media image and a CTA button, the **only** fully representable
top-level node in that fixture is the plain `section` (heading + paragraph).
Everything else is an honest gap. This is a genuine coverage limit, not an
implementation detail, and it must be surfaced in the UI.

## 5. Insertion semantics

The operation vocabulary already expresses every insertion point needed here
(`documentOperations.ts:79-83`): `document_start`, `document_end`,
`before_block`, `after_block` (and `insert_text`/`insert_image` can target a
`ref` or a block `path`). Therefore:

- **Recommended v1**: append all mapped blocks with
  `position: { mode: 'document_end' }`. It is the simplest deterministic
  semantics, matches the brief's "append after the last existing section", and
  preserves the composed top-level order because each `document_end` push
  appends to the tail.
- **Not in v1**: insertion relative to a selected section/block. The vocabulary
  supports it (`after_block`/`before_block`, exactly what
  `sectionCreationService.sectionPositionFor` uses at `:52-65`), but it requires
  a contextual insertion UI, which this slice must not invent.
- Semantic caveat to state in the implementation: a composed document usually
  starts with a hero. Appending it at the end of a non-empty document is
  deterministic but often not where a user wants it. A later slice can choose
  `document_start` for a hero when the base document has none; that is a product
  decision, not a vocabulary gap.

## 6. ID and reference safety

- The operation vocabulary carries **no canonical ids**: operations use a
  batch-local `ref` only, which is erased from the result, and the executor
  synthesises no `id` (`documentOperations.ts:11-14`, test
  `documentOperations.test.ts:135-140`). `textBlockOf`/`imageBlockOf`
  (`:366-380`) produce id-less blocks.
- Composed documents **do** carry ids only on leaf/requiredContent blocks, and
  those are the deterministic `compositionSlotId` values (e.g. `hero__title`,
  `compositionPlan.ts:122-124, :403`). Composed container blocks carry no id
  (`compositionPlan.ts:434`); writer-created `listItem` blocks carry none
  (`compositionWriter.ts:188`).
- Consequence: mapping composed -> operations **drops** the composed slot ids.
  That is consistent with every existing inserted block (all id-less) and with
  the explicit "no persistent identity synthesized" boundary. No collision with
  existing base-document ids is possible because the appended blocks are
  id-less, and the base is only read (deep-cloned) by the executor.
- **No id remapping is required.** The one reference-bearing field that could
  cross the boundary is `insert_image.image.assetId` -> `attrs.mediaId`
  (`documentOperations.ts:373-380`); composed images have no asset, so there is
  nothing to remap and no dangling reference is created.
- If preserving composed slot ids ever becomes a requirement, that is a new
  operation field (additive vocabulary change) and is out of scope here.

## 7. Unsupported-structure behavior

There is currently **no partial-apply mechanism**: the executor is all-or-nothing
and throws on `result_incomplete`/`result_invalid`; `EditorContext` maps that to
`apply-failed`. A batch either applies whole or not at all. So the honest
behavior is to decide representability **before** building the batch and to
report every unrepresentable block explicitly.

Recommended: the pure transform returns both the operations and a typed gap
report, e.g.

```ts
export interface CompositionAppendGap {
  path: number[];                 // structural path in the composed document
  type: string;                   // canonical block type
  reason: 'unsupported_block' | 'unsupported_child' | 'image_without_asset';
}
export interface CompositionAppendMapping {
  operations: DocumentOperation[];
  gaps: CompositionAppendGap[];
}
```

Rules:
- Supported blocks are mapped; unsupported blocks/children are listed in `gaps`.
- If `operations` is empty, the append is refused with the gap report shown -
  never a fallback to whole-document replacement (which would destroy content).
- The UI must present the gap report before apply and must not claim the full
  composition was applied. This satisfies the honesty rule.

Existing reporting options considered: `DesignerProposal.review` exists
(`DesignerReview { ok, errors, warnings, score }`,
`designer.ts:273-290`) and can carry `warnings: DesignerReviewIssue[]`
(`code`/`message`), so the gaps *could* be mirrored there. Because the append is
client-applied and the proposal is only an in-memory transport (server apply
refuses `operations`), the transform result should be the source of truth; the
`review.warnings` mirror is optional and not required for R5.4.3.4.

Crucially, the distinction the brief asks for is:
- **successfully mapped**: hero/section containers with heading/paragraph
  children;
- **unsupported**: everything else in section 4 (needs no new machinery to
  detect - it is a type/shape check);
- **representable only after new op types**: list, quote, code, featureGrid,
  cta, callout, testimonial, stats, mediaText, footer, badge, button, statItem,
  and asset-less images.

## 8. Proposal and review semantics

1. Can Composer produce an operation proposal without mutating? **Yes** - the
   transformation is pure and the batch is data; nothing writes until the editor
   applies it.
2. Can it be reviewed before apply? **Yes** - client-side, exactly like the
   embedded-agent `operations` surface (`EmbeddedAgentStatus.tsx:137-178`). The
   Designer view's `EditReview` does **not** render `proposal.operations` today
   (`views/Designer.tsx`), so review belongs in the Composer/workspace surface,
   not Designer.
3. Appliable through `EditorContext.applyDocumentOperations`? **Yes**
   (`EditorContext.tsx:163-203`).
4. Revision guard: both the live document revision and `batch.baseRevision` must
   equal `expectedRevision` (`EditorContext.tsx:167-170`).
5. Document changes between proposal and apply -> `stale-revision`; no write.
6. Rejection/discard: existing behavior is **local-only** (Designer `reject`
   never calls the API; embedded agent `close` bumps the epoch). Reuse that:
   cancel clears the staged pending value.
7. Proposal vs mutation is already distinguished: `DesignerProposal` is never
   persisted and `DesignerService.apply` refuses `operations`
   (`designerService.ts:455-461`); only the editor mutates. No new review
   framework is needed.

## 9. Revision and async safety

The append apply is **synchronous** once the composed document exists: Composer
generation is already complete and held in `Compose` state, so the only steps are
transform -> stage -> mode switch -> editor transaction. Safety requirements and
how the existing mechanisms cover them:

| Requirement | Mechanism (unchanged) |
| --- | --- |
| Capture the workspace boundary | shell captures `session.boundary` at staging (`ProjectWorkspaceShell.tsx:193`) |
| Capture the expected revision | `documentRevisionOf(ws.live.current.doc)` at staging |
| Transform operations | pure function, run at staging time |
| Stale operations after a document switch | bridge compares `session.boundary` (`CompositionApplyBridge.tsx:67-71`) |
| Operations from an obsolete revision | `EditorContext.applyDocumentOperations` revision check (`EditorContext.tsx:167-170`) |

No new epoch, session generation or document identity is introduced. Because
there is no async gap between staging and apply, `useOperationBoundary` is not
required (same as R5.4.3.2); if apply is ever made asynchronous, the R5.4.2
`beginHandoff` pattern (`ComposerMode.tsx:59-70`) is the precedent to reuse.

## 10. Compatibility with R5.4.2 and R5.4.3.2

- **R5.4.2 new document** (unchanged): `Composer -> POST /content ->
  requestDocumentSwitch -> save barrier -> editor`. No part of the append path
  touches this.
- **R5.4.3.2 empty current document** (unchanged): `Composer -> CanonicalDocument
  -> DesignerProposal.document -> applyExternalDocument`. The append path is a
  sibling branch keyed on the document being **non-empty**; the two are mutually
  exclusive by the emptiness predicate `isCanonicalDocumentEmpty` already used
  for eligibility (`ProjectWorkspaceShell.tsx:109-115`).
- The append proposal uses the same `DesignerProposal` envelope and the same
  `baseRevision`/`boundary` captures; it adds no document identity and no second
  session. R5.4.3.2's bridge code path stays byte-for-byte in behavior: when a
  proposal has no `operations`, it still calls `applyExternalDocument`.

## 11. Recommended R5.4.3.4 implementation boundary

Smallest slice that makes the append real, using only existing mutation paths:

1. **Contracts (pure transformation, no deps)**: add
   `packages/contracts/src/compositionAppend.ts` exporting
   `mapCompositionToAppendOperations(composed: CanonicalDocument):
   CompositionAppendMapping` (section 7 shape) plus the gap types; export from
   the `@seo/contracts` index. Deterministic, synchronous, no ids, no persistence.
   This is the "pure transformation layer" the architecture supports.
2. **Web bridge**: generalise `PendingComposition` into a small discriminated
   value (replace vs append) or add a sibling, and make
   `CompositionApplyBridge` branch: `proposal.operations` ->
   `applyDocumentOperations(batch, expectedRevision)`; otherwise the existing
   `applyExternalDocument`. Keep the boundary check, the one-shot guard, the
   `ready` wait and the `CompositionApplyOutcome` result type unchanged.
3. **Shell**: add `canAppendComposition` (editor + ready + **not** empty) and
   `appendComposition(document)` that transforms, refuses when there are no
   operations, stages `{ version, baseRevision, document: baseDoc, operations:
   batch }`, and moves to editor mode; keep `canApplyComposition`/`applyComposition`
   for the empty path. Hold the gap report for display.
4. **Composer surface**: add an "Add to current document" affordance (alongside
   the existing R5.4.3.2 "Apply to current document"), enabled only for
   representable non-empty output, with the gap report shown before apply. Do not
   redesign the Composer.
5. **Do not touch**: `documentOperations.ts` operation types or executor,
   `DesignerService.apply`, the session/boundary/revision model, R5.4.2, and the
   R5.4.3.2 replacement behavior.
6. **Tests**: contracts mapping (hero/section+heading/paragraph mapped; gap for
   featureGrid/cta/image/list/button; deterministic order; no synthesized ids);
   bridge append (applies via `applyDocumentOperations`; boundary and stale
   revision refuse); shell append (non-empty applies operations, no `/content`,
   no switch; empty still replaces; R5.4.2 handoff untouched); Composer gap
   display.

## 12. Explicit non-goals

- No new operation types and no `DocumentOperationBatch` redesign.
- No new proposal/review framework; `DesignerProposal` remains the envelope.
- No server-side apply for operations (stays editor-only).
- No Composer UI redesign, no standalone Composer route retirement.
- No media/asset resolution for composed placeholder images.
- No id remapping and no preservation of composed slot ids.
- No changes to Designer, EditorMode architecture, or the canonical
  session/document model.
- No database migration.
- No implementation of partial-apply behavior in this slice; R5.4.3.3 changes
  documentation only.
