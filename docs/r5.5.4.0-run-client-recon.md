## 2. The one endpoint (facts, unchanged)

- `POST /projects/:projectId/designer/runs` (editor+), returns `202`
  `{ data: { run, reused } }`; never synchronous
  (`apps/api/src/http/routes/designer.ts:250-291`).
- Body (intent): `{ mode:'intent', instruction, content_id }` for an existing
  document, or `{ mode:'intent', instruction, base_revision }` for a creation.
  `content_id` and `base_revision` are mutually exclusive (route zod,
  `designer.ts:178-190`).
- `editor_context?: ImageInsertionContext` is accepted **only** with
  `content_id` (`designer.ts:161-176`). It is the sole editor-side context the
  endpoint accepts; the route does not accept a client canonical document or a
  selection.
- `idempotency_key?: string` is accepted (`designer.ts:130`). On a hit the
  service returns the existing run with `reused: true`
  (`agentRunService.ts:202-208`); on insert it persists the key and relies on the
  unique index to collapse a concurrent race (`agentRunService.ts:213-257`).
- `GET /projects/:projectId/designer/runs/:runId` (viewer+, project-bound)
  returns the durable `AgentRun`; a foreign/unknown id is not found.
- The run is project-scoped and durable (`seo_agent_runs`, `kind:'design'`,
  `queued -> running -> succeeded|failed`); the proposal is persisted in
  `result_json` only on success. Status predicates live in
  `packages/contracts/src/agentRun.ts` (`isTerminalAgentRunStatus`,
  `isValidAgentRunStatus`, `isAgentRunId`).

**Finding (unused capability):** neither web client sends `idempotency_key`, and
no web source constructs one (`apps/web/src` has no `idempotency_key` sender).
Because the key is the only path to `reused: true` across separate requests, the
`reused` flag is effectively always `false` from the current UI. The server
capability exists; the clients do not use it.

## 4. Durable run identity and bookmark semantics (first-class)

This is the part to settle before writing the controller, because it defines what
"the same run" means across resume, inspect and reconnect.

**Today**

- Designer mode is the only surface with durable identity: a project-scoped
  bookmark (`seo.designer.run.<projectId>`). It survives reload and re-authorizes
  the run against the URL project on every read, so a foreign id is not leaked.
- Editor mode has no durable identity. Navigating away or closing the surface
  orphans the in-flight run: the worker still completes it and persists the
  proposal, but the UI cannot reconnect to it.
- The Writer precedent keys on document as well:
  `seo.writer.run.<projectId>.<contentId>` (`WriterPanel.tsx`). The Designer key
  is project-only, so two documents in one project share one bookmark slot; a run
  restored for document A while B is open is already surfaced as a foreign
  proposal (R5.5.1).

**Questions the controller must answer (for review)**

1. **Key scope:** should the durable run bookmark be
   `seo.designer.run.<projectId>` (current, project-scoped) or document-scoped
   like the Writer (`.<projectId>.<contentId>`, with a separate creation slot)?
   Document scope removes the shared-slot ambiguity and matches the Writer; it
   also needs a defined creation key.
2. **One bookmark or per-surface:** a single shared key means the Designer mode
   and the editor agent contend for the same slot. Per-surface keys
   (`...designer...` / `...agent...`) preserve current behavior; one key enforces
   "one run per project". The ADR says one controller, not necessarily one
   stored run.
3. **Idempotency key:** should a submission send `idempotency_key` (e.g. derived
   from project + document + instruction hash) so a double-submit or a resume
   collapses onto the same run via the existing server capability? This is the
   server's intended reuse path and is currently unused.
4. **Reconnect scope:** should the editor surface gain a bookmark at all, or is
   the durable bookmark a Designer-mode-only affordance? Reconnecting the editor
   run would change editor UX and must be decided explicitly, not implied.

**Recommendation (for sign-off):** make the controller accept an explicit
`bookmarkKey` and `idempotencyKey` from its adapter, defaulting to today's
behavior (Designer mode bookmarks project-scoped; editor does not bookmark), so
R5.5.4 is behavior-preserving. Choose document scope / editor reconnect as a
separate, visible decision rather than smuggling it in.

## 5. Proposed single run controller boundary

**Owns (server lifecycle, shared):**

- Submit `POST /designer/runs` (optional `editor_context`, optional
  `idempotency_key`), returning the durable run pointer + `reused`.
- Durable identity: read/write/clear the bookmark (key supplied by the adapter).
- Restore-on-mount, re-authorize, and clear-on-404.
- One epoch guard covering restore, submit, poll and reset.
- One poll loop at `pollMs` with an optional max-attempt budget; stop at terminal;
  transient-read retry without dropping the last snapshot.
- Classify the run into a shared outcome (reuse `embeddedAgentOutcomeFromRun`,
  generalized) and expose the raw `AgentRun`.
- Expose lifecycle transitions (`idle|submitting|queued|running|succeeded|failed`)
  and typed transport errors, without product copy.

**Does NOT own (surface policy):**

- Presentation state machine and copy (`EmbeddedAgentState` vs the Designer
  view's `mode`/`applyState`).
- `blockedReason` / `canSubmit` policy (dirty/ready/unrepresentable/configured/
  role). These are editor-context and Designer-form concerns.
- Proposal classification and application (`planDesignerMutation`,
  `applyImageInsertion`, `applyDocumentOperations`) - R5.5.2 already routes these.
- The `generation_required` confirmation flow, image context building, review
  hold, chrome, and navigation.
- Whether/how to reconnect the editor surface (section 4).

**Shape:** a `DesignerRunController`/client (pure module plus a thin hook) that
both `useDesignerRun` and `useEmbeddedAgent` consume. The controller is the one
brain; each hook is a mouth that keeps its own UI state. This is explicitly not
one hook calling the other.

**Parity checks before deleting duplicate logic:** existing `Designer.test.tsx`
(25), `EmbeddedAgentEntry.test.tsx` (32), and `embeddedAgent.test.ts` (47)
behavior must hold unchanged; add a controller-level race suite (restore, double
submit, document switch, 404 bookmark clear, poll stop at terminal, transients).

## 6. Divergences that are policy, not lifecycle (keep)

- **Outcome vocabulary:** editor normalizes to product outcomes; Designer shows
  raw status/proposal. Keep both, fed from one classifier.
- **Poll budget:** the editor's 60-attempt cap is a UX policy; the Designer has
  none. Keep it as an option, not a shared default.
- **Error copy:** product-facing in the editor, structured in the Designer. The
  controller returns typed facts; adapters render copy.
- **Bookmark presence:** Designer bookmarks, editor does not (today). Governed by
  the adapter-supplied key.
- **Application:** editor applies, Designer hands off to the shell. Fully out of
  scope for the controller.

## 7. Decisions (approved before implementation)

Approved before R5.5.4a:

1. **Bookmark key scope:** behavior-preserving. The controller takes an
   adapter-supplied `bookmarkKey`; Designer keeps its project-scoped key, the
   editor keeps none.
2. **One shared bookmark vs per-surface:** per-surface, expressed through the
   adapter-supplied key.
3. **Idempotency key:** deferred. Neither client sends one; recorded as a
   follow-up so the server's reuse path stays intentionally unused for now.
4. **Editor reconnect:** no. The editor run stays session-only.
5. **Sequencing:** split. R5.5.4a extracts the controller behavior-preserving;
   R5.5.4b would change bookmark/reconnect policy separately if approved. See
   `docs/r5.5.4a-single-run-controller.md`.
