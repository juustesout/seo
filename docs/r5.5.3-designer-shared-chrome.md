# R5.5.3 - Designer shared chrome and review hold

Status: **delivered**. The Designer now uses the one shared workspace chrome
(the shell's document header) instead of rendering its own page header, and it
reports an open review to the shell so a mode switch cannot silently discard it,
mirroring the Composer pattern (R5.4.6).

This milestone is integration only. It adds no new router, document id, loader,
autosave, history, context or workspace-state provider, no second chrome, and no
new provider, contract, migration or agent/planner change.

## 1. What changed

- **`ProjectWorkspaceShell.tsx`**: `showChrome` no longer branches on the active
  mode; it is shown for any mode while a ready, editable document is open
  (`lifecycle.status === 'ready' && canEdit`). `showCanvasControls` remains
  `activeMode === 'editor'`, so Composer and Designer get the shared header
  without the editor-only Insert/Preview controls.
- **Review navigation hold**: the shell now mirrors both
  `composerReviewOpen` and `designerReviewOpen`. `requestMode` refuses to leave
  Composer or Designer while that mode's review is open, with a mode-specific
  reason:
  - `Finish or cancel the composition review before leaving Composer.`
  - `Finish or cancel the Designer review before leaving Designer.`
- **`DesignerMode.tsx`** forwards a new `onReviewOpenChange` prop to the view; it
  already forwards `onApplyProposal`.
- **`views/Designer.tsx`**:
  - removed its own `PageHeader` (and the `@/components/ui/page-header` import);
    the shell's document header is the single chrome anchor;
  - added `onReviewOpenChange` and reports `reviewOpen = showEditReview && applyState !== 'rejected'`
    through an effect, clearing the hold on unmount. Only an **actionable edit
    review** holds navigation: a creation-mode proposal and a foreign-document
    proposal stay proposal-only and never block a mode switch.

## 2. Chrome ownership (after R5.5.3)

| Element | Editor | Composer | Designer |
| --- | --- | --- | --- |
| Shared document header | yes | yes | yes |
| Save indicator/status | yes | yes | yes |
| Insert/Preview canvas controls | yes | no | no |
| Page header of its own | no | no | no (removed here) |
| Editor-coupled assistant entry | yes | no | no |
| Review navigation hold | - | yes | yes (actionable edit review only) |

## 3. What did not change

- No second document identity, loader, save state or lifecycle: the header still
  reads `useWorkspaceSessionContext()`.
- No new editor infrastructure in Composer/Designer, so the R5.3.3 isolation
  guarantee is preserved (the assistant entry still mounts only in `EditorMode`).
- The Designer apply handoff (R5.5.2), run client (`useDesignerRun`), bookmarks
  and server routes are untouched.

## 4. Tests / verification

- `workspace/ProjectWorkspaceShell.chrome.test.tsx`: the designer case now
  asserts the shared document header and save state are **present** in designer
  mode, with the Insert/Preview canvas controls and assistant entry absent.
- `workspace/ProjectWorkspaceShell.designerApply.test.tsx` (5, +1): a new case
  pins the review hold (switch refused while open with the reason, allowed after
  close), alongside the existing apply/refuse cases.
- `views/Designer.test.tsx` (25, +2): the Designer reports an actionable edit
  review as open and clears it on reject, and does not hold navigation for a
  creation-mode proposal.
- Counts (after): `@seo/web` **634** tests / 62 files (was 631 / 62).
  `@seo/api` **1658** / 126 and `@seo/contracts` **483** / 26 unchanged.
  `pnpm typecheck`, `pnpm build` and `git diff --check` are clean.

## 5. Known gaps deferred to later R5.5 milestones

- **Single run controller**: `useDesignerRun` (Designer view) and
  `useEmbeddedAgent` (editor-native) remain two clients of the one
  `/designer/runs` endpoint; converging them is R5.5.4.
- **Legacy `/p/:id/designer`** view and the `DesignPackage` decision are R5.5.5.
- **popstate bypasses the review hold** for an in-flight apply; recorded as a
  hardening item, not fixed here.
