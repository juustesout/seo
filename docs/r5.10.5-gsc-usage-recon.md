# R5.10.5 - GSC Usage Instrumentation Recon

Reconnaissance record for recording Google Search Console API consumption as
`gsc_request` usage events through the R5.10.2 append-only ledger.

Recon only. No production code, migration, vocabulary or ledger schema is
changed by this slice. This document records the existing GSC call graph, the
exact HTTP boundary, retry/failure/scope behavior, the recommended
instrumentation seam, the source/idempotency decision, metadata, the test plan
and the open decisions that must be settled before coding.

The contract this must satisfy is `packages/contracts/src/usageEvent.ts`
(R5.10.1) and the ledger is `supabase/migrations/20260101000031_usage_events.sql`
(R5.10.2). The closest precedent is R5.10.4
(`docs/r5.10.4-dataforseo-job-usage.md`).

The vocabulary is fixed for this slice:

```ts
{ category: 'dataforseo', provider: 'gsc', unit: 'gsc_request', quantity: 1 }
```

## 1. Existing GSC architecture

There is exactly one GSC adapter and one HTTP client. There is no second client,
wrapper, service or side door to the Search Console API.

```text
caller (job executor | HTTP route)
      |
      v
GscDataSource (apps/api/src/providers/gsc/gscDataSource.ts)   <- adapter boundary
      |  apiWithRefresh(ctx, fn)  (token lifecycle + ONE 401 retry)
      v
GscApiClient (apps/api/src/providers/gsc/gscApi.ts)           <- HTTP boundary
      |  private request<T>()  ->  fetch(BASE + path)
      v
https://searchconsole.googleapis.com/webmasters/v3/...        <- external GSC API
```

`apps/api/src/providers/gsc/oauth.ts` is a *separate* module that talks to
`https://oauth2.googleapis.com/token` (authorization-code exchange and
refresh-token grant). It is not the Search Console API.

### Provider context

Every adapter call receives a `ProviderContext` from `buildProviderContext`
(`apps/api/src/context.ts:192`), which already attaches the R5.10.4 usage seam:

```ts
usage: {
  sink: container.usageEvents,          // the R5.10.2 append-only store
  sourceId: args.usageSourceId ?? null, // e.g. the job id
  nextOccurrence: (operation) => ...,   // 0-based sequence per operation, per execution
}
```

`ProviderContext` has `projectId`, `userId`, `config`, `credentials`, `logger`
and `usage`. It does **not** carry `accountId`; the ledger derives `account_id`
from `project_id` via the `seo_usage_events_set_account` trigger.

## 2. Complete list of external GSC operations

Actual Search Console API calls are made only by `GscApiClient`:

| Client method | HTTP | Endpoint (relative to `.../webmasters/v3`) |
| --- | --- | --- |
| `listSites()` | GET | `/sites` |
| `searchAnalytics(siteUrl, body)` | POST | `/sites/{encodeURIComponent(siteUrl)}/searchAnalytics/query` |

Everything else in the provider is either local or a different host:

- `disconnect()` deletes encrypted credential keys locally - no external call.
- `refreshAccessToken()` and `exchangeCode()` POST to `oauth2.googleapis.com/token`
  (documented separately in section 6; not `gsc_request`).
- `buildAuthorizationUrl()` builds a string - no call.

## 3. Actual HTTP/request seams

The single, GSC-specific choke point is `GscApiClient.request<T>()`
(`gscApi.ts:59`). It is the only place a `fetch` to the Search Console API
happens. It is intentionally "dumb and stateless": one invocation = exactly one
HTTP request, no internal retry, no polling, no rate limiting, no caching. The
two public methods are thin wrappers, one request each.

`GscDataSource.apiWithRefresh` is the adapter-boundary wrapper. It calls the
client's method through an `attempt` closure and may call it a second time after
a token refresh. `fetchDimension` loops weekly chunks, each iteration making one
`apiWithRefresh` call (and therefore one or two real requests).

## 5. Retry behavior

There is exactly one retry and it lives in the adapter, not the transport:

```text
apiWithRefresh(ctx, fn):
  access, refresh = read credentials          (local)
  attempt(access)                             -> real request #1
    on success            -> return
    on UnauthorizedError  -> refreshAccessToken()   (oauth2.googleapis.com, not GSC)
                             persist new token        (local)
                             attempt(newToken)        -> real request #2
```

- `GscApiClient.request` retries **nothing**; a `401`/`403` becomes
  `UnauthorizedError`, any other non-2xx becomes `Error`, `200` returns JSON.
- `apiWithRefresh` retries **once** after a refresh. Two consecutive auth
  failures propagate.
- There is no job-level retry of the fetch calls inside the executor; the whole
  `gsc_sync` job may be retried by the worker on failure, which re-runs the whole
  executor with a fresh context (and fresh `occurrence` counters).

Semantics consequence: at a request-level seam, a 401-then-refresh-then-retry is
**two** genuine Search Console API requests (one failed, one succeeded), so two
`gsc_request` facts (one `success:false`, one `success:true`) are honest. At an
adapter-level seam it would be one. The brief's default assumption is one actual
external request = one `gsc_request`, so the request-level seam is recommended
(section 11).

The refresh call to `oauth2.googleapis.com/token` is a separate Google host and
is **not** `gsc_request`. See section 6.

## 6. Failure behavior

No request is made (and therefore no usage event), when the failure is local and
happens before `fetch`:

- integration/token missing: `apiWithRefresh` throws
  `Search Console connection is missing OAuth tokens` before any client call.
- `siteUrl` missing: `this.siteUrl(ctx)` throws before `apiWithRefresh`.
- OAuth client not configured (`oauth()` throws): this only happens on the
  refresh branch, i.e. *after* request #1 already reached Google.
- local authorization/validation in routes/executor before the adapter call.

A request is made (and usage with `success:false` is possible) when:

- `fetch` resolves `401`/`403` -> `UnauthorizedError`.
- `fetch` resolves another non-2xx -> `Error` with truncated body.
- `fetch` rejects (network/DNS/abort) -> thrown before a response; the call was
  still attempted.

`GscApiClient.request` narrows the thrown body to 300 chars and never leaks the
token (the token is only in the request header). The original error must always
propagate unchanged; usage instrumentation is best-effort and must never be the
transaction boundary (same rule as R5.10.3/R5.10.4): a failed append is logged
and swallowed, and the GSC result/error is unaffected.

Edge case to decide in implementation: a `200` whose JSON body fails to parse
throws after a successful HTTP exchange. The recommended `success` value is
`res.ok` (the API request itself succeeded), recorded before JSON parsing.

## 7. Scope propagation

Current sources of scope:

- **Job (`gsc_sync`)** - `executors.ts:166`:
  `buildProviderContext({ projectId: job.project_id, userId: job.created_by, owner: { integrationId, providerType: 'gsc' }, config: { siteUrl } })`.
  Real `projectId`; `userId = job.created_by` (may be null in principle).
  **It currently does not pass `usageSourceId`** - a required implementation
  change (section 9).
- **Project routes** (`integrations.ts:295`, `:182`) - real `projectId`, real
  `userId`.
- **Account route** (`account.ts:93` `gscContext`) - `projectId =
  String(integration.project_id ?? '')`. The account-level GSC integration has
  `project_id = NULL` (Stage 4), so this resolves to the **empty string**. There
  is no project and no account carried on `ProviderContext`.

Consequence: a usage helper that follows the R5.10.4 shape (requires a UUID
`projectId` and derives `accountId` through the ledger trigger) would emit
**no event** for `/account/gsc/discover`. This is the one unresolved scope gap
and is recorded in section 18. The R5.10.2 ledger itself supports account-only
scope (`project_id` null, `account_id` set), but the current provider context
does not expose `accountId`.

Local operations (integration lookup, token read, property lookup, normalization,
persistence, dashboard reads) never carry external consumption and must not be
instrumented. Background job requests legitimately have `userId = null`.

## 8. Job callers

Only one background path calls the GSC API: the `gsc_sync` executor
(`executors.ts:149-207`). It builds a single `ProviderContext` and makes:

1. `fetchDaily(ctx, range)` -> 1 request
2. `fetchDimension(ctx, range, ['date','query'])` -> `ceil(days/7)` requests
3. `fetchDimension(ctx, range, ['date','page'])` -> `ceil(days/7)` requests

`gscSyncService.ts`, `projectGsc.ts` and `oauth.ts` only enqueue jobs, read the
DB, or talk to the token endpoint - none call the GSC API. No other job type
touches `getDataSource('gsc')`.

The R5.10.4 pattern is directly reusable: add `usageSourceId: job.id` to the
`buildProviderContext` call in the executor (line ~166-171), exactly as the
DataForSEO executors already do at `executors.ts:228,286,395,444`. Nothing else
in the job correlation system changes.

## 9. Idempotency

Use the R5.10.2 mechanism only; no second dedup layer. `sourceId` is the stable
operation identity when one exists:

- **Job path**: `sourceId = job.id` (`seo_sync_jobs.id`). Multiple requests
  within one job are disambiguated by `nextOccurrence(operation)` (0-based, one
  counter per operation, per execution). A worker re-execution builds a fresh
  counter, derives the same key sequence and dedupes against rows already
  written.
- **HTTP path** (discover / properties / test): there is no per-attempt domain
  record. `sourceId = null`, so `usageEventIdempotencyKey` returns null and the
  row is honestly non-deduplicatable (NULL keys are never deduped by the partial
  unique indexes). Do **not** substitute the `integrationId` (would collapse
  every future call into one event) or a timestamp/random UUID (forbidden by the
  brief).

Operation tokens must distinguish different request kinds so occurrence
sequences stay meaningful; recommended `list_sites` and `search_analytics`
(section 10).

## 10. Metadata

Keep it empty or minimal. `operation` already names the call, so do not duplicate
it in metadata. Do **not** store tokens, auth headers, raw responses, result rows,
`siteUrl` (a property URL, not needed - the project/job already scopes the fact),
request bodies, or timestamps.

If a discriminator is wanted, the only bounded, safe one is the searchAnalytics
dimension shape:

```ts
metadata: { dimensions: 'date' | 'date,query' | 'date,page' }
```

Recommendation: omit metadata entirely in the first implementation (smallest
surface, no secrets risk); the `operation` field plus scope is sufficient.

## 11. Recommended instrumentation seam

Instrument **`GscApiClient.request<T>()`** (`gscApi.ts:59`), the single
GSC-specific fetch choke point.

Justification against the brief:

- It is the *only* place a real Search Console API request happens, and it is
  GSC-specific (`BASE = searchconsole.googleapis.com/webmasters/v3`), not a
  generic Google/OAuth transport.
- 1 invocation = 1 request, with no retry/polling/rate-limiting of its own, so
  it is a genuine 1:1 request seam - unlike R5.10.4's `DataForSeoClient.request()`
  (which mixes auth, retries and `tasks_ready` polling and therefore had to be
  instrumented at the adapter boundary).
- It naturally covers `listSites` and `searchAnalytics` and therefore every
  adapter method, including the weekly `fetchDimension` chunks, with no
  per-caller instrumentation.
- It correctly counts the `apiWithRefresh` 401 retry as the second real request
  it is, matching the brief's default assumption.

Rejected alternative: instrumenting `GscDataSource.apiWithRefresh`. It would
count one usage per *logical* call, which under-counts the refresh retry and
requires touching every adapter method individually. It is less faithful to the
"one actual external request" definition. If product later decides on logical
counting, this is the alternate seam and the 401 retry is the only place the two
differ.

Design shape (no code in this slice):

- A small `apps/api/src/providers/gsc/providerUsage.ts` helper mirroring
  `providers/dataforseo/providerUsage.ts`: it builds and best-effort appends the
  events.
  - `buildGscUsageEvent({ projectId, userId, usage, operation, success })`
    -> `NewUsageEvent | null`; guard UUID `projectId` and token `operation`;
    `quantity: 1`, `unit: 'gsc_request'`, `category: 'dataforseo'`,
    `provider: 'gsc'`, `sourceId: usage.sourceId`, idempotency key via
    `usageEventIdempotencyKey({ category:'dataforseo', provider:'gsc', operation,
    unit:'gsc_request', sourceId, occurrence: usage.nextOccurrence(operation) })`.
  - `emitGscRequestUsage(...)`: calls `usage.sink.append`, catches and logs -
    never throws.
- Thread a tiny recorder into `GscApiClient`. `request()` already lives next to
  the `fetch`; give it an `operation` label (`'list_sites'` / `'search_analytics'`)
  and a recorder callback. The *adapter* builds that callback from
  `ctx.projectId`, `ctx.userId` and `ctx.usage`, so the client stays free of
  business logic/scope and only reports `(operation, success)`.
- `apiWithRefresh` passes `ctx.usage` when constructing the client; no other
  adapter method changes. `fetchDaily`/`fetchDimension`/`listProperties`/
  `testConnection`/`connect` need no instrumentation edits.
- Single layer only: do not also instrument `apiWithRefresh` or the adapter
  methods.

Token endpoint calls (`exchangeCode`, `refreshAccessToken`) are explicitly
**out of scope**: they hit `oauth2.googleapis.com`, not Search Console, and the
brief separates OAuth/token traffic from Search Console consumption.

## 12. Search Analytics analysis

`searchAnalytics` is one request per invocation, but the *application operation*
`fetchDimension` issues N requests:

- `chunkRanges(range, 7)` splits the window into contiguous 7-day chunks. A
  28-day default sync = 4 chunks. Each chunk is one `apiWithRefresh` call = one
  request (plus at most one refresh retry).
- `fetchDaily` uses a single date-dimensioned query for the whole range (`rowLimit
  400`) = 1 request.
- There is no cursor/`startRow` pagination in the client; the 25k row cap is
  handled by shrinking the date window, not by paging.
- Results are re-aggregated in memory (`fetchDimension`) and persisted by
  `seoWriter.persistGsc`; that aggregation/persistence is local and not usage.

Therefore the app operation vs actual requests mapping for a default 28-day job:

```text
fetchDaily                            -> 1 request  -> 1 gsc_request
fetchDimension(['date','query'])      -> 4 requests -> 4 gsc_request
fetchDimension(['date','page'])       -> 4 requests -> 4 gsc_request
                                     total 9 gsc_request (happy path)
```

Appending exactly where the request is made (inside `GscApiClient.request`)
yields the correct count automatically; no arithmetic at the executor is needed.

## 14. Cache analysis

There is **no** GSC response cache anywhere:

- `GscApiClient` is stateless per call (holds only a token).
- `GscDataSource` keeps no instance/local cache; every executor run re-fetches
  from Google.
- Dashboard/UI reads (`services/keywordService.ts`, `services/accountService.ts`,
  `services/contentIntelligenceService.ts`, `http/routes/seo.ts`,
  `http/routes/projectGsc.ts`) read only local tables
  (`seo_gsc_performance`, `seo_gsc_queries`, ...) and never call Google.
- `seoWriter.persistGsc` is durable domain persistence, not a cache that
  short-circuits a request.

So there is no cache seam to special-case: a local read never produces a
`gsc_request`, and every `GscApiClient.request` is a real external request.

## 18. Unresolved repository-specific questions

1. **Account-scoped discover has no honest scope.** `/account/gsc/discover`
   (`account.ts:238`) builds its context with `projectId = ''` because the
   account-level GSC integration has `project_id = NULL`, and `ProviderContext`
   carries no `accountId`. Under the R5.10.4-style helper (UUID project required)
   these live-discovery requests would emit nothing. Decide one of:
   - (a) accept no usage for account-scoped discovery in this slice (smallest
     change; matches "do not introduce a new account/project provider"), or
   - (b) extend the provider usage context to carry an optional `accountId` and
     allow `projectId: null`, emitting account-scoped events (the R5.10.2 ledger
     already supports `project_id is null, account_id not null`). This is a
     contracts/context change and should be its own decision.
   Recommendation: (a) for the first implementation slice, with (b) recorded as
   follow-up.
2. **Refresh-retry counting.** Confirm that the 401-then-refresh-then-retry is
   intended to be two `gsc_request` facts (request-level seam), not one. This
   recon recommends two, per the brief's "one actual external request" default.
3. **`200`-but-unparseable-JSON** should be recorded `success:true` (HTTP
   exchange succeeded) with the parse error propagated. Confirm product is
   comfortable with that; the alternative is `success:false`, which would be
   less faithful to "external request made successfully".
4. **Legacy project-scoped GSC integrations.** `integrations.ts` `/:id/test`
   and `/:id/gsc/properties` only resolve integrations with `project_id` set
   (`loadIntegration` filters by project). These are legacy after Stage 4; their
   usage would be project-scoped and deduplicatable only if a stable source id
   existed (it does not; `sourceId` would be null). No action needed, but note
   that these paths are non-deduplicatable by design.
