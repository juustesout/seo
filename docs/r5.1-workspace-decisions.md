# R5.1 Workspace Architecture Decisions (ADR)

Status: **Accepted**. Locked before R5.2 begins.
Companion to `docs/r5.1-workspace-architecture-recon.md` and
`docs/phase-5-roadmap.md`.

These five decisions resolve the open questions raised in the R5.1 recon
(section 10 there). They are binding for R5.2 onward: implementation must not
drift from them. The document-switch save barrier is the first R5.2 gate.

---

## Decision 1 - Canonical workspace route

**Decision:** keep the existing `/p/` convention. The canonical route is:

```
/p/:projectId/workspace/:mode
```

Supported modes: `designer`, `composer`, `editor`.

Base route `/p/:projectId/workspace` redirects internally to the default mode.

- Default mode: **Editor** (the current document-facing surface).
- Invalid mode: redirect to Editor, or render a controlled 404 if that matches
  existing routing conventions.
- Existing routes remain temporarily available through redirects or
  compatibility entry points.

**Why:**

- `/p/` is already established throughout the application
  (`apps/web/src/App.tsx:90`, `apps/web/src/lib/nav.ts:19`).
- `/projects/:projectId/` would introduce an unnecessary second convention.
- The mode in the URL makes the workspace deep-linkable and
  browser-navigation-friendly.

**Consequences:** the mode is a route sub-segment read in `parseRoute`
(`App.tsx:87-94`); `WorkspaceModeSwitcher` syncs mode changes to the URL without
a full reload; legacy `/p/:id/compose`, `/p/:id/designer` and
`/p/:id/content/:contentId` become compatibility entry points.

## Decision 2 - Workspace shell ownership

**Decision:** introduce a new product-level `ProjectWorkspaceShell`. The
existing `EditorWorkspace` and `EditorShell` remain editor-specific and are
**not** renamed into the product shell.

`ProjectWorkspaceShell` owns:

- Project identity
- Active document identity
- Active mode
- Shared workspace/session context
- Save status
- Selection/context shared across modes
- Loading and error boundaries
- Mode navigation
- Workspace-level lifecycle

`ProjectWorkspaceShell` does not own:

- Designer tools
- Composer panels
- Editor toolbar behavior
- Mode-specific API workflows
- Mode-specific local UI state

Target structure:

```
ProjectWorkspacePage
`- ProjectWorkspaceShell
   |- WorkspaceHeader
   |- WorkspaceModeSwitcher
   |- WorkspaceSessionProvider
   `- ActiveMode
      |- DesignerView
      |- ComposerView
      `- EditorView
```

**Why:** the phase needs one shell that owns identity, session and lifecycle,
while each mode keeps its own tools and panels. R5.1 recon established that no
project- or workspace-level session context exists today; state is passed as
props from `App.tsx` with `contentId` living inside `views/Content.tsx`.

**Consequences:** `EditorWorkspace` (`components/content/workspace/EditorWorkspace.tsx:58`)
becomes the internals of `EditorView`; `EditorContextProvider` /
`EditorSelectionProvider` move up to the session layer so all modes share one
live document and selection.

## Decision 3 - Autosave safety on document switching

**Decision:** document switching must pass through a centralized **save
barrier**. No mode switching or document switching may silently abandon dirty
content. The barrier belongs to the shared workspace/session layer, not to an
individual mode.

Required behavior:

```
User requests document switch
        |
Check dirty state
        |
If clean  -> switch
        |
If dirty  -> flush pending autosave
        |
If save succeeds -> switch
        |
If save fails    -> remain on current document
```

The system must never:

- Switch documents while a pending save can still overwrite or lose changes.
- Reset editor state before the save barrier completes.
- Treat a stale document prop as the authoritative saved baseline.
- Silently discard unsaved changes.

Recommended contract:

```ts
requestDocumentSwitch(nextDocumentId: string): Promise<SwitchResult>

type SwitchResult =
  | { status: 'switched' }
  | { status: 'blocked'; reason: 'save_failed' }
  | { status: 'blocked'; reason: 'save_in_progress' };
```

**Why:** R5.1 recon found a blocker - switching documents can lose unsaved
changes. `workspaceReady` flips false immediately on `open()`
(`views/Content.tsx:209`, `:318-326`), `useAutosave` then clears its timer and
returns (`components/content/useAutosave.ts:82-84`), the navigation helpers
never call `saveNow()` (`Content.tsx:318-357`), and `RichTextEditor` is
remounted (`workspace/EditorWorkspace.tsx:134`). This is the first R5.2 gate.

**Consequences:** the session layer must expose a flush/await primitive; mode
and document switches call it; add tests for "switch with pending edits" and
"save failure keeps the current document".

## Decision 4 - Authoritative Designer run engine

**Decision:** consolidate around the existing **server-backed Designer
execution path**. The authoritative flow is:

```
Designer intent
    |
Server-side planning/run engine
    |
Validated operations/proposal
    |
Explicit apply
    |
Document/editor update
```

The client must not maintain a competing interpretation of Designer execution.

- Select the server-backed engine as the source of truth.
- Retain client code only as presentation/orchestration where necessary.
- Remove or deprecate duplicate execution logic after parity is verified.
- Do not create a third orchestration path inside the workspace.
- The workspace invokes Designer capabilities through a stable service
  boundary, not into internal run-engine details.

**Why:** two independent engines exist over the same endpoints -
`components/designer/useDesignerRun.ts:74` and
`components/content/workspace/useEmbeddedAgent.ts:84` - each re-implementing
epoch guards, polling and outcome mapping, and apply capabilities are split
(`services/designerService.ts:441-461` refuses non-document proposals while the
embedded agent applies client-side).

**Consequences:** R5.5 (Designer integration) converges the two clients onto one
controller over the server run engine; parity must be verified before duplicate
logic is removed.

## Decision 5 - Unified write-path strategy

**Decision:** converge toward one canonical document mutation pipeline.

Current situation: server-side insertion/operation refusal in some paths,
client-side editor application in others, and three separate write paths into
`seo_content` (Compose create `views/Compose.tsx:144`, editor autosave
`views/Content.tsx:235-236`, Designer apply `views/Designer.tsx:178`).

Target architecture:

```
Intent / UI action / Agent proposal
                |
Canonical document operation contract
                |
Validation + authorization
                |
Canonical persistence
                |
Editor state synchronization
```

The editor may optimistically display an operation, but it must not become a
separate persistence authority.

Rules:

- All document mutations use the same operation contract.
- Persistence is centralized.
- Editor state reflects the persisted document and pending local operations.
- Designer and Composer do not write directly through bespoke database paths.
- Legacy write paths are wrapped, migrated, or retired.
- No second document model is introduced.

**Why:** `ContentService.write` (`services/contentService.ts:200`) is already the
single persistence target, but the three entry paths carry different client-side
guards and the operation contract (`packages/contracts/src/documentOperations.ts`)
is not yet the shared mutation vocabulary.

**Consequences:** R5.2 first creates the contract and identifies adapters;
migration is incremental. No immediate rewrite of every existing path.

---

## Locked decision summary

| Decision | Resolution |
| --- | --- |
| Canonical route | `/p/:projectId/workspace/:mode`, preserving `/p/` |
| Product shell | New `ProjectWorkspaceShell`, separate from editor-specific shells |
| Document switching | Central save barrier before switching |
| Designer execution | Server-backed engine is authoritative |
| Document writes | One canonical operation and persistence pipeline |

## First R5.2 gate

The document-switch save barrier (Decision 3) is the first R5.2 implementation
gate. Unsaved-changes safety must be real and tested before the workspace route
and mode switching are built on top of it.
