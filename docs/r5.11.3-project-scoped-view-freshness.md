# R5.11.3 - Project-Scoped View Freshness (H4)

Slice H4 of the R5.11 hardening plan (`docs/r5.11-hardening-recon.md`, section
B/E.3). The defect: `useAsync` kept its previous `data` across a change of its
identity deps, so a project-scoped view could paint the previous project's
payload while the new request was in flight.

## Defect (as previously reachable)

`useAsync` (`apps/web/src/lib/ui.tsx`) fetched on `deps` change and set
`loading = true` inside the effect, but left `data` untouched until the new
response resolved. `Dashboard` renders with
`if (loading && !data) return <Loading />` (`views/Dashboard.tsx:62`). Switching
project via the header select re-rendered the same `Dashboard` instance with the
new `projectId`; between the project change and the resolution of the new
request the component had `loading === false` (the effect had not run yet) and
the old `data`, so Project A's metrics rendered under Project B. This is the
"briefly render the previous project's data" finding H4.

## Fix

`useAsync` now drops the payload belonging to the previous scope during render,
before the new one resolves:

- A `prevDepsRef` holds the last identity deps; on every render the current deps
  are compared element-wise (`sameDeps` via `Object.is`) with the previous. On a
  difference the hook clears `data`, clears `error` and sets `loading = true`
  during render, so the stale value never commits to the DOM.
- `reload()` (the internal tick) is deliberately **not** part of this
  comparison, so a polling refresh keeps the current `data` and refreshes in
  place instead of flashing a loading state.
- The existing per-run `alive` guard already drops a late response from an
  abandoned deps run; the render-time clear complements it for the window before
  the new response arrives.

The change is confined to the shared hook and needs no consumer edit: every
project-scoped view (`Dashboard`, `Usage`, `Publishing`, `Data`, `Keywords`,
`Integrations`, the Knowledge panels, `ScheduleModal`, ...) inherits the
guarantee. No API, contract, schema, route, provider or usage change.

All current `useAsync` call sites pass primitive deps (strings, numbers,
booleans, `undefined`), so the element-wise comparison cannot flap on
freshly-created object/array identities. `Dashboard`'s existing
`loading && !data` gate is left as-is; it is now correct because `data` is
cleared on a scope change.

## Tests added

- `apps/web/src/lib/ui.test.tsx` (new, 4): the hook resolves the current payload;
  a deps change drops the previous payload before the new one resolves; a manual
  `reload()` keeps `data` during the refresh; a late response from the previous
  deps run is ignored.
- `apps/web/src/views/Dashboard.test.tsx` (new, 1): renders Project A's
  dashboard, re-renders the same instance with a new `projectId`, and asserts
  Project A's distinctive row is gone and the loading state shows before
  Project B's payload resolves; Project B then renders with no trace of A.
