# R5.10.6 - Publishing Usage Instrumentation Recon

Reconnaissance record for recording external publishing consumption as
`publishing` / `publish_attempt` usage events through the R5.10.2 append-only
ledger.

Recon only. No production code, migration, vocabulary, contracts or ledger
schema is changed by this slice. This document records the existing publishing
call graph, the actual external request boundary per publisher, retry/failure
semantics, scheduled vs manual publishing, job correlation, scope propagation,
the media-upload boundary, the recommended instrumentation seam, the test plan
and the open decisions that must be settled before coding.

The contract this must satisfy is `packages/contracts/src/usageEvent.ts`
(R5.10.1) and the ledger is
`supabase/migrations/20260101000031_usage_events.sql` (R5.10.2). The closest
precedents are R5.10.4 (`docs/r5.10.4-dataforseo-job-usage.md`) and R5.10.5
(`docs/r5.10.5-gsc-usage-recon.md`).

The vocabulary is fixed for this slice and must not change:

```ts
{ category: 'publishing', unit: 'publish_attempt', quantity: 1 }
```

## 1. Existing publishing architecture

Publishing is a Content Studio subsystem. A publication is a durable row in
`seo_publications`; the actual external call is made by a background worker job
of type `publish` (create), `publish_update` or `publish_delete`. No HTTP route
ever calls a publisher adapter synchronously.

There are exactly three publisher adapters in the tree:

- `wordpress` - real WordPress REST API (`WordPressClient`).
- `x` - real X (Twitter) API v2 text posting (`XOAuthClient.createPost`).
- `mock_social` - demo/test adapter, registered only when
  `ENABLE_TEST_PUBLISHERS=true`; it never calls an external platform.

```text
HTTP route (editor)                 schedule service (editor)
  POST /api/projects/:id/publications      scheduleService.create
        |                                        |
        | inserts seo_publications row           | inserts seo_publications row
        | + jobStore.enqueue('publish')          | + jobStore.enqueue('publish',
        |                                        |     idempotency_key=scheduleId...)
        v                                        v
                 seo_sync_jobs (durable queue)
                              |
                              v
              worker.runOnce -> executor 'publish'
                              |
                 +------------+-------------+
                 |                          |
        load seo_publications        load seo_publishers
        (project-scoped RLS)         (project-scoped RLS)
                 |                          |
                 +------------+-------------+
                              v
        registry.getPublisher(publisher.provider)
                              v
        buildProviderContext(container, { projectId, userId: job.created_by,
                               owner: { publisherId, providerType }, config })
                              v
        adapter.publish | adapter.update | adapter.delete
                              v
        provider-specific client -> external platform HTTP API
```

### Provider context

`buildProviderContext` (`apps/api/src/context.ts:192`) attaches the R5.10.4
usage seam to every adapter call:

```ts
usage: {
  sink: container.usageEvents,          // the R5.10.2 append-only store
  sourceId: args.usageSourceId ?? null, // e.g. the job id
  nextOccurrence: (operation: string) => number, // per-execution 0-based counter
}
```

The `publish` executor currently calls `buildProviderContext` **without**
`usageSourceId`, so `sourceId` is `null` at the publisher boundary today. The
publisher adapters do not read `ctx.usage`; publishing therefore emits no
`publishing` usage event. `buildPublisherProviderContext` (used by
`publishers.ts` `/test`) delegates to `buildProviderContext` and also passes no
`usageSourceId`; connection tests are not publication attempts and must not emit
usage.

## 3. Complete publish call graph

### Entry points (all job-backed)

1. `publications.ts POST /` -> `seo_publications` insert (`queued` or
   `scheduled`) + `jobStore.enqueue({ job_type: 'publish', params: {
   publication_id, remote_status } })`.
2. `publications.ts POST /:id/actions` -> `job_type` in
   `{ publish, publish_update, publish_delete }`, `params: { publication_id,
   remote_status }`.
3. `scheduleService.create` -> `scheduled` publication + one `publish` job with
   `params: { publication_id, remote_status: 'publish', schedule_id }` and a
   deterministic job-store `idempotency_key`.

There is no synchronous/manual adapter call outside the worker. "Manual
publishing" and "scheduled publishing" both converge on the same `publish`
executor.

### Executor dispatch (`executors.ts` `publish`, lines 729-795)

```text
publish         -> adapter.publish(ctx, { title, content, excerpt, slug, status })  -> 'published'
publish_update  -> adapter.update(ctx, remoteId, { title, content, excerpt, status }) -> 'updated'
publish_delete  -> adapter.delete(ctx, remoteId)                                     -> 'deleted'
```

All three update `seo_publications` only with the adapter-confirmed
`remote_id` / `target_url` / `published_at`; an adapter failure propagates to
the worker. `remote_status` (`publish` | `draft`) becomes the remote `status`.

### Per adapter

`WordPressPublisher` (`wordpress.ts`):

- `clientFor(ctx)` builds a fresh `WordPressClient` from `ctx.config.base_url`
  and `ctx.credentials` (`wordpress_username`,
  `wordpress_application_password`). It throws before any network call when
  config or credentials are missing.
- `publish` -> `WordPressClient.createPost` -> `POST /wp-json/wp/v2/posts`.
- `update` -> `WordPressClient.updatePost` -> `POST /wp-json/wp/v2/posts/:id`.
- `delete` -> `WordPressClient.deletePost` -> `DELETE /wp-json/wp/v2/posts/:id?force=true`.
- Each adapter method makes exactly one external request. No media upload, no
  featured image, no metadata call, no internal retry.

`XPublisher` (`xPublisher.ts` + `xOAuth.ts`):

- `publish` builds the text via `buildSocialTextPost`, rejects empty text and
  text over `X_POST_MAX_CHARS` (280) locally, then
  `withToken(ctx, (access) => XOAuthClient.createPost(access, body))`.
- `XOAuthClient.createPost` -> `POST https://api.x.com/2/tweets`.
- `withToken` retries **once** on a 401 by refreshing the access token
  (`POST /2/oauth2/token`) and re-issuing `createPost`. This is a
  provider-internal retry, not a job retry.
- `update` / `delete` throw `publisher_not_available` before any call.
- `connect` / `testConnection` call `fetchAuthenticatedUser` (`GET /2/users/me`)
  via the same client - a connection read, not a publication.

`MockSocialPublisher` (`mockSocial.ts`):

- `publish`/`update` return a deterministic `demo:<sha1>` id from the payload;
  `delete` is a no-op. Zero external requests.

## 4. Actual external request boundaries

The external attempt boundary is the provider-specific client method that issues
the remote publication HTTP request. It is **not** `fetch`, the adapter entry,
the job enqueue, the schedule, or the route.

| Adapter | Publication method | External request | Counts as a publication attempt? |
| --- | --- | --- | --- |
| `wordpress` | `WordPressClient.createPost` | `POST /wp-json/wp/v2/posts` | yes |
| `wordpress` | `WordPressClient.updatePost` | `POST /wp-json/wp/v2/posts/:id` | yes |
| `wordpress` | `WordPressClient.deletePost` | `DELETE /wp-json/wp/v2/posts/:id?force=true` | yes |
| `wordpress` | `WordPressClient.whoami` | `GET /wp-json/wp/v2/users/me` | no (connection read) |
| `x` | `XOAuthClient.createPost` | `POST https://api.x.com/2/tweets` | yes |
| `x` | `XOAuthClient.fetchAuthenticatedUser` | `GET https://api.x.com/2/users/me` | no (connection read) |
| `x` | `XOAuthClient.refreshAccessToken` / `exchangeCode` | `POST /2/oauth2/token` | no (token endpoint) |
| `mock_social` | `publish` / `update` / `delete` | none | no (no external platform) |

`buildSocialTextPost` is pure and must never be instrumented.

## 5. Definition of `publish_attempt`

**One `publish_attempt` = one actual HTTP request to a connected publisher's
remote API that attempts to create, update or delete a published object.**

- `quantity` is always `1`; `unit` is always `publish_attempt`.
- Connection/identity reads and OAuth token calls are not publication attempts.
- Local validation or configuration failures before any request emit nothing.
- `mock_social` emits nothing (no external platform).

Operation tokens (reuse the existing job_type names, which already describe the
lifecycle action):

```text
operation = 'publish'        // create
operation = 'publish_update' // update an existing remote object
operation = 'publish_delete' // delete an existing remote object
```

Applied to the brief's cases:

### Case A - local validation fails before any external call

`XPublisher.publish` empty/over-280 text, `clientFor` missing config/creds,
`XPublisher.update`/`delete` (`publisher_not_available`), missing
`publication_id`, missing `remote_id`, unknown publisher -> **0 events**.

### Case B - external request made and accepted

`createPost`/`updatePost`/`deletePost` returns a non-error HTTP response ->
**1 event, `success = true`**.

### Case C - external request made and rejected

The remote responds 4xx/5xx (WordPress `WordPressError`, X `XApiError` mapped to
`PublisherError`) -> **1 event, `success = false`**. The `PublisherError` remains
authoritative and is what the worker persists.

### Case D - transport failure after a request may have been sent

The client cannot know whether the remote received the request. Following
R5.10.5, an attempt is recorded at the moment the request is initiated:
`fetch` throwing is **1 event, `success = false`**. `success = false` means
"the attempt did not complete", not a claim that the remote rejected it. This is
the only honest option; no event would hide a real attempt, and `success = true`
would fabricate success.

## 6. Retry semantics

| Retry mechanism | Location | External requests | Usage consequence |
| --- | --- | --- | --- |
| Transport retry | none in `WordPressClient` / `XOAuthClient.createPost` | - | - |
| Provider-internal retry | `XPublisher.withToken` refresh-once after 401 | 1 or 2 `POST /2/tweets` per logical publish | each `createPost` call is observed separately (see below) |
| Job retry | `worker.runOnce` on a `retryable` failure (`jobStore.fail(..., true)`) | re-executes the whole executor | same `job.id`; deduplicated by the R5.10.4 occurrence reset (see open decision) |
| Manual re-publish | `POST /:id/actions` | new job + new external request | new `job.id` -> new fact |
| Scheduler retry | `scheduleService` creates one job; the job store owns retries | - | same as job retry |

`retryable` comes from `jobErrorPayload` (`apps/api/src/jobs/types.ts`):
`PublisherError` carries an explicit `retryable`; otherwise 429/5xx ->
retryable, other 4xx -> terminal, no status (transport) -> retryable. The worker
only records the R5.10.4 `job` fact on a terminal outcome.

**X refresh-once.** Within one `adapter.publish`, an expired access token causes
the first `createPost` to fail 401 and a second `createPost` to run after the
refresh. Both are real `POST /2/tweets` attempts, so the operator should emit
one fact per `createPost` (first `success = false`, second its outcome), matching
R5.10.5's "a 401-refresh-retry = 2 facts". The token refresh itself
(`refreshAccessToken`) is not a publication attempt and emits nothing.

**Job retry.** The durable worker retry reuses the same `seo_sync_jobs` row and
therefore the same `job.id`. R5.10.4 resets the occurrence counter on every
execution, so a re-execution produces the same idempotency key and is
deduplicated. Whether a job retry should be a second `publish_attempt` is the
one unresolved product decision (Section 17). It is **not** resolved by adding a
new retry system.

## 7. Scheduled publishing

Scheduled publishing is not a separate seam:

1. `scheduleService.create` inserts a `scheduled` `seo_publications` row and one
   `publish` job with `run_after = scheduled_at`, `params.schedule_id`, and a
   deterministic job-store `idempotency_key` (`scheduleIdempotencyKey`).
2. The worker claims the job when it is due and runs the same `publish`
   executor; `syncScheduleStatus` reflects `publishing` -> `published`.
3. The adapter boundary is identical to manual publishing.

The job-store `idempotency_key` only prevents duplicate *jobs*; it has no
bearing on usage. Scheduled and manual publishing must be instrumented at the
same shared provider boundary.

## 8. Manual publishing

"Manual" and "scheduled" are the same executor path; the difference is only
`run_after` and `params.schedule_id`. Manual publishing still goes through
`seo_sync_jobs`, so it always has:

- `caller`: `POST /api/projects/:projectId/publications` or
  `POST /:id/actions`.
- authenticated user: `job.created_by` (the enqueuing `auth.users.id`).
- provider: `seo_publishers.provider`.
- publish identity: `seo_publications.id` (and, after a create, `remote_id`).
- job id: `seo_sync_jobs.id`, a stable `sourceId`.

There is no synchronous "publish now" path that bypasses the job. Therefore
every product publishing action has a stable `sourceId`; no artificial id is
required.

## 9. Job correlation

`job.id` **is** available at the provider boundary: the executor has `job` and
builds `ctx` immediately before calling the adapter. The recommended wiring is
the R5.10.4/R5.10.5 pattern, with no new mechanism:

```ts
const ctx = buildProviderContext(container, {
  projectId: job.project_id,
  userId: job.created_by,
  owner: { publisherId: String(publisher.id), providerType: String(publisher.provider) },
  config: publisher.config ?? {},
  usageSourceId: job.id, // NEW - the only executor change
});
```

The adapter then binds `ctx.usage` (sink + sourceId + occurrence) to a
publishing observer and passes it to its client. `job.id` reaches the provider
boundary unchanged.

One job can legitimately generate multiple facts:
- `publish_update` / `publish_delete` use a different `operation`, so they do
  not collide with `publish`.
- X refresh-once yields two same-operation requests within one execution; the
  existing `nextOccurrence(operation)` counter (0, 1) distinguishes them.

`buildPublisherProviderContext` (used by `publishers.ts` `/test`) does not need
`usageSourceId`: connection tests never emit usage. If it is later used for a
publication call, it will need the same parameter.

## 10. Scope propagation

Scope reuses the canonical model already present on `ProviderContext`; no new
lookup is introduced.

| Field | Source | Notes |
| --- | --- | --- |
| `projectId` | `job.project_id` (worker) | always the project that owns the publication and publisher. |
| `userId` | `job.created_by` | the real enqueuing user for both manual and scheduled publishing; `null` only when the job has no `created_by`. |
| `accountId` | not set by the caller (`null`) | the R5.10.2 `seo_usage_events_set_account` trigger mirrors the project's account on insert. Callers must not resolve accounts. |
| `provider` | `publisher.provider` (`wordpress` / `x`) | reuse the registry id; do not hardcode. |
| `sourceId` | `job.id` | stable correlation handle. |

The publish executor already passes `userId: job.created_by`; usage should
preserve it rather than forcing `null`, because publishing is user-initiated
even though it runs in the worker. If the implementer prefers the strict
"worker-originated -> `userId = null`" reading, that is a product decision, but
`job.created_by` is available and is the truthful actor.

## 11. Idempotency / occurrence

Reuse the R5.10.2 deterministic key builder
(`usageEventIdempotencyKey`, `packages/contracts/src/usageEvent.ts`):

```text
v1|publishing|<provider>|<operation>|publish_attempt|<sourceId>|<occurrence>
```

- `sourceId = job.id` for job-backed publishing.
- `occurrence = ctx.usage.nextOccurrence(operation)` - call it once per actual
  external request.
- A `null` `sourceId` disables dedup (`NULL` keys are not deduplicated); the
  recommended design keeps `sourceId = job.id`, so keys are stable.
- Never use timestamps, random UUIDs or response hashes as identities.

Within one execution, occurrence distinguishes repeated same-operation requests
(X refresh-once). Across job re-executions the key is currently identical, so a
job retry deduplicates - see Section 17.

## 12. Media-upload boundary

No publisher performs a media upload today:

- `WordPressClient.createPost` sends only `title`, `content`, `status`,
  `excerpt`, `slug` as JSON. There is no `/wp/v2/media` call, no featured-image
  assignment, no post-meta call.
- `XPublisher.publish` posts text only (`POST /2/tweets` with `{ text }`).
- `publish_kind` `image`/`video` is rejected by the capability gate before any
  job is created.

Media acquisition (`Unsplash`, `openai_media`) runs in the content pipeline
(`content_images` executor / media services) and is already a separate `media`
category. It is not part of publishing. Therefore counting a publication as one
`publish_attempt` cannot double-count an existing media usage category, and no
media event is emitted by the publishing seam.

Boundary rule for the future: if an adapter ever uploads media as part of
publishing, that upload is a `media` usage fact (its own provider/operation),
**not** a `publish_attempt`. Only the publication create/update/delete request is
a `publish_attempt`.

## 13. Provider-specific findings

### WordPress

A WordPress publication is exactly one REST request today. The publication
request is: `createPost` for `publish`, `updatePost` for `publish_update`,
`deletePost` for `publish_delete`. `whoami` is a connection check. There is no
internal retry and no cache. `WordPressError` carries the HTTP status for
`jobErrorPayload` classification.

### X

A logical publish can be one or two `POST /2/tweets` requests (refresh-once).
Local 280-char validation happens before any request. `update`/`delete` are not
implemented and never call out. `createPost` is the only publication request;
`fetchAuthenticatedUser`, `refreshAccessToken` and `exchangeCode` are not.

### Mock social

No external platform; must emit no usage event. This is a key reason to place
the seam in the provider-specific client rather than wrapping the adapter
interface: a generic adapter wrapper would wrongly count mock publishes.

### Provider table

| Provider | Publish operation | External requests | Retry model | Job-backed | Recommended seam |
| --- | --- | ---: | --- | --- | --- |
| `wordpress` | create / update / delete post | 1 | none (worker job retry only) | yes | `WordPressClient.createPost` / `updatePost` / `deletePost` |
| `x` | create text post | 1 or 2 (refresh-once) | provider refresh-once + worker job retry | yes | `XOAuthClient.createPost` |
| `mock_social` | demo publish | 0 | none | yes | none (never emits) |

## 14. Recommended instrumentation seam

Mirror R5.10.5 exactly: instrument the provider-specific HTTP client's
publication method with an optional, best-effort observer. Do not instrument
`fetch`, the adapter interface, the executor, the job store or the route.

```text
PublishRequestObserver = (operation, success) => Promise<void>

WordPressClient(..., observe?)  -> createPost/updatePost/deletePost report once
XOAuthClient(..., observe?)     -> createPost reports once
mock_social                     -> no client, no observer
```

- The observer is invoked once per actual external request, after the outcome is
  known (including a thrown `fetch`, reported `success = false`), before the
  method throws.
- The observer is wrapped so its own failure can never fail the publish call
  (`record()` try/catch, then `appendUsage` swallows persistence errors).
- The publisher adapter builds the observer from `ctx` (projectId, userId,
  provider id, `ctx.usage` sink/sourceId/nextOccurrence) using a small shared
  helper analogous to `apps/api/src/providers/gsc/providerUsage.ts`, and passes
  it into the client it constructs. WordPress builds a fresh client per call in
  `clientFor`; X builds one in `client()`.
- `whoami` / identity / token methods must not report, so the observer is only
  wired into the publication methods (or the client only reports from those
  methods).

Recommended event shape:

```ts
{
  accountId: null,                 // ledger trigger mirrors project's account
  projectId: ctx.projectId,
  userId: ctx.userId,              // job.created_by
  category: 'publishing',
  provider: 'wordpress' | 'x',     // publisher.provider
  operation: 'publish' | 'publish_update' | 'publish_delete',
  quantity: 1,
  unit: 'publish_attempt',
  success,                         // res.ok / request completed
  sourceId: ctx.usage.sourceId,    // job.id
  metadata: { mode: 'publish' | 'draft' }, // optional, bounded
  idempotencyKey: usageEventIdempotencyKey({
    category: 'publishing', provider, operation, unit: 'publish_attempt',
    sourceId, occurrence,
  }),
}
```

`mode` (remote `publish` vs `draft`) is the only candidate metadata; it is
bounded and not already represented by a field (`operation` is the lifecycle
action, not the remote status). If a stricter minimalism is preferred, emit
`metadata: {}`. Never include tokens, authorization headers, request bodies,
content, provider responses or arbitrary payloads.

Recommended additions (implementation slice, not this recon):

1. Successful publication: one adapter call records exactly one event,
   `category='publishing'`, `unit='publish_attempt'`, `success=true`.
2. Provider rejection: 4xx/5xx records one event `success=false`; the thrown
   `PublisherError` is unchanged and the usage append failure is swallowed.
3. Local validation failure: X empty/over-280, missing config/credentials, or
   `mock_social` -> **zero** events.
4. Transport failure: `fetch` rejects -> one event `success=false`.
5. X refresh-once: 401 then success -> two events (occurrence 0/1), token
   refresh never counted.
6. Job correlation: executor passes `usageSourceId = job.id`; `publish_update`
   / `publish_delete` use their own operation tokens.
7. Scope: `projectId`/`userId` from the job; `accountId=null` at the seam.
8. Usage append failure: publish behavior is unchanged (best-effort).
9. No double counting: a WordPress `publish` emits one event for `createPost`
   and none for `whoami`; `mock_social` emits none.

## 16. Explicit non-goals

Do not implement in this slice: publishing instrumentation; media-search or
external-embedding instrumentation; billing; pricing; cost calculation; quotas;
credits; usage UI or dashboard; usage vocabulary changes; usage ledger schema
changes; new publishing providers; publishing retries; publishing architecture
changes; media instrumentation beyond documenting the publishing boundary.

## 17. Unresolved repository-specific questions

1. **Job retry vs raw attempt.** `sourceId = job.id` plus the per-execution
   occurrence reset means a job retried after a retryable failure produces the
   same idempotency key and is deduplicated by the ledger. This counts one
   logical publication job, retaining the first persisted attempt's outcome
   (which may be `success=false` even though a later retry succeeded), whereas
   the brief's default hypothesis ("one actual external publishing attempt =
   one `publish_attempt`") would count each real retry. Resolve before coding:
   (a) accept R5.10.4 semantics (one fact per logical job; simplest, no new
   mechanism), or (b) count each attempt by including the durable, non-random
   `job.retry_count` in the source identity. Option (b) is a key-semantics
   change and should be a deliberate, reviewed decision.
2. **Update/delete as `publish_attempt`.** This recon counts external
   `publish_update` / `publish_delete` requests as `publish_attempt` facts
   because the closed vocabulary exposes only one publishing unit and the
   category is external publishing consumption. If the product intends
   `publish_attempt` to mean only "created a new publication", update/delete
   must be excluded (or the vocabulary revisited) - a decision, not a code
   detail.
3. **`userId` for worker publishing.** `job.created_by` is available and is the
   truthful actor; if the product mandates `userId = null` for all
