# R5.10.4 - DataForSEO and Job Usage Instrumentation

R5.10.3 instrumented AI and image generation. R5.10.4 instruments the two
remaining external-consumption boundaries: DataForSEO logical operations and
background job executions. It does not change the usage vocabulary or the ledger
schema, and adds no HTTP route, UI or MCP surface.

The central rule:

```text
logical provider consumption  !=  HTTP transport activity  !=  background execution

Never instrument DataForSeoClient.request() for usage accounting.
Count logical provider consumption at the DataForSEO adapter boundary,
and count background execution once at the worker boundary.
```

DataForSeoClient owns auth, rate limiting, retries and `tasks_ready` polling. If
usage were counted there, one 100-keyword task SERP run would become dozens of
fake "requests" as polling and retries repeat HTTP calls. Instead usage facts are
emitted around the *logical* adapter operations, and one job execution yields one
job fact.

## 2. Seam A - DataForSEO logical operations

Instrumentation wraps each logical operation inside `DataForSeoDataSource`; it is
never placed in `DataForSeoClient.request()`.

| Operation | category | provider | operation | units (quantity) |
| --- | --- | --- | --- | --- |
| Suggestions expansion | `dataforseo` | `dataforseo` | `keyword_research` | `request` (1), `keyword` (seeds submitted) |
| Related expansion (per seed) | `dataforseo` | `dataforseo` | `keyword_related` | `request` (1), `keyword` (1) |
| Ideas expansion (one call) | `dataforseo` | `dataforseo` | `keyword_ideas` | `request` (1), `keyword` (seeds) |
| Live SERP | `dataforseo` | `dataforseo` | `serp_live` | `serp_request` (keywords), `keyword` (keywords) |
| Task SERP | `dataforseo` | `dataforseo` | `serp_task` | `keyword` (keywords), `task` (batches created), `serp_request` (keywords) |
| Competitor discovery | `dataforseo` | `dataforseo` | `competitor_discovery` | `request` (1) |
| Competitor gap analysis | `dataforseo` | `dataforseo` | `competitor_gap` | `request` (competitor intersections run) |

Deliberate rules:

- **Batch quantity, not per-item rows.** One logical operation produces one fact
  set for each unit it consumed. `keyword_ideas` with 10 seeds is `request = 1`,
  `keyword = 10` - never 10 requests.
- **Suggestions are not keywords.** The suggestion rows returned by the provider
  are a result cardinality, not consumption; only the submitted seed count is
  `keyword`.
- **Returned gap keywords are not usage.** Gap analysis counts the competitor
  intersection calls actually made; the returned gap rows are not keywords
  consumed.
- **Not counted:** `tasks_ready` polling, `task_get` fetches and internal HTTP
  retries (transport, not consumption); credential `connect()` / `testConnection()`
  probes; local normalization; provider-result persistence; empty/no-op paths
  (an operation with nothing to submit emits nothing).
- **Failure is honest.** When a configured provider call fails after it was
  attempted, the operation emits `success: false` with the attempted quantities
  and the error is rethrown unchanged. A not-configured failure emits nothing
  because nothing reached the provider.

## 3. Correlation and dedup

The provider context carries an optional `usage` hook
(`ProviderUsageContext`): the write-only sink, a stable `sourceId`, and a
per-execution `nextOccurrence(operation)` allocator. Scope comes from
`projectId` / `userId`; the account is mirrored by the ledger's existing trigger,
so no second scope mechanism is introduced.

- `sourceId = job.id`, so a re-execution of the same job is deduplicated by the
  ledger's derived idempotency key.
- `nextOccurrence(operation)` yields a stable 0-based sequence, so a method
  invoked several times within one execution (related expansion, one call per
  seed) produces distinct facts that do not collide, while a re-execution
  reproduces the same sequence and dedups.
- No `DataForSeoClient.request()` instrumentation means no generic telemetry
  context and no per-HTTP-request identity is needed.

## 4. Seam B - background job execution

The worker's `runOnce()` is the single execution boundary (claim -> executor ->
complete/fail). A job emits **one** usage fact:

```text
category:  job
provider:  job.provider
operation: job.job_type
unit:      job
quantity:  1
sourceId:  job.id
metadata:  { retryCount, status: 'completed' | 'failed', durationMs? }
success:   terminal outcome
```

- Emitted only on a **terminal** outcome: a successful completion, or a failure
  with no retries left. A retryable failure that is requeued records nothing, so
  the job is one fact carrying `retryCount` - not one row per worker attempt.
- `sourceId = seo_sync_jobs.id` makes a re-execution idempotent; the ledger keeps
  a single fact for the logical job.
- `durationMs` is derived from `started_at`; `retryCount` is the durable job
  field. Worker/background executions keep `userId = null` when the job has no
  acting user.
- No new job telemetry table is introduced: `seo_sync_jobs` remains
  authoritative, and the event only projects its terminal outcome.

`DataForSEO` HTTP retries and the durable job retry are kept separate: HTTP
retries never produce usage events, and a requeued job produces none until it
terminates.

## 5. Non-goals

- no change to the usage vocabulary or the ledger schema (no migration);
- no instrumentation of `DataForSeoClient` transport, polls or retries;
- no GSC, publishing, media-search or embedding-external instrumentation (later
  R5.10.x slices);
- no HTTP route, UI or MCP surface;
- no billing, credits, quotas, pricing or stored cost.
