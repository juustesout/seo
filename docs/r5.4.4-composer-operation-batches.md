# R5.4.4 - Composer operation batches

Status: **delivered**. The Composer-level boundary between a generated
composition and the unified workspace document. R5.4.3.4 already mapped a
composition onto the existing operation vocabulary and executed it; this slice
makes that mapping a first-class Composer contract and hands the workspace a
single, explicit payload.

It is a **proposal boundary, not an apply**: the existing
`CompositionApplyBridge` still executes the batch against the one open document,
and the existing document/session/revision model is untouched. No R5.4.5 review
UX is introduced here.

## 1. Flow

```text
Composer
  |  brief -> /composition/plan -> /composition/compose
  v
Composition (CanonicalDocument + CompositionPlan)
  |
  v
composeOperationBatch(composition, plan)        (contracts, R5.4.4)
  |  delegates to mapCompositionToAppendOperations
  v
CompositionOperationBatch { version, composition, plan, operations, gaps }
  |
  v  workspace binds the open document's revision (pendingAppendCompositionFromBatch)
DesignerProposal { document, baseRevision, operations: DocumentOperationBatch }
  |
  v
existing CompositionApplyBridge
  |
  v
applyDocumentOperations -> unified document          (autosave persists it)
```

## 2. The operation-batch contract

`packages/contracts/src/compositionOperations.ts` adds:

```ts
COMPOSITION_OPERATION_BATCH_VERSION = 1

interface CompositionOperationBatch {
  version: typeof COMPOSITION_OPERATION_BATCH_VERSION;
  composition: CanonicalDocument;      // the generated, filled composition
  plan?: CompositionPlan;              // composition identity, when available
  operations: DocumentOperation[];     // existing operation vocabulary
  gaps: CompositionGap[];              // unsupported/unmatched structures
}

function composeOperationBatch(
  composition: CanonicalDocument,
  plan?: CompositionPlan,
): CompositionOperationBatch
```

Design choices:

- **Reuses, never duplicates.** The builder delegates to
  `mapCompositionToAppendOperations`; the batch carries `DocumentOperation` and
  `CompositionGap` verbatim. There is no second mapper and no parallel operation
  system.
- **No `baseRevision` in the batch.** The Composer is document-independent and
  owns no document identity, so it cannot honestly bind a revision. The batch is
  bound to the open document's revision by the workspace, at the one point where
  a Composer payload becomes a `DesignerProposal` the bridge executes.
- **`composition` and `plan` are provenance/identity** for the workspace and for
  the R5.4.5 review surface. They are not a second mutation instruction;
  `operations` remains the only thing the bridge applies.
- **Inert construction.** `composeOperationBatch` is pure: it reads the
  composition, produces a value, and mutates neither its inputs nor any document.

## 3. How Composer produces the batch

`Compose.tsx` builds the batch for the current run with a `useMemo` over the
filled `document` and `plan`:

```ts
const appendBatch = useMemo(
  () => (document ? composeOperationBatch(document, plan ?? undefined) : null),
  [document, plan],
);
```

The "Add to current document" affordance hands that batch to the workspace
(`onAppendToDocument(batch)`) instead of the raw composition. The batch is built
for the on-screen preview but is **not** handed off, persisted, or applied until
the user clicks the button (pinned by test). `ComposerMode` only forwards the
prop; it still owns no document identity and mounts no editor infrastructure.

## 4. How the batch connects to `CompositionApplyBridge`

`CompositionApplyBridge.tsx` adds one pure staging helper:

```ts
function pendingAppendCompositionFromBatch(
  batch: CompositionOperationBatch,
  baseDocument: CanonicalDocument,
  baseRevision: string,
  boundary: string,
): PendingComposition
```

It binds the open document's `baseRevision` and maps the batch onto the
already-existing `pendingAppendCompositionOf(baseDocument, batch.operations,
baseRevision, boundary, batch.gaps)`. The bridge's execution path is unchanged:
`proposal.operations` present -> `context.applyDocumentOperations(...)`. The
shell (`appendComposition`) now consumes a `CompositionOperationBatch` directly
and no longer performs the mapping itself.

## 5. Preserved / non-goals

- No new operation types, no parallel operation system, no bypass of the bridge.
- No second document id, revision model, history model, selection owner,
  autosave, or Composer-owned document state; the unified document stays the
  source of truth.
- No R5.4.5 review/apply UX: no review modal, approval/rejection, extra undo or
  rollback beyond existing document history, and no new Composer document state.
- No flattening of a composition back into plain text.
- The empty-document replacement path (R5.4.3.2) and the create-draft handoff
  (R5.4.2) are behaviorally unchanged; only the append handoff becomes
  batch-based.
- Server-side apply still refuses an `operations` proposal; the batch is
  editor-applied only.

## 6. Tests

- `packages/contracts/src/compositionOperations.test.ts` (new): the builder
  produces a versioned batch carrying composition, optional plan, operations and
  gaps; it deep-equals `mapCompositionToAppendOperations`
  (mapping semantics unchanged); unsupported elements stay explicit gaps;
  building is inert (no input mutation, no apply); an unrepresentable composition
  yields an empty versioned batch.
- `workspace/CompositionApplyBridge.test.tsx` (extended): a
  `CompositionOperationBatch` staged via `pendingAppendCompositionFromBatch`
  applies through `applyDocumentOperations`.
- `views/Compose.test.tsx` (extended): the append affordance hands the workspace
  a `CompositionOperationBatch` (version + composition + non-empty operations)
  without posting `/content`; building the batch for the preview applies nothing
  and is not handed off until clicked.
- `workspace/ProjectWorkspaceShell.composerApply.test.tsx` (updated): the
  Composer mock now hands ready batches; the append/partial/refused behaviours and
  the R5.4.2/R5.4.3.2 paths remain green.

  `operations`; R5.4.4 deliberately keeps the batch immutable once built.
