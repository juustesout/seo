# R5.4.5 - Composer review and apply

Status: **delivered**. The user-facing review boundary between a generated
`CompositionOperationBatch` and the unified workspace document. R5.4.4 gave the
workspace a single, explicit payload; this slice gives the user a chance to see
what that payload will do before anything is staged or applied.

It is a **review, not an editor**: the batch stays immutable and
document-independent, the only actions are Cancel and Apply, and Apply reuses the
existing R5.4.4 staging path and `CompositionApplyBridge`. No per-operation
editing, reordering, or deletion is introduced.

## 1. Flow

```text
Composer
  |  brief -> /composition/plan -> /composition/compose
  v
Composition (CanonicalDocument + CompositionPlan)
  |
  v
appendBatch = composeOperationBatch(composition, plan)     (R5.4.4, unchanged)
  |
  |  "Add to current document" -> setReview({ batch, isStale })   <- inert
  v
CompositionReviewDialog
  |  composition (existing CanonicalRenderer)
  |  operation summary       (derived from batch.operations)
  |  gaps                    (batch.gaps, only when present)
  |
  +-- Cancel -> clear review; document untouched
  |
  +-- Apply  -> onAppendToDocument(batch)                    (existing path)
                 |
                 v  workspace binds the open document's revision
               pendingAppendCompositionFromBatch
                 |
                 v
               existing CompositionApplyBridge
                 |
                 v
               applyDocumentOperations -> unified document   (autosave persists)
```

## 2. The review surface

`apps/web/src/views/CompositionReviewDialog.tsx` adds a single overlay dialog
(patterned on the existing `SourceDeleteDialog`: fixed overlay, `role="dialog"`,
`Button` variants). It receives the batch and two callbacks and owns no document
state:

- **Composition** - rendered with the existing `CanonicalRenderer`, the same
  renderer used by the Composer preview and the editor preview. There is no
  second renderer.
- **What will be added** - a plain-language summary derived from
  `batch.operations` by `summarizeCompositionOperations`, using the existing
  operation vocabulary (`Hero section`, `Section`, `Heading`, `Paragraph`,
  `Image`). Raw operation JSON is never shown, and no second operation
  representation is stored.
- **Not added** - shown only when `batch.gaps.length > 0`, listing each gap's
  deterministic message so unsupported structures are surfaced, never silently
  dropped. When `gaps` is empty the section is absent.
- **Provenance** - derived from the batch's `plan`/`composition` only
  (`Composer - <format> - <purpose>`); no new metadata is introduced.

Apply is disabled when `operations` is empty, so the user cannot stage a no-op.

## 3. Review state in `Compose`

`Compose.tsx` holds `review: { batch, isStale } | null`:

- **Opening is inert.** Clicking "Add to current document" captures the batch and
  the workspace boundary's stale check (`beginHandoff?.().isStale`). It does not
  call `onAppendToDocument`, does not touch the open document, and does not post
  `/content` (pinned by test).
- **Cancel** clears the review; the document is untouched.
- **Apply** discards the review and calls the existing
  `onAppendToDocument(batch)`. If the captured boundary is stale (the user
  switched documents while reviewing), the batch is discarded and a message is
  shown instead of applying to the wrong state.
- A new generation resets the review, alongside the existing draft/error state.

## 4. Revision binding stays where it was

The batch remains document-independent: **no `baseRevision` is added** to
`CompositionOperationBatch`. The workspace binds the open document's revision at
staging time in `appendComposition` (the same place as R5.4.4), and
`applyDocumentOperations` still performs its live double revision check. The
Compose-level stale guard is a minimal boundary check only; it does not introduce
a Composer revision model.

## 5. Preserved / non-goals

- No per-operation editing, drag/reorder, delete/edit of operations, parameter
  changes, partial selection, or operation-level undo.
- No second mutable batch, no second operation mapper, no second apply path: the
  bridge and `applyDocumentOperations` are unchanged.
- No new document id, revision model, autosave, selection owner,
  `EditorContext`, or Composer persistence; the unified document stays the source
  of truth.
- No R5.4.6 chrome redesign and no R5.4.7 Composer retirement.
- The empty-document replacement path (R5.4.3.2) and the create-draft handoff
  (R5.4.2) are behaviorally unchanged.

- `views/CompositionReviewDialog.test.tsx` (new, 8): the composition renders with
  `CanonicalRenderer`; the summary is derived from `batch.operations`;
  gaps render only when present; Apply/Cancel report back; Apply is disabled
  with no operations; `summarizeCompositionOperations` counts in document order.

  workspace and posts no `/content`; Apply hands the batch (no `baseRevision`)

  batch and surfaces an error.

  `workspace/ProjectWorkspaceShell.composerApply.test.tsx`: unchanged and still
  green (the apply path they pin is reused, not modified).
