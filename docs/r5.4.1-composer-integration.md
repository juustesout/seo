# R5.4.1 - Composer integration boundary

Status: **delivered**. First slice of R5.4 (`docs/phase-5-roadmap.md:120`), after
the R5.3 shell. It makes Composer a first-class workspace mode with an explicit
integration boundary, without redesigning the Composer surface or its engine.

## 1. Resulting shape

```text
ProjectWorkspaceShell
|- shared: one document session (identity, loader, lifecycle, autosave,
|          save barrier), document-scoped workspace state, WorkspaceChrome
|- shared: WorkspaceModeSwitcher
`- exactly one active mode
     |- editor   -> EditorMode   -> editor-only infrastructure
     |- composer -> ComposerMode -> Compose (existing Composer surface)
     `- designer -> Designer     (compatibility body, unchanged)
```

`workspace/ComposerMode.tsx` is the seam between the shared workspace/session and
the existing `Compose` surface. It is deliberately small: it reads the shared
context and renders `Compose`. It is not a mode framework and creates no second
workspace/session system.

## 2. Canonical identity

- Project and role come from the shared `WorkspaceSessionValue`
  (`useWorkspaceSessionContext`), not from Composer-local state or from props
  passed through the shell. `Compose` still accepts `projectId`/`role` for its
  legacy standalone use (account-level `compose` area, which is unchanged); when
  mounted inside the shell they are supplied by `ComposerMode` from context.
- The canonical active document identity stays in `useDocumentSession`
  (`session.identity`). Composer holds no document id of its own.
- The previous shell-local `composedDraftId` was removed. It was a second
  document-id variable used to shuttle a Composer-created draft into the editor.

## 3. Composer handoff (document creation)

`Compose`'s existing handoff is preserved: after `POST
/projects/:id/content` creates a draft from the composed `CanonicalDocument`, it
calls `onOpenEditor(id)`. Inside the shell that callback is now the canonical
switch:

```text
Compose "Open in Editor"
   -> shell openInEditor(contentId)
   -> session.requestDocumentSwitch(contentId)   (save barrier)
   -> onModeChange('editor')
```

So the new draft becomes the one canonical active document through the shared
boundary, exactly like opening a row from the editor list. The shell does not
invent a new boundary mechanism. The created row is still persisted through the
existing Content Studio `POST /content` path; Composer generation itself stays
preview-only.

## 4. Lifecycle ownership

| Responsibility | Owner after R5.4.1 |
| --- | --- |
| project identity, role | shell / `useWorkspaceSession` |
| canonical document identity | shell / `useDocumentSession` |
| document loading, lifecycle | shell / `useDocumentLoad` + `documentLifecycle` |
| save lifecycle, dirty, revision, autosave, save barrier | shell / `useAutosave` |
| document switching / creation / close | shell / session barrier |
| composition workflow (brief, format, phase, plan, preview, open/close) | `Compose` |
| draft creation from a composed document (`POST /content`) | `Compose` (existing domain handoff) |

Composer had no independent document identity, loader, dirty/save state, autosave
or save barrier to begin with; the one real duplication (`composedDraftId`) was
removed. No second autosave/save/revision mechanism is introduced.

## 5. Composer-local state (intentionally retained)

Classified as composition workflow state, not workspace/document state, and left
owned by `Compose`: `brief`, `format`, `phase`, `error`, `plan`, `document`,
`tab`, `creating`, `createError`. These are legitimate Composer-local state and
are not moved into any workspace store.

The current Composer surface is document-independent: a generation run is a
preview, not an edit of the shared document. It therefore consumes the canonical
project identity, and the canonical document identity only at the handoff. This
is documented as intended, not as a hidden discrepancy.

## 6. Editor isolation

`ComposerMode` renders `Compose` only. It mounts no Tiptap instance, no
`EditorContextProvider`, no `EditorSelectionProvider`, no editor keymap and no
editor AI state; `EditorMode` is not mounted in composer mode. The R5.3.3
guarantee is preserved and covered by regression tests.

## 7. Shared chrome

The shell remains the owner of workspace-level chrome. The always-on shared
`WorkspaceModeSwitcher` is rendered above every mode. The document-scoped
`WorkspaceChrome` (`DocumentHeader`, save indicator, save-failure banner) is only
meaningful while a shared document is open and editable in the editor, so it does
not render in composer mode; Composer keeps its own internal `PageHeader` rather
than expanding shared chrome prematurely. Converging Composer onto the shared
document header is a later R5.4 concern, not part of this boundary slice.

## 8. Route behavior

Unchanged canonical route `/p/:projectId/workspace/composer/:contentId`. No new
Composer route, no route-parser change, and the legacy account-level `compose`
area still renders `Compose` directly with its own `onOpenEditor`.

## 9. Tests

- `workspace/ComposerMode.test.tsx` (new): renders the existing Composer surface
  and no editor infrastructure; consumes the canonical project identity from the
  shared session (API called with the context's project id); a change to the
  canonical active document does not reset or re-key the Composer workflow and
  does not fetch the newly active document through the Composer.
- `workspace/ProjectWorkspaceShell.test.tsx`: the Composer draft handoff now
  opens through the shared session - the created id becomes
  `session.identity.documentId`, not a shell-local id.
- `workspace/ProjectWorkspaceShell.isolation.test.tsx`: editor/designer modes do
  not render the Composer surface; composer mounts no editor infrastructure.
- `views/Compose.test.tsx`: unchanged and green - the existing Composer domain
  behavior and handoff are preserved.
