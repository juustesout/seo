# R5.2.6 - Canonical document loading/error lifecycle

Status: **implemented, awaiting review** (not committed as part of the R5.2
batch).

This slice closes the R5.2 gap "One document lifecycle" from
`docs/phase-5-roadmap.md`. It consolidates the active document's
loading/ready/error state into the existing `DocumentSession` ownership model.
It does not add a global error store, a second epoch, or a new state manager.

## 1. The lifecycle

The active document has exactly four states, defined once in
`session/useDocumentSession.ts`:

```text
idle     no document is active (the content list is shown)
loading  a document is active but not yet loaded/aligned
ready    the active document is loaded and safe to act on
error    the active document failed to load
```

`documentLifecycle(identity, load)` is the one pure projection that decides the
state. It takes the canonical session identity plus the raw, identity-stamped
loader state and returns `{ status, documentId, error }`. Nothing else decides
readiness.

## 2. The loader

`session/useDocumentLoad.ts` replaces the ad-hoc `useAsync` detail fetch. It is
an **identity-keyed** loader: it is asked for an id and only ever reports a
result for that id.

- Changing the requested id immediately reports `loading` and clears the
  previous payload/error, so a render between the identity change and the new
  response can never read the previous document's data.
- A response that arrives after the id changed is dropped by a per-run `alive`
  guard, so a stale load cannot surface under the active document.
- `reload()` re-runs the active load (used by the load-error screen's Retry).

It is a loader, not a lifecycle: it carries no readiness rule. That rule stays
in `documentLifecycle`.

## 3. Why a stale load cannot win

The lifecycle trusts the loader only when the loader's stamped id matches the
active identity:

```ts
if (load.documentId !== identity.documentId) return loading;
```

So both failure modes are covered without a second epoch:

- a late response for the previous document is dropped by the loader's `alive`
  guard, and even if it were not, its stamped id would not match the active
  identity;
- a load error is surfaced only for the active identity - a stale error for the
  previous document is reported as `loading`, never as the active document's
  error.

A brand-new document is `ready` without a fetch (its content is seeded empty).

## 4. Render boundaries

`Content.tsx` renders from the lifecycle only; `workspaceReady`, the separate
`loadedRef` "already seeded" flag and the ad-hoc `detail.data?.id === editingId`
guard are gone.

```text
idle     -> content list
loading  -> loading screen (workspace not mounted)
error    -> load-error screen with Retry / Back to list (workspace not mounted)
ready    -> read-only viewer (viewers) or EditorWorkspace (editors)
```

Because the workspace is not mounted unless the active document is `ready`, a
new identity is never paired with the previous document's editor. On a switch
that succeeds at the barrier but fails to load, the stale editor is gone, not
merely hidden.

`DocumentSessionValue` now exposes `lifecycle: DocumentLifecycle` in place of the
`ready` boolean. `EditorWorkspace` derives the editor context's boolean
`ready` from it at the boundary; no consumer keeps its own copy.

## 5. Errors stay distinct

The lifecycle is driven solely by the session identity and the document loader:

- an **AI/action error** lives in the view's own state and never changes the
  lifecycle;
- a **save failure** is `AutosaveStatus` (`saveState`), which is surfaced
  separately from the lifecycle.

A failed save therefore does not look like a failed load, and a failed load does
not look like an AI failure.

## 6. What this slice did not touch

No generic `SessionError`, no global error store. AI/toolbar/notice/publishing/
Composer/Designer errors were not moved into the session. Autosave, revision,
selection, undo/redo, persistence, beforeunload, routes, mode switching,
embedding, notifications and doc-scoped rail/assistant/preview are unchanged.

## Tests

`session/documentLifecycle.test.tsx` (12) has two parts.

Contract tests on the pure `documentLifecycle`:

1. idle with no active document;
2. a brand-new document is ready without a load;
3. stays loading until the loader describes the active identity;
4. ready exactly when the loader matches the active identity;
5. a stale error for the previous document is not surfaced.

Harness tests compose the real `useDocumentSession`, the real
`useDocumentLoad` and a real keyed `RichTextEditor` mounted only when ready
(mirroring `Content.tsx`):

6. a successful switch makes B active and is `loading` before ready;
7. B reaches `ready` once its load resolves;
8. a B load failure yields lifecycle `error` and never shows the stale A editor;
9. a failed switch preserves A and never starts the B load;
10. a stale response for the previous document cannot alter B;
11. AI errors remain outside the lifecycle;
12. save failures stay distinct from document load failures.
