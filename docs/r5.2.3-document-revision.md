# R5.2.3 - Canonical document revision/dirty and the live-document seam

Status: **implemented, awaiting review** (not committed).

This slice closes two R5.2 gaps identified in
`docs/r5.1-workspace-architecture-recon.md`: conflict 2 (EditorContext reads a
lagging `doc` prop) and sequence item 5 (one revision/dirty model). It does not
touch selection, routes, mode switching, the save barrier or the write paths.

## The live document source

The live source of truth is the Tiptap `Editor` instance (`editor.getJSON()`).
The `doc` prop is only a render trigger plus a fallback for the moment before an
editor exists; it lands one render behind the editor.

`EditorContextProvider` now resolves the current document through one helper,
`liveDocumentOf(editor, doc)`, for:

- the snapshot (`document.canonical` and `document.revision`);
- the `applyExternalDocument` / `applyImageInsertion` /
  `applyDocumentOperations` revision guards;
- the base document the operation batch is applied to.

Before this change the guards and the base used the `doc` prop
(`EditorContext.tsx:129/153/163/168`), so an apply that arrived in the same tick
as an edit could read a stale revision or, worse, apply a batch to the wrong
base. The guards now read the editor at call time; no mirrored document state is
introduced.

## The one revision/dirty contract

`apps/web/src/components/content/documentRevision.ts` is the single contract.
There are two revisions because there are two genuinely different questions, and
both are built from the same stable hash (`contentRevisionOf`) so they cannot
become two incompatible systems:

- `documentRevisionOf(doc)` - revision of the document content alone. This is
  the concurrency token: the server derives the same token from the persisted
  `content_json`, and the editor apply guards compare against it. EditorContext
  reports it.
- `workspaceRevisionOf(state)` - revision of the whole persisted unit: the
  document revision plus the editable metadata (title, status, target keyword,
  meta title/description). Autosave compares it against its baseline.
- `workspaceSnapshotOf(state)` - the canonical JSON payload that is actually
  persisted. It stays a string (not a hash) because the server parses the same
  keys back out.

`workspaceRevisionOf` embeds `documentRevisionOf`, so a document change always
changes the workspace revision; a metadata-only change changes only the
workspace revision. That is the documented distinction, not an accident: a
metadata edit must dirty the workspace (autosave persists metadata too), while
the document concurrency token must stay document-only to match the server.

## Dirty definition

Dirty means: the canonical workspace revision differs from the persisted
baseline. `useAutosave` now takes an optional `makeRevision`, used for the
dirty check and the save decision, separate from `makeSnapshot` (the payload).
When omitted it defaults to `makeSnapshot`, so callers whose payload is already
canonical are unaffected. `Content.tsx` passes `makeRevision:
workspaceRevisionOf`, `makeSnapshot: workspaceSnapshotOf` and uses the workspace
revision as the debounce key; the seed effects set the baseline to the workspace
revision. This replaces the old equality on the raw snapshot string with the
same canonical revision the rest of the editor uses.

The EditorContext `document.dirty` flag remains the autosave (workspace) dirty
passed through from the session: it answers "does the persisted unit differ",
not "did the document bytes change".

## Why no second document model

The provider reads the existing editor boundary instead of owning a copy of the
document. The snapshot is built from the live JSON at render time; guards read
it at call time. There is no additional React document state to keep in sync.

## Tests

- `components/content/documentRevision.test.ts` (7): document revision equals the
  contracts revision; workspace revision stability, document-change and
  metadata-only-change behaviour; the embedding guarantee; the persisted payload
  shape and key order.
- `components/content/editor/EditorContext.test.tsx` (+4): the snapshot reports
  the live editor revision while the prop lags; an apply whose revision matches
  the live editor succeeds; the lagging prop revision is rejected as stale; a
  batch is built on the live editor content (existing text preserved), not the
  prop.
- `components/content/useAutosave.test.ts` (+2): dirty and save gate on the
  canonical revision while persisting the payload; flush applies the same gate.
- Two `EmbeddedAgentEntry.test.tsx` tests that asserted a rejection after only
  swapping the `doc` prop were updated. They encoded the old bug: the live
  editor had not changed, so the correct outcome is to apply. They now move the
  live document on (an editor edit) before asserting `document changed`.
