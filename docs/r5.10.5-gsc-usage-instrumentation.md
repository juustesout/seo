# R5.10.5 - GSC usage instrumentation

Delivered behavior for recording Google Search Console API consumption in the
R5.10.2 append-only usage ledger. The repository analysis this builds on is
`docs/r5.10.5-gsc-usage-recon.md`; this document records the delivered design and
decisions, not the call-graph discovery.

Contract: `packages/contracts/src/usageEvent.ts` (R5.10.1). Ledger:
`supabase/migrations/20260101000031_usage_events.sql` (R5.10.2). No migration,
vocabulary change or ledger schema change is required or made.

## 1. Instrumentation seam

`GscApiClient.request<T>()` (`apps/api/src/providers/gsc/gscApi.ts`) is the sole
GSC usage seam. It is the only place a real Search Console HTTP request is made
and it is GSC-specific (`searchconsole.googleapis.com/webmasters/v3`), so one
invocation equals exactly one real request.

```text
GscDataSource
    -> apiWithRefresh
        -> GscApiClient.request()   <- the one usage seam
            -> fetch(searchconsole.googleapis.com/webmasters/v3)
                -> usageEvents.append()   (best-effort)
```

- `request(operation, path, init)` reports the outcome once, after the HTTP
  response is known (`success = res.ok`). `listSites()` passes
  `operation: 'list_sites'`; `searchAnalytics()` passes
  `operation: 'search_analytics'`.
- Reporting goes through a small `GscRequestObserver` callback. The adapter binds
  project/user/usage into it (`GscDataSource.usageObserver`), so the client stays
  free of credentials and business scope and only reports `(operation, success)`.
- The adapter passes the observer when it constructs the client in
  `apiWithRefresh`. `GscDataSource` methods (`fetchDaily`, `fetchDimension`,
  `listProperties`, `testConnection`, `connect`) are **not** instrumented
  individually - they inherit the request seam.

## 2. Why `GscApiClient.request()`

The R5.10.4 rule ("do not instrument low-level transport; count logical
consumption at the adapter boundary") exists because `DataForSeoClient.request()`
mixes auth, retries, rate limiting and `tasks_ready` polling, so counting it
would fabricate requests. The GSC client is the opposite: intentionally dumb and
stateless, one call = one fetch, no internal retry, no polling, no caching. It is
therefore a genuine 1:1 request boundary and the correct seam, exactly as the
recon determined.

This choice also makes the request count correct for free: a 28-day sync makes
`1 (fetchDaily) + 4 (query chunks) + 4 (page chunks) = 9` requests and therefore
nine `gsc_request` facts - never one collapsed "sync" event. See
`buildGscRequestUsageEvent` in
`apps/api/src/providers/gsc/providerUsage.ts`.

## 3. Actual request counting

| Application operation | Operation token | Requests | Usage |
| --- | --- | ---: | --- |
| `listSites` (via `connect` / `testConnection` / `listProperties`) | `list_sites` | 1 | 1 x `gsc_request` |
| `fetchDaily` (via `searchAnalytics`) | `search_analytics` | 1 | 1 x `gsc_request` |
| `fetchDimension` (via `searchAnalytics`), per 7-day chunk | `search_analytics` | `ceil(days/7)` | 1 per chunk |
| `disconnect` | - | 0 | none |

Event shape:

```ts
{
  category: 'google',
  provider: 'gsc',
  operation: 'list_sites' | 'search_analytics',
  unit: 'gsc_request',
  quantity: 1,
  success: boolean,
  accountId: null,          // mirrored from project by the ledger trigger
  projectId,
  userId,
  sourceId,                 // job id for job-originated requests, else null
  idempotencyKey            // v1|...|sourceId|<occurrence>
}
```

## 4. 401 refresh/retry semantics

`apiWithRefresh` behavior is unchanged. A `401`/`403` makes `request()` report a
failed request, then the adapter refreshes the token and retries. Both attempts
reach Google, so both are reported:

```text
request #1 -> report success=false (401)
token refresh -> oauth2.googleapis.com (NOT reported)
request #2 -> report success=true
```

A 401-refresh-retry therefore produces **two** `gsc_request` facts, not one. This
is the physical-request semantics the recon chose over a logical-operation seam,
which would under-count the legitimate retry. Nested retries do not multiply
facts because the client has no retry of its own and only the request seam
reports.

## 5. OAuth exclusion

`oauth.ts` (`exchangeCode`, `refreshAccessToken`) posts to
`oauth2.googleapis.com/token`, a different host. It is never routed through
`GscApiClient` and is never instrumented. The token endpoint produces zero GSC
usage even when it runs as part of a refresh.

## 6. Failure semantics

- **Before `fetch`** (missing integration/tokens, missing `siteUrl`, local
  validation/authorization): no client call, no event.
- **`fetch` resolves non-2xx** (including 401/403): one event with
  `success: false`; the original `UnauthorizedError`/`Error` propagates
  unchanged.
- **`fetch` rejects** (network/abort): the call was attempted, so one event with
  `success: false`; the original error propagates.
- **`fetch` resolves 2xx**: one event with `success: true`, recorded before the
  body is parsed, so a later JSON parse error still reflects a successful HTTP
  exchange.
- **Account-scoped calls** (`projectId` not a UUID, e.g. `/account/gsc/discover`)
  build no fact, so nothing is appended (section 9).

## 7. Best-effort append

`emitGscRequestUsage` reuses the shared `appendUsage` seam from
`services/usageInstrumentation.ts`: a missing sink or a failed append is logged
and swallowed. `GscApiClient.record` additionally wraps the observer in its own
try/catch, so even a misbehaving observer cannot fail a GSC call. Usage
persistence is never the GSC transaction boundary: a successful request still
returns its result, and a failed request still throws its original provider
error.

## 8. Scope propagation

Scope comes from the existing R5.10.4 `ProviderContext.usage` plus
`ProviderContext.projectId` / `userId` - no new scope system:

- Job: `buildProviderContext` in `executors.ts` supplies the real `projectId`,
  `userId = job.created_by` (may be null) and `usage.sourceId = job.id`.
- Project routes: real `projectId`, real `userId`.
- `accountId` is intentionally `null` on the event; the ledger's
  `seo_usage_events_set_account` trigger mirrors it from `project_id`, so callers
  never need to know about accounts.

## 9. Job correlation

The recon found one wiring gap, now closed: the `gsc_sync` executor passes
`usageSourceId: job.id` to `buildProviderContext` (`executors.ts`), matching the
DataForSEO pattern.

```text
job.id -> ProviderContext.usage.sourceId -> GscApiClient.request() -> event.sourceId = job.id
```

Multiple requests within one job stay distinct through the existing occurrence
mechanism: each real request calls `usage.nextOccurrence(operation)`, yielding a
stable 0-based sequence per operation per execution. A default sync produces nine
events with occurrences `0..8` and distinct idempotency keys.

## 10. Idempotency / occurrence

The R5.10.2 ledger mechanism is reused verbatim; there is no application-level
dedup. `idempotencyKey` is derived by `usageEventIdempotencyKey`:

```text
v1|google|gsc|<operation>|gsc_request|<sourceId>|<occurrence>
```

- Job requests: `sourceId = job.id`, so a worker re-execution derives the same key
  sequence and dedupes against rows already written.
- Non-job requests (discover / properties / test): no stable attempt identity, so
  `sourceId = null`, the key is null, and the event is honestly
  non-deduplicatable, matching the existing nullable-`sourceId` semantics.
- No timestamps, random ids or response hashes are used as identities.

## 11. Account-scoped discovery limitation

`/account/gsc/discover` uses an account-level integration whose `project_id` is
`NULL`; its context therefore carries `projectId = ''`. This slice does not
redesign account-level GSC integration and does not invent a project id, so
`buildGscRequestUsageEvent` refuses the malformed scope and **no** usage event is
emitted for that path. The request still executes normally - only metering is
absent. Account-scoped coverage is a documented follow-up (the ledger already
supports account-only scope; the provider context would need to carry
`accountId`), deliberately out of scope here.

## 12. Test coverage

- `apps/api/src/providers/gsc/providerUsage.test.ts` - fact shape, non-project
  guard, invalid operation guard, occurrence-key uniqueness, nullable-sourceId
  behavior, best-effort append (including a throwing sink).
- `apps/api/src/providers/gsc/gscApi.test.ts` - one report per request for
  `listSites`/`searchAnalytics`, success/failure classification, error
  preservation on 401/500/network rejection, observer failure cannot fail the
  request, works without an observer.
- `apps/api/src/providers/gsc/gscDataSource.test.ts` - `fetchDaily` = 1 fact,
  `fetchDimension` = one fact per weekly chunk, `listProperties` = 1 fact,
  missing-tokens pre-fetch failure = 0 facts, account-scoped `projectId=''` = 0
  facts, 401-refresh-retry = 2 facts with the token call excluded.
- `apps/api/src/jobs/executors.gsc.usage.test.ts` - `gsc_sync` emits nine
  `gsc_request` facts with `sourceId = job.id` and `userId` from the job, and a
  re-execution deduplicates via the ledger key.

## 13. Explicit non-goals

Billing, pricing, cost calculation, quotas, credits, usage dashboard/UI,
DataForSEO/AI/publishing/media-search/external-embedding instrumentation, OAuth
or generic Google telemetry, new retry or caching infrastructure, account/project
integration redesign, usage vocabulary changes, usage ledger schema changes.
