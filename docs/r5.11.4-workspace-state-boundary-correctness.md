# R5.11.4 - Workspace-State Boundary Correctness (H5+H6)

Slice H5+H6 of the R5.11 hardening plan (`docs/r5.11-hardening-recon.md`,
sections B/E.4). Both are defensive ownership fixes around the
document-scoped workspace UI state; neither closed a reachable wrong-document
write, but each removed a seam where state sat outside the boundary it belongs
to.

## H5 - staged composition handoff owned outside the boundary

`ProjectWorkspaceShell` staged a Composer/Designer handoff in a plain
`useState<PendingComposition | null>` (`ProjectWorkspaceShell.tsx:166`). The
value carried the `session.boundary` it was built for, and the
`CompositionApplyBridge` rejected a mismatch with `stale-document`, so no
wrong-document write was possible - but the staged value lived at the shell
owner outside the boundary and only got discarded at apply time.

Fix: the staging slot is now
`useDocumentScopedState<PendingComposition | null>(null)`
(`ProjectWorkspaceShell.tsx:169`). The enclosing `WorkspaceStateProvider` is
already keyed by `ws.session.boundary` (`:100`), so the staged handoff is now
scoped to the exact document boundary: when the boundary moves the owner reads
`null` and the stale handoff is gone before any bridge can see it. The
composer -> editor mode switch does not change the boundary, so the staged
value still survives that switch and is consumed by the bridge exactly as
before. No apply/consume logic changed.

Reachability note: within the shell's own UI the open document cannot change
while a staged handoff is pending (only the Composer's `onOpenEditor` opens
documents, and once the editor mode mounts the bridge consumes the staged
value), so H5 is ownership hygiene rather than a user-visible defect. The fix
nonetheless makes the boundary the single owner of the staged value.

## H6 - replayed setter could discard the current scope's value

`useDocumentScopedState` scoped the stored entry by the scope captured in the
setter closure. A setter captured under boundary A and invoked after the
boundary moved to B wrote `{ scope: 'A', value }`, overwriting B's entry; reads
then fell back to `initial`, silently discarding whatever B had stored. The
existing tests only replayed a stale setter when B held no value, so the loss
was not observable.

Fix: the hook keeps a `scopeRef` holding the live scope (`workspaceState.tsx`)
and the setter refuses to run when its captured scope no longer matches
(`if (scopeRef.current !== scope) return;`). A replayed setter from a previous
scope is now a no-op, so it cannot clobber the current scope's value. The normal
path is unaffected - a setter from the current render has `scope ===
scopeRef.current` and writes as before.

## Tests

- `apps/web/src/components/content/workspace/workspaceState.test.tsx` (+1):
  "cannot let a replayed setter from a previous document discard the current
  value". B stores a value, then A's captured setter is replayed; B's value must
  survive. Verified to fail without the guard (the entry was replaced by A's
  stale scope and reads returned `initial`).
- H5 reuses the already-covered `useDocumentScopedState` reset contract
  ("resets document-scoped state on a successful switch"), which pins that a
  value written under one boundary is unreadable after the boundary moves - the
  exact guarantee `pendingComposition` now relies on. Existing Composer/Designer
  handoff suites (`ProjectWorkspaceShell.composerApply.test.tsx`,
  `ProjectWorkspaceShell.handoff.test.tsx`, `CompositionApplyBridge.test.tsx`)
  still pass unchanged.
