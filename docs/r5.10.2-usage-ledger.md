# R5.10.2 - Append-Only Usage Ledger

R5.10.1 defined the usage-event vocabulary as pure types. R5.10.2 gives it a
home: the `seo_usage_events` table, the append-only persistence seam, the RLS
boundary and a fixed aggregation RPC. It adds no provider instrumentation, no
HTTP route, no UI, no MCP surface, and no billing/pricing/credit/quota logic.

The invariant this slice protects:

```text
Usage events can be appended, queried and aggregated.
They cannot be updated or deleted through the application domain.
```

## 2. Schema

`seo_usage_events` maps 1:1 onto the R5.10.1 `UsageEvent` contract:

```sql
id              uuid primary key default gen_random_uuid()
occurred_at     timestamptz not null default now()
account_id      uuid references public.seo_accounts (id) on delete set null
project_id      uuid references public.seo_projects (id) on delete set null
user_id         uuid references auth.users (id) on delete set null
category        text not null
provider        text not null
operation       text not null
quantity        bigint not null default 0
unit            text not null
success         boolean not null
source_id       text
metadata        jsonb not null default '{}'::jsonb
idempotency_key text
created_at      timestamptz not null default now()
```

Deliberate choices:

- **No `updated_at` and no touch trigger.** The row is written once; the absence
  of the column is part of the append-only invariant, not an oversight.
- **`occurred_at` and `created_at` are distinct.** The first is the fact's time;
  the second is the ledger row's time.
- **`quantity` is `bigint`.** Every unit is a non-negative integer count and
  `bigint` maps cleanly to `number` over PostgREST (unlike `numeric`, which is
  returned as a string). The contract guard was tightened to `Number.isInteger`,
  so contract and column agree.
- **Closed vocabulary in the DB too.** `category` and `unit` CHECKs mirror the
  contract enums; `provider`/`operation` are validated as bounded lowercase
  tokens (`^[a-z0-9_]{1,64}$`). `source_id` is bounded to 1..200 chars and
  `idempotency_key` to 1..512 chars (sized to hold the longest derived key from a
  max-length `source_id`); `metadata` must be a JSON object.
- **`on delete set null` on all three scope FKs (not cascade).** Deleting a
  project, account or user must not erase historical usage evidence. The event
  keeps its fact and only loses its live tenancy link.

Indexes: `(project_id, occurred_at desc)`, `(account_id, occurred_at desc)`,
`(category, occurred_at desc)` and a partial `(source_id)` index for trace-back.

## 3. Account mirroring

When a project-scoped event omits `account_id`, a `before insert ... when
(new.account_id is null)` `security definer` trigger copies it from
`seo_projects.account_id` - the same pattern as `seo_writer_runs` and
`seo_agent_runs`. Project membership stays the primary authorization boundary;
the account is derived, never guessed. Account-scoped events (`project_id is
null`) and worker events (`user_id is null`) remain fully representable.

## 4. Idempotency

A usage event is deduplicatable only when it is tied to a stable external
attempt identity. `sourceId` (job id, publication id, media id, DataForSEO task
id, AI call id, ...) is that handle.

The deterministic key is a pure function of the fact:

```text
usageEventIdempotencyKey(category, provider, operation, unit, sourceId, occurrence?)
  = "v1|<category>|<provider>|<operation>|<unit>|<sourceId>|<occurrence ?? 0>"
  = null when sourceId is null
```

`occurrence` (default `0`) exists only for the rare case of several facts of the
same kind within one external attempt; prefer one event with a summed `quantity`.
The `v1` prefix leaves room to change the scheme additively.

Scope is enforced by the database, not by string composition. Because
`project_id` and `account_id` are independently nullable, there are two partial
unique indexes:

```sql
unique (project_id, idempotency_key)
  where idempotency_key is not null and project_id is not null
unique (account_id, idempotency_key)
  where idempotency_key is not null and project_id is null and account_id is not null
```

NULL keys are never deduplicated. Callers may pass an explicit `idempotencyKey`
override when a stable identity exists outside `sourceId`; such a key must be
namespaced by the caller. `append` treats a unique violation (23505) as "already
recorded" and counts it as a duplicate rather than erroring - the DB index is
the real guard. Retries that genuinely re-call a provider carry a new attempt
identity and correctly become new events.

## 5. Persistence seam (append-only by type)

`UsageEventStore` exposes exactly three operations:

```ts
export interface UsageEventStore {
  append(events: readonly NewUsageEvent[]): Promise<{ inserted: number; duplicates: number }>;
  list(filter: UsageEventFilter): Promise<UsageEvent[]>;
  aggregate(request: UsageAggregateRequest): Promise<UsageAggregate[]>;
}
```

There is no `update`, no `delete` and no generic CRUD - the type itself protects
the invariant. Two implementations share the contract: a Supabase service-role
store and an in-memory double with the same idempotency, scope and fail-closed
semantics. Rows are mapped fail-closed through `isValidUsageEvent`, so a corrupt
row throws `usage_event_state_invalid` instead of being reinterpreted.

`list` requires a project or account scope and filters on
category/provider/operation/unit/success/sourceId/`occurredFrom`/`occurredTo`
with a bounded limit (default 200, max 500). It never returns delete/update
capability.

## 6. RLS and aggregation

RLS is SELECT-only for browser/PostgREST traffic:

```sql
create policy seo_usage_events_select on public.seo_usage_events
  for select using (
    (project_id is not null and public.seo_is_member(project_id, auth.uid()))
    or (project_id is null and account_id is not null
        and account_id = public.seo_account_id_for_user(auth.uid()))
    or (project_id is null and account_id is null and user_id = auth.uid())
  );
-- Intentionally no insert / update / delete policies.
```

There is no write policy, so even a client that somehow had table privileges
could not mutate a historical event. Writes belong exclusively to the API/worker
service-role client.

Aggregation happens in SQL, never by pulling the ledger into the API.
`seo_usage_totals(...)` is a `security definer` RPC with a **fixed** shape - no
dynamic SQL and no `p_group_by` parameter. The only dimensions are
category/provider/operation/unit; the caller may regroup further.

```text
seo_usage_totals(p_user, p_project, p_account, p_from, p_to,
                 p_category, p_provider, p_operation, p_unit, p_success)
  -> (category, provider, operation, unit, quantity bigint, event_count bigint)
```

It requires a project or account scope, checks `seo_is_member` / account
ownership before aggregating, and `revoke execute ... from public` +
`grant execute ... to service_role`, so only the server (which passes the
already-verified actor as `p_user`, mirroring `seo_ensure_account`) may call it.

## 7. Non-goals

- no provider instrumentation or event emission (no executor/provider changes);
- no HTTP route, no UI, no MCP surface;
- no billing, credits, quotas, pricing or stored cost - cost is a future
  derivation (`usage event -> pricing rule -> calculated cost`), so historical
  usage stays truthful when provider prices change;
- no retention/partitioning/archival policy;
- no changes to R5.6-R5.9 behavior.
