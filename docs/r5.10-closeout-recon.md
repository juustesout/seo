# R5.10 Closeout Recon

Recon-only. No code, schema, migration, vocabulary or test change. This document
decides whether the R5.10 usage-metering foundation is genuinely complete against
its own architecture, and names the concrete remaining work if it is not.

Sources inspected: `packages/contracts/src/usageEvent.ts`,
`apps/api/src/services/usageInstrumentation.ts`,
`apps/api/src/services/usageEventRepository.ts`,
`apps/api/src/providers/{dataforseo,gsc,publishing,media,knowledge}/*`,
`apps/api/src/services/{aiService,embeddingService,imageInsertionService}.ts`,
`apps/api/src/jobs/executors.ts`, `apps/api/src/worker.ts`,
`apps/api/src/context.ts`, `apps/api/src/app.ts`,
`supabase/migrations/20260101000031_usage_events.sql`,
`docs/phase-5-roadmap.md` and the R5.10.1-R5.10.7 documents/recons.

## A. End-to-end flow

```text
external provider call
  -> provider/service seam (observer or wrapper)
       -> fact builder (build*UsageEvent / *Events)
            -> appendUsage() best-effort
                 -> UsageEventStore.append() (SupabaseUsageEventStore | InMemory)
                      -> seo_usage_events  (append-only; UNIQUE idempotency)
                           -> UsageEventStore.list()      (scope required)
                           -> UsageEventStore.aggregate() -> seo_usage_totals() RPC
                                -> ??? no HTTP route, no UI, no MCP tool
```

Every external-consumption boundary is instrumented through a best-effort seam
that records only after a real attempt and never becomes a transaction boundary
(`appendUsage` logs and swallows, `usageInstrumentation.ts:94`). Idempotency is
derived in the DB path (`usageEventIdempotencyKey`, null when `sourceId` is null)
and the ledger treats a `23505` as a duplicate.

The chain is complete **up to and including aggregation**, and then stops. There
is no consumer of `list`/`aggregate`/`seo_usage_totals`:

- `rg "usageEvents" apps/api/src` finds only writes (`context.ts:162` wiring,
  `worker.ts:164`, `aiService.ts:187`, `imageInsertionService.ts:295`,
  `knowledgeService.ts:1477`, `opportunityTopicService.ts:308`,
  `executors.ts:610,634,673,691,928`). No read.
- `apps/api/src/http/routes/*` contains zero `usage` references and
  `app.ts:117-171` mounts no usage router.
- `apps/web/src` has no usage view (`MediaPanel.tsx:195` `m_usage_count` is
  media reuse, unrelated).

So the product cannot answer R5.10's own stated first question ("What did this
account or project actually consume?"). That is the central closeout finding.

## C. Concrete gaps

### C1. No read/reporting surface (primary; the R5.10 architecture is incomplete)

- **Where:** `services/usageEventRepository.ts` (`list` at `:264`, `aggregate`
  at `:286`), migration `20260101000031_usage_events.sql` (`seo_usage_totals`
  at `:150`, granted to `service_role` at `:210`), `context.ts:66,162`
  (`usageEvents` store), `app.ts:117-171` (no usage mount), `apps/web/src`
  (no view).
- **Current behavior:** facts are written and aggregable in SQL, but no HTTP
  route, UI or MCP tool reads them. `list` requires a project/account scope and
  `aggregate` requires an `actorUserId`; both authorization paths are already
  designed but unused.
- **Why it matters:** this is the value R5.10 was created for. The vocabulary
  doc (`r5.10.1...md:11`) and the roadmap
  (`phase-5-roadmap.md:274`, "First answer: What did this account or project
  actually consume?", suggested phase "R5.10.5 Add basic account/project usage
  view") both require it. Every slice's non-goals deferred it, so no slice
  delivered it - the classic cross-slice gap. Without it, the ledger is
  write-only and cannot be verified by a user.
- **Smallest boundary:** one project-scoped read route
  (`GET /api/projects/:projectId/usage`, `requireRole` then
  `list`/`aggregate`; optional `category/provider/operation/unit/success/
  occurredFrom/occurredTo` filters), the account-scoped counterpart behind
  `seo_account_id_for_user`, and a minimal web view rendering the fixed
  (category, provider, operation, unit, quantity, eventCount) aggregate. No
  schema, RPC, vocabulary or ledger change - the read layer already exists.

### C2. Interactive usage loses the acting user (`userId: null`)

- **Where:** `aiService.ts:184-189` (fixed `userId: null` at the resolution
  gate), `imageInsertionService.ts:295-296` (`usageScopeContext` with no user),
  `knowledgeService.ts:1477` and `opportunityTopicService.ts:308` (read-path
  scope, `userId: null`).
- **Current behavior:** job-originated usage carries `job.created_by`, but
  user-initiated AI/media/embedding usage is attributed to the project with no
  user even when an authenticated user triggered it.
- **Why it matters:** the roadmap asks for "user where relevant", and the
  vocabulary explicitly supports `userId`. Per-user consumption is currently
  unrecoverable for the interactive paths, and the ledger RLS exposes a
  `user_id = auth.uid()` branch that no interactive producer ever feeds.
- **Smallest boundary:** thread the acting `userId` (already available at the
  route edge via `requireRole`) through `AIService.resolve`/`resolveImageGeneration`,
  `ImageInsertionService`, and the knowledge/opportunity read scopes. No new
  vocabulary; the column already exists.

### C3. Two embedding meters with inconsistent granularity; one is dead

- **Where:** `usageInstrumentation.ts:152` (`embeddingEvents`, logical summed,
  batch 16) + `aiService.ts:238` versus
  `providers/knowledge/embeddingUsage.ts` + `providers/knowledge/embedding.ts:63`
  (physical per-request, batch 8); `services/embeddingService.ts`
  (`EmbeddingService.embedderFor`, only self-referenced, no production caller).
- **Current behavior:** the live embedding path is `OpenAiCompatibleEmbedder`
  (physical facts). The instrumented `AIProvider.embed` wrapper path is
  unreachable because `EmbeddingService`/`ProjectEmbedder` is dead code, so no
  double count occurs today. But the same `ai/embed/input_token` vocabulary is
  produced by two implementations with different semantics (logical sum vs
  per-request) and different batch sizes (16 vs 8).
- **Why it matters:** it is a latent double-count and a vocabulary inconsistency.
  If `ProjectEmbedder` is ever wired (the recon `r5.10.7-...-recon.md:333` lists
  it as "becomes live if wired"), the same physical call would emit a logical
  fact *and* per-request facts, and totals would change semantics.
- **Smallest boundary:** choose one semantic. Either delete/deprecate the
  `instrumentAiProvider.embed` instrumentation (and mark `ProjectEmbedder` as
  the non-metered adapter), or make the wrapper delegate to the physical
  observer. No vocabulary change; this needs an explicit decision, not a new
  slice.

### C4. Doc/impl divergences (low risk, no behavior impact)

- `r5.10.1-usage-vocabulary.md:99` example `keyword_gap`; implementation emits
  `competitor_gap` (`dataforseo/providerUsage.ts`, `dataSource.ts:433`).
- `r5.10.1...md:158-164` GSC example is one `gsc_sync` fact of quantity 25;
  implementation emits one `gsc_request` per physical request
  (`list_sites`/`search_analytics`, quantity 1), as documented in R5.10.5.
- `r5.10.1...md:279` image-generation `sourceId='<seo_media.id>'`; implementation
  uses `null` (interactive) or `job.id` (`contentImages`).
- `r5.10.1...md:156` metadata `keywordCount`; implementation uses `{ method }` /
  `{ mode }`.
- `r5.10.3-ai-usage-instrumentation.md:47` says embed is one summed fact; R5.10.7
  superseded that with per-physical-request facts.
- `imageGenerationUsageEvent` (`usageInstrumentation.ts:178`) is no longer called
  in production after the R5.10.7 migration to the media observer.

### C5. Unused vocabulary

- `asset` (`usageEvent.ts:67`) has no producer. The optional `media_acquire`
  step was explicitly declined in R5.10.7. Harmless reserved vocabulary, but it
  means the closed-unit list is not fully exercised.

## D. Deferred items (intentional, not closeout blockers)

1. **Cohere reranker metering** (`providers/rerank/cohereReranker.ts`,
   `POST /v1/rerank`). Real external consumption, no usage fact. R5.10.7 recon
   gap 11 records it as an explicit follow-up; it is absent from the roadmap's
   "first version should measure" list and would require a category/unit
   decision. Intentional defer.
2. **Jina URL fetch metering** (`providers/jina/jinaKnowledgeFetcher.ts`). Same
   classification: real external call, explicitly out of R5.10.7 scope, needs a
   vocabulary decision. Intentional defer.
3. **Asset acquisition (`asset` unit)** - CDN byte downloads are excluded by
   design (R5.10.7 section 6.2.4); the optional `media_acquire` fact was
   deliberately not added. Intentional defer.
4. **Account-scoped GSC discovery** (`/account/gsc/discover`, `projectId = ''`)
   emits nothing; documented limitation in R5.10.5 section 11. The ledger already
   supports account-only scope; the provider context would need to carry
   `accountId`. Intentional defer.
5. **BYOK not honored at media/embedding provider seams** (`UNSPLASH_ACCESS_KEY`,
   `embedderFromConfig` read server env). Pre-existing credential design, not a
   usage-metering defect.
6. **`EMBEDDINGS_*` not in the zod env schema** (`config.ts`); forwarded via
   `context.ts:146-149` from `process.env`. Pre-existing config split.
7. **No retention/partitioning/archival policy** for `seo_usage_events` -
   declared non-goal in R5.10.2.

## E. Closeout verdict

**ONE OR MORE CONCRETE IMPLEMENTATION SLICES REMAIN.**

Reasoning against the closeout criteria:

| Criterion | Status |
| --- | --- |
| Coverage | Good; 11 producer seams across all 5 categories. Gaps: Cohere rerank, Jina fetch, `asset` (deferred). |
| Accuracy | Physical-attempt model where it matters; per-logical for DataForSEO/jobs; honest failures. |
| No double count | No live double count; one latent risk in dead `ProjectEmbedder` path (C3). |
| Scope | Project scope correct; account mirrored by trigger; interactive `userId` is null (C2). |
| Honest identity | No fabricated `sourceId`; null used where no stable id exists. |
| Local exclusion | Correct - Qdrant, lexical, chunking, local validation, OAuth tokens, CDN downloads, DataForSEO polling are not metered. |
| Vocabulary | Closed categories all used; `asset` unit unused; stale doc examples (C4/C5). |
| Persistence | Append-only, idempotent, fail-closed, best-effort; verified by DB smoke tests. |
| Reporting | **Absent** - no route, no UI, RPC unreachable (C1). |
| Tests | Strong producer/repository/DB coverage; zero coverage for a reporting surface because none exists. |

The instrumentation half of R5.10 is complete and internally consistent. The
account/project **usage read + reporting surface** explicitly named by the
roadmap ("Add basic account/project usage view") and required by R5.10's stated
first question was never delivered by any R5.10.x slice; it is the concrete
remaining implementation slice (C1). Two secondary items should accompany it or
be tracked: interactive user attribution (C2) and collapsing the two embedding
meters to one semantic (C3). Cohere/Jina/asset remain documented, intentional
deferrals (section D) and are not prerequisites for closing R5.10.

No further architectural recon is required: the read layer
(`list`/`aggregate`/`seo_usage_totals`), authorization model and vocabulary all
already exist.
