# R5.2.4 - One canonical selection model

Status: **implemented, awaiting review** (not committed).

This slice closes the R5.2 gap "One selection model" from
`docs/phase-5-roadmap.md`. Recon found three owners of the editor selection:

- `EditorSelectionContext` - coarse element selection (`EditorSelection`), lifted
  out of the composition surface;
- `EditorContext` - a normalized `EditorSelectionSnapshot`, synced by its own
  Tiptap subscription;
- `Content.tsx` - a local `hasSelection` boolean driven by yet another
  subscription (`selectionUpdate` + `transaction`).

They could disagree, and the two subscriptions duplicated the same Tiptap
selection. R5.2.4 makes one of them the owner and derives the rest. It does not
redesign selection UX, add workspace UI, or introduce a second Tiptap model.

## The canonical owner

`apps/web/src/components/content/editor/EditorSelectionContext.tsx` is the single
owner. `EditorSelectionProvider` subscribes to the live Tiptap instance once
(`selectionUpdate` / `focus` / `blur`) and publishes one value:

```ts
interface EditorSelectionContextValue {
  selection: EditorSelectionSnapshot; // canonical
  element: EditorSelection;           // derived coarse projection
  revealRequest: number;
  requestReveal: () => void;
}
```

It no longer exposes `setSelection`. Producers never push a selection in;
selection only ever flows out of the editor.

## The canonical representation

`EditorSelectionSnapshot` (already defined in `editorContext.ts`) is the one
representation:

- `{ type: 'none' }` - no usable editor (the empty value, also
  `EMPTY_EDITOR_SELECTION`);
- `{ type: 'cursor', from, to }` - collapsed insertion point;
- `{ type: 'text', from, to }` - non-empty text range;
- `{ type: 'node', from, to }` - a selected node.

Any snapshot may additionally carry `nodeType`, `nodePath` (transient structural
index, not an identity) and `blockId` (only when the node already has a real
`id`). Nothing is fabricated.

The coarse composition selection is a **derived projection**, not a second
representation:

- `editorSelectionFromSnapshot(snapshot)` returns the element type (via
  `resolveElementType`), plus `id`/`path` when present, or null when the snapshot
  has no reliable editor node.

`readSelectionSnapshot` samples the real ProseMirror selection; there is no
mirrored/copied Tiptap selection anywhere.

## Derived consumers

- `EditorContext` no longer owns selection state or subscribes to the editor for
  it. `EditorContextProvider` reads
  `useEditorSelection()?.selection ?? EMPTY_EDITOR_SELECTION` and copies it into
  `snapshot.selection` - a pure projection. Its own state remains identity,
  document/revision and dirty.
- `EditorWorkspace` nests `EditorSelectionProvider` **outside**
  `EditorContextProvider` and passes `editor` and `session.documentId`. Its
  `WorkspaceToolbar` derives `hasSelection` from the canonical value and overrides
  whatever the view passed.
- `ContentToolbar`'s `ContentAiToolbar.hasSelection` is now optional: the view
  cannot see the selection, so the workspace fills it in at the boundary.
- `EditorShell` reads `shared.element` instead of `shared.selection`; it keeps a
  local fallback only for standalone use without a provider (tests, other hosts).

## `hasSelection` derivation

```ts
snapshotHasSelection(snapshot) === snapshot.type === 'text' || snapshot.type === 'node'
```

`Content.tsx` no longer holds a `hasSelection` state or subscribes to
`selectionUpdate`/`transaction`. The AI toolbar's "select text" state now follows
the canonical selection for every consumer.

## Document-scoped selection

A selection belongs to the document it was made in. `EditorSelectionProvider`
takes `documentId` and clears its snapshot to `EMPTY_EDITOR_SELECTION` when that
identity changes. The Tiptap subscription reads the document id through a ref and
**ignores** events whose document no longer matches the one it subscribed under,
so a late event from the outgoing document cannot repopulate the snapshot. A
switch that does not change identity (a failed switch) does not clear anything.

## Why this owner

`EditorSelectionProvider` was already the selection seam furthest up the tree
(the contextual toolbar and the workspace both read it), and it is the only one
that lives at the boundary above `EditorContext`, so it can be the source both
`EditorContext` and the composition surface derive from without a cycle. Keeping
the normalized snapshot `EditorSelectionSnapshot` (not the coarse
`EditorSelection`) as the canonical value preserves every existing normalized
consumer (`embeddedAgent.ts`, `imageInsertion.ts`) while the coarse surface gets
a derived projection. No new state-management layer was added.

## Tests

New `components/content/editor/EditorSelectionContext.test.tsx` (6):

1. block select publishes one canonical value + the EditorContext projection and
   `hasSelection === true`;
2. clear: collapsed cursor is not a selection, and losing the editor empties the
   canonical value, projection and flag;
3. changing the selection replaces ownership with no stale value;
4. switching documents clears instead of carrying over;
5. a switch that keeps identity preserves the selection;
6. a selection-aware editor operation (`applyDocumentOperations` inserting an
   image) updates the canonical selection end to end.

`EditorWorkspace.test.tsx` (+1): the AI action availability follows the canonical
selection even though the view passed `hasSelection: false` - proof the flag is
derived, not view-owned. Selected-element lifting still passes.

Updated harnesses to sit inside the canonical provider: `EditorContext.test.tsx`,
`EmbeddedAgentEntry.test.tsx` (two harnesses), `EditorWorkspace.test.tsx`
selection harness.
