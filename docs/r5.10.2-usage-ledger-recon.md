# R5.10.2 - Usage Ledger Recon

This is the reconnaissance record that preceded R5.10.2. It captures the
conventions that were inspected, the proposed schema and the decisions. It is
kept for provenance; the delivered behavior is documented in
`docs/r5.10.2-usage-ledger.md`, which is authoritative where the two differ.
Two decisions changed during implementation and are corrected inline below:
scope FKs are `on delete set null` (not cascade) so historical usage evidence
survives project/account deletion, and `aggregate` takes the verified actor
(`actorUserId`) because the RPC enforces membership.

Recon only. No migration, repository, route or UI is implemented here. This
document records the existing conventions R5.10.2 must follow, the proposed
`seo_usage_events` schema, the idempotency decision, the persistence seam, RLS
and the test plan, and the open decisions that need confirmation before coding.

The contract this serves is `packages/contracts/src/usageEvent.ts` (R5.10.1) and
`docs/r5.10.1-usage-vocabulary.md`.

## 1. The invariant to protect

```text
Usage events can be appended, queried, and aggregated.
They cannot be updated or deleted through the application domain.
```

Concretely:

- the repository seam exposes `append` / `list` / `aggregate` only - no
  `update`, no `delete`, no generic CRUD;
- the table has a SELECT RLS policy and **no** INSERT/UPDATE/DELETE policy for
  `authenticated`/`anon`, so browser/PostgREST traffic cannot mutate rows;
- rows are inserted by the API/worker through the existing service-role client
  (`getContainer().sb`), which is the same path every other system-written table
  uses (`seo_audit_logs`, `seo_sync_jobs`, `seo_publications`, ...);
- cost is never stored. Later: `usage event -> pricing rule -> calculated cost`,
  never `usage event -> stored cost`, so historical usage stays truthful when
  provider prices change.

## 2. Existing migration conventions (recon findings)

From `supabase/migrations/` (30 files, next number `20260101000031`):

- Naming: `YYYYMMDDNNNNNN_<snake_case>.sql`, sequence `202601010000NN`; tables
  are `seo_*`; indexes `seo_<table>_<purpose>_idx`; constraints
  `seo_<table>_<rule>`; policies `seo_<table>_<action>`.
- PKs: `id uuid primary key default gen_random_uuid()`.
- Tenancy: `project_id uuid not null references public.seo_projects (id) on
  delete cascade`. Account-level rows use `account_id uuid references
  public.seo_accounts (id) on delete cascade` and may have a NULL `project_id`
  (precedent: `seo_api_keys` in `20260101000018`).
- Acting user: `created_by uuid references auth.users (id) on delete set null`.
- Timestamps: `created_at timestamptz not null default now()`; mutable tables add
  `updated_at` + a `seo_touch_updated_at()` trigger. An immutable table must NOT
  have `updated_at` and must NOT get the touch trigger.
- JSONB: `jsonb not null default '{}'::jsonb` + `check (jsonb_typeof(col) =
  'object')` (precedent: `seo_media.source_meta`, migration `20260101000030`).
- Account mirroring: when a project-scoped row omits `account_id`, a
  `before insert ... when (new.account_id is null)` `security definer` trigger
  copies it from `seo_projects.account_id` (precedents: `seo_writer_runs`,
  `seo_agent_runs`). Project membership stays the primary authorization
  boundary; the account is derived, never guessed.
- Idempotency: an optional `idempotency_key text` plus a partial unique index
  scoped to the owning project, e.g. `unique (project_id, idempotency_key) where
  idempotency_key is not null` (`seo_agent_runs`, migration `20260101000029`);
  NULL keys are not deduplicated (also `seo_sync_jobs`).
- RLS helpers (`20260101000006`, `20260101000011`): `seo_is_member(project,
  user)`, `seo_has_role(project, roles[])`, `seo_account_id_for_user(user)`.
- Server-written tables (migration `20260101000006`) get a SELECT-only policy;
  members may read, only the API/worker (service role) writes. `seo_audit_logs`
  adds a `(project_id is null and user_id = auth.uid())` branch for
  account/global rows - the exact shape nullable-scope usage events need.
- Read-model aggregation precedent: `seo_dashboard_summary(p_project,
  p_range_days)` is a `security definer` RPC that checks `seo_is_member` first
  and returns JSON (`20260101000007`).
- Consolidated schema: `dist/supabase-schema.sql` referenced in `CLAUDE.md` is
  not present in this checkout (no `dist/` tracked); schema work is the numbered
  migration plus the smoke harness.

## 4. Proposed `seo_usage_events` schema

New migration `supabase/migrations/20260101000031_usage_events.sql`:

```sql
create table public.seo_usage_events (
  id              uuid primary key default gen_random_uuid(),
  occurred_at     timestamptz not null default now(),

  account_id      uuid references public.seo_accounts (id) on delete set null,
  project_id      uuid references public.seo_projects (id) on delete set null,
  user_id         uuid references auth.users (id) on delete set null,

  category        text not null,
  provider        text not null,
  operation       text not null,

  quantity        bigint not null default 0,
  unit            text not null,

  success         boolean not null,

  source_id       text,
  metadata        jsonb not null default '{}'::jsonb,

  idempotency_key text,
  created_at      timestamptz not null default now(),

  constraint seo_usage_events_category_check
    check (category in ('ai','dataforseo','job','publishing','media')),
  constraint seo_usage_events_unit_check
    check (unit in ('request','task','keyword','serp_request','gsc_request',
                    'input_token','output_token','image_generation','asset',
                    'publish_attempt','job')),
  constraint seo_usage_events_quantity_check
    check (quantity >= 0),
  constraint seo_usage_events_provider_format
    check (provider ~ '^[a-z0-9_]{1,64}$'),
  constraint seo_usage_events_operation_format
    check (operation ~ '^[a-z0-9_]{1,64}$'),
  constraint seo_usage_events_source_id_length
    check (source_id is null or char_length(source_id) between 1 and 200),
  constraint seo_usage_events_metadata_object
    check (jsonb_typeof(metadata) = 'object')
);
```

Deliberate choices:

- No `updated_at`, no touch trigger. The row is written once.
- `occurred_at` is the fact's time; `created_at` is the ledger row's time.
  They are intentionally distinct.
- `bigint`, not `numeric`: every unit in the vocabulary is a non-negative
  integer count and `bigint` maps cleanly to `number` in PostgREST/supabase-js
  (whereas `numeric` comes back as a string). See open decision D2.
- `account_id` nullable with a project-mirroring trigger, so account-scoped
  events (`project_id is null`) and worker events (`user_id is null`) are both
  representable, exactly as the contract allows.
- Categories/units are enforced by CHECK (DB boundary) as well as by the
  contract guard (application boundary) - the vocabulary is closed in both.

Indexes (query + idempotency):

```sql
create index seo_usage_events_project_time_idx
  on public.seo_usage_events (project_id, occurred_at desc);
create index seo_usage_events_account_time_idx
  on public.seo_usage_events (account_id, occurred_at desc);
create index seo_usage_events_category_time_idx
  on public.seo_usage_events (category, occurred_at desc);
create index seo_usage_events_source_idx
  on public.seo_usage_events (source_id) where source_id is not null;

-- Idempotency is scoped, exactly like seo_agent_runs. Two partial indexes
-- because project_id and account_id are independently nullable (a single
-- (project_id, account_id, key) index would never dedupe NULL-project rows,
-- since Postgres treats NULLs as distinct).
create unique index seo_usage_events_project_idem_idx
  on public.seo_usage_events (project_id, idempotency_key)
  where idempotency_key is not null and project_id is not null;
create unique index seo_usage_events_account_idem_idx
  on public.seo_usage_events (account_id, idempotency_key)
  where idempotency_key is not null and project_id is null and account_id is not null;
```

Global events (both `project_id` and `account_id` null) are not deduplicated;
documented limitation, not a silent one.

Account-mirroring trigger mirrors `seo_writer_runs` / `seo_agent_runs`:

```sql
create or replace function public.seo_usage_events_set_account()
returns trigger language plpgsql security definer set search_path = '' as $$
begin
  if new.account_id is null and new.project_id is not null then
    select p.account_id into new.account_id
    from public.seo_projects p where p.id = new.project_id;
  end if;
  return new;
end; $$;
```

RLS - read-only for browser, service-role for writes:

```sql
alter table public.seo_usage_events enable row level security;

create policy seo_usage_events_select on public.seo_usage_events
  for select using (
    (project_id is not null and public.seo_is_member(project_id, auth.uid()))
    or (project_id is null and account_id is not null
        and account_id = public.seo_account_id_for_user(auth.uid()))
    or (project_id is null and account_id is null and user_id = auth.uid())
  );
-- Intentionally no insert / update / delete policies.
```

## 6. Idempotency decision (the important one)

R5.10.1 deferred this; R5.10.2 fixes it.

The risk: instrumentation is added later and a job retry re-emits a fact for an
attempt that did not actually happen again, double-counting usage.

Decision:

1. A usage event is idempotent **only when it is tied to a stable external
   attempt identity**. `sourceId` is that handle (job id, publication id, media
   id, DataForSEO task id, AI call id, ...). When `sourceId is null` the event is
   *not* deduplicated - it cannot be, honestly.
2. The deterministic key is a pure function of the fact, not a random uuid:

   ```text
   usageEventIdempotencyKey(category, provider, operation, unit, sourceId, occurrence?)
     = "v1|<category>|<provider>|<operation>|<unit>|<sourceId>|<occurrence ?? 0>"
     = null when sourceId is null
   ```

   `occurrence` (default 0) only exists for the rare case of several facts of
   the same kind within one external attempt (prefer one event with a summed
   `quantity`). The `v1` prefix leaves room to change the scheme additively.
3. Scope is enforced by the DB, not by string composition: the unique indexes
   are `(project_id, idempotency_key)` and `(account_id, idempotency_key, where
   project_id is null)`. A key can never collide across projects/accounts.
4. Retries that genuinely re-call a provider produce a new attempt identity
   (new provider task id, or `<jobId>:<attempt>`), so they correctly become new
   events. Application-level re-delivery of the *same* fact derives the same key
   and is dropped.
5. `append` is idempotent: duplicate keys are counted, not errored. No
   deduplication logic runs outside the store; the DB unique index is the real
   guard and the store treats 23505 as "already recorded".

This keeps the R5.10.1 promise ("do not emit duplicate events for retries unless
the underlying external attempt actually occurred") enforceable by the DB.

## 7. Persistence seam

One small, append-only module:
`apps/api/src/services/usageEventRepository.ts` (mirrors
`agentRunRepository.ts`: interface + Supabase implementation + in-memory double).

```ts
export interface UsageEventStore {
  append(events: readonly NewUsageEvent[]): Promise<{ inserted: number; duplicates: number }>;
  list(filter: UsageEventFilter): Promise<UsageEvent[]>;
  aggregate(request: UsageAggregateRequest): Promise<UsageAggregate[]>;
}
```

- No `update` / `delete` / `upsert` on the interface - the type itself protects
  the invariant.
- Supabase implementation maps rows fail-closed with `isValidUsageEvent` (a
  corrupt row throws `usage_event_invalid`, like `agent_run_state_invalid`)
  and converts `quantity` to a JS number.
- `append` derives the idempotency key when the caller does not supply one,
  inserts, and treats a 23505 as a duplicate (agent-run read-back pattern).
- In-memory implementation enforces the same idempotency + isolation semantics
  for unit tests.
- Wire `usageEvents: UsageEventStore` into `ServiceContainer` (`context.ts`) from
  `container.sb`, mirroring how other stores are constructed. No route and no
  executor call it yet (instrumentation is a later slice), so no runtime
  behavior changes.
- `aggregate` is the only part needing more than a select. Recommended: a
  `security definer` RPC `seo_usage_totals(...)` that checks membership first
  (mirrors `seo_dashboard_summary`) and groups by category/provider/operation/
  unit, so aggregation never pulls unbounded rows into the API. See D4.

## 8. Test plan

DB smoke test, appended to `scripts/db-migrate-local.sh` (the established
pattern is a `do $$ ... $$` block plus a separate non-superuser RLS leak check):

- insert a project-scoped event; assert the row and that `account_id` mirrors
  the project;
- insert an account-scoped event (`project_id is null`) and a worker event
  (`user_id is null`);
- reject malformed events: bad `category`/`unit` (check_violation), negative
  `quantity`, non-object `metadata`, non-token `provider`/`operation`;
- idempotency: duplicate `(project_id, idempotency_key)` rejected with
  unique_violation; the same key in another project accepted; duplicate
  `(account_id, idempotency_key)` for account-scoped rows rejected; assert both
  partial indexes exist;
- immutability: as `authenticated` (granted update/delete like Supabase's
  default privileges), `update` and `delete` affect 0 rows because there is no
  policy;
- isolation: a non-member reads 0 foreign-project rows (RLS leak count = 0).

Repository unit tests, `apps/api/src/services/usageEventRepository.test.ts`
(vitest, in-memory store, behavior-level - no snapshots):

- append a valid event returns `{ inserted: 1, duplicates: 0 }`;
- malformed event is rejected closed (does not write);
- appending the same fact twice is `{ inserted: 1, duplicates: 1 }`;
- the same key in two projects/accounts is two events;
- `list` respects scope (account/project isolation) and filters;
- `aggregate` sums `quantity` per category/provider/operation/unit;
- the store surface has no `update`/`delete` (compile-time / `@ts-expect-error`).

## 9. Decisions

Resolved (confirmed by the requester):

- **D1 - include `aggregate` now: yes (resolved via D4).** `list` + `aggregate`
  ship in R5.10.2, not a later read-model slice.
- **D2 - `quantity` type: `bigint` + tighten the guard.** `quantity bigint not
  null default 0 check (quantity >= 0)`; R5.10.2 also tightens
  `isValidUsageQuantity` to require `Number.isInteger` (a non-negative integer),
  so contract and column are 1:1. `bigint` maps cleanly to `number`, unlike
  `numeric`.
- **D3 - `idempotency_key`: derived by default, caller can override.** The store
  derives `usageEventIdempotencyKey(category, provider, operation, unit,
  sourceId, occurrence?)`; it is null when `sourceId is null` (not deduplicated).
  A caller may pass an explicit key when `sourceId` is absent but a stable id
  exists. The DB partial unique indexes remain the real guard.
- **D4 - aggregation: `security definer` RPC.** One membership-checked RPC
  `seo_usage_totals(...)` (mirrors `seo_dashboard_summary`) groups in SQL and
  never returns raw rows to the API.

Still open at recon time - both resolved yes during review:

- **D5 - container wiring: yes.** `usageEvents: UsageEventStore` is added to
  `ServiceContainer` (`context.ts`) so later instrumentation/read slices share
  one wiring point.
- **D6 - commit shape: one slice.** Migration + smoke, contracts additions,
  repository + unit tests and docs ship as one commit
  (`feat(r5): add append-only usage ledger`).

Status: delivered; see `docs/r5.10.2-usage-ledger.md` for the implemented
schema, seam and verification.

## 10. Explicit non-goals for R5.10.2

- no provider instrumentation or event emission (no executor/provider changes);
- no HTTP route, no UI, no MCP surface;
- no billing, credits, quotas, pricing or stored cost;
- no retention/partitioning/archival policy (noted as future operational work);
- no account switcher or second tenancy model - existing account/project
  relationships stay authoritative;
- no changes to R5.6-R5.9 behavior.
