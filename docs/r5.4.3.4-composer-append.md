# R5.4.3.4 - Appending Composer output to a non-empty document

Status: **delivered**. The append slice of R5.4.3 (after the R5.4.3.3 recon): the
representable parts of a composed page can be added to the currently open
**non-empty** workspace document. R5.4.3.2 already replaces an empty document;
this slice is the complement for a document that already has content.

The composed `CanonicalDocument` is mapped onto the existing operation-batch
vocabulary (R2 `documentOperations`) by a pure contracts function, then applied
through the existing `EditorContext.applyDocumentOperations` path. No new
operation types, no new proposal/mutation/persistence model, and no whole-document
replacement fallback.

## 1. Flow

```text
Composer planning/preview                 (document-independent, R5.4.1)
        |
        v
 composed CanonicalDocument               (existing composition pipeline)
        |
        v
 mapCompositionToAppendOperations         (pure; operations + explicit gaps)
        |
        v
 shell stages a DesignerProposal          (document + operations + baseRevision + boundary)
        |
        v
 onModeChange('editor')                   (composer -> editor, shell stays mounted)
        |
        v
 CompositionApplyBridge (inside the editor context)
        |  boundary check + revision check (applyDocumentOperations)
        v
 applyDocumentOperations                   (the single operation-batch mutation path)
        |
        v
 one setContent transaction                (undoable, onDocChange + autosave persist)
        |
        v
 gaps reported by notice                   (never silently dropped)
```

Two proposal forms now share one bridge: `proposal.document` only ->
`applyExternalDocument` (empty target, R5.4.3.2); `proposal.operations` present ->
`applyDocumentOperations` (append, this slice).

## 2. Why operations, and never replacement

The Composer emits a full `CanonicalDocument`; when the open document is
non-empty, that page must not replace it. The only existing mechanism for
inserting structure into an existing document is the operation batch
(`applyDocumentOperations`), which is `baseRevision`-guarded, deep-clones the base
and is already the executor used by the section-creation flow. This slice reuses
that mechanism rather than inventing a merge path.

There is **no fallback to whole-document replacement** and **no silent drop** of
unsupported content: every structure the operation vocabulary cannot represent is
reported as an explicit `CompositionGap`, and a run with no representable
structure is refused before staging.

## 3. Mapping (`@seo/contracts/src/compositionAppend.ts`)

`mapCompositionToAppendOperations(composed): CompositionAppendMapping` is pure,
deterministic and has no React/editor/session/API/Tiptap dependency. It emits
existing operation kinds at `position: { mode: 'document_end' }`:

| Composed structure | Result |
| --- | --- |
| top-level `hero` / `section` | `insert_section` (kind, validated `variant`, validated `layout`) plus its mapped children, under a fresh `section-N` ref |
| child `heading` (valid level 1-6, representable text) | `insert_text` heading into the ref |
| child `paragraph` (representable text) | `insert_text` paragraph into the ref |
| child `image` with `mediaId` + `src` + `alt` (valid insertion candidate) | `insert_image` into the ref |
| anything else | a `CompositionGap` |

Gap codes are deliberately small: `unsupported_block` (top-level or child type
outside the vocabulary), `unsupported_content` (empty / non-text / over-long text,
heading without a valid level), `image_without_asset` (image lacking a real
`mediaId`), `empty_container` (hero/section whose children mapped to nothing) and
`operation_limit` (the `DOCUMENT_OPERATION_MAX_OPS` cap was reached). Each gap
carries a structural `path`, the `type`, the `code` and a deterministic
user-facing `message`.

The realistically composed hero (image + primary CTA) is **not** fully
representable: the asset-less image and the CTA become gaps while any
heading/paragraph children are still appended. That is the honest outcome, not a
degraded document.

## 4. Staging and the bridge

- `ComposerMode` forwards `onAppendToDocument` / `canAppendToDocument` to
  `Compose`. `Compose` shows an outline **"Add to current document"** button,
  disabled unless the open document is an eligible (non-empty) target, with an
  explanatory hint.
- The shell's `appendComposition(document)` re-checks non-emptiness against the
  live editor document, maps the composed document, refuses (with an error) when
  nothing is representable, and otherwise stages
  `pendingAppendCompositionOf(base, operations, documentRevisionOf(openDoc),
  session.boundary, gaps)` as a `DesignerProposal` with an `operations` batch,
  then moves to the editor mode. It never posts `/content` and never switches
  documents.
- `CompositionApplyBridge` sees `proposal.operations` and applies through
  `context.applyDocumentOperations(proposal.operations, proposal.baseRevision)`.
  The result is a normal `setContent` transaction: undoable, and it emits an
  update so the existing `onDocChange` + autosave boundary persists it.

Eligibility: `canApplyComposition` (empty) and `canAppendComposition` (non-empty)
are mutually exclusive through `isCanonicalDocumentEmpty`, so a run can never
offer both actions for the same document.

## 5. Async / stale-result safety

The operation batch carries the same two guards as the R5.4.3.2 replacement, and
`applyDocumentOperations` adds its own double revision check (live document
revision and `batch.baseRevision`):

- **Boundary**: the staged value captures `session.boundary` at request time. If
  the session document changed before the bridge runs, its boundary differs and
  the apply is a no-op (`stale-document`); content is never written into the wrong
  document.
- **Revision**: a mismatched base revision returns `stale-revision` rather than
  writing when the document moved underneath the staged composition.

The bridge applies each staged value at most once and waits for the editor
instead of dropping the work.

## 6. Failure semantics

| Case | Result |
| --- | --- |
| Non-empty document, supported structures, apply succeeds | operations appended in place; notice (with gaps when partial); autosave persists it; no document switch, no `/content` create |
| Empty document | append refused before staging; error points to "Apply to current document" |
| Run has no representable structure | append refused before staging; error lists the gaps; document unchanged |
| Run is partly representable | supported parts appended; remaining gaps reported in the notice |
| Session boundary moved before apply | `stale-document`; document unchanged |
| Live revision no longer matches the staged base | `stale-document`; document unchanged |
| Editor not ready yet | bridge waits; applies once ready |

All outcomes clear the staged pending value, so a stale or failed append cannot
fire again later.

## 7. Preserved / non-goals

- R5.4.2 create-new-draft handoff and R5.4.3.2 empty-document replacement are
  behaviorally unchanged; the three composer affordances share one shell and one
  mutation pipeline.
- No new operation types and no operation-batch redesign; the mapping emits only
  the existing `insert_section` / `insert_text` / `insert_image` vocabulary.
- No new proposal/review framework and no server-side apply of operations:
  `DesignerService.apply` still refuses an `operations` proposal with
  `422 designer_operations_require_editor`; the append is editor-applied only.
- No Composer UI redesign, no Composer persistence or document identity, no
  Composer-owned Tiptap APIs, no direct Tiptap mutation from Composer mode
  (R5.3.3 isolation holds).
- No media/asset resolution for placeholder images: an image without a real
  `mediaId` is a reported gap.
- No id remapping / preservation of composed slot ids; refs are fresh
  `section-N`.
- No Designer/EditorMode architecture change, no session/boundary/revision model
  change, no DB migration.
- No partial-apply of unsupported structures and no contextual (non-
  `document_end`) insertion.
