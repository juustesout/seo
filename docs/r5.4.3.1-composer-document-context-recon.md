# R5.4.3.1 - Composer output to shared document context (recon)

Status: recon complete. No production code, no migration, no operation type and no
proposal framework changed. This document maps how the existing Composer output
can reach the unified workspace document *without* introducing a second mutation
model, and recommends the R5.4.3 boundary.

Roadmap R5.4 line addressed: "Adapt Composer output to the shared document
context" and "Ensure structural proposals use the existing operation-batch model"
(`docs/phase-5-roadmap.md:137,139`).

## 1. Question and scope

After R5.4.1 (Composer mounted as a workspace mode) and R5.4.2 (create-then-switch
handoff), the open question is:

> How does a composed page become part of the one shared document context, given
> that the shared model has exactly one mutation pipeline and Composer currently
> produces a whole `CanonicalDocument` with no base document?

In scope: describe the existing pieces, classify every Composer output shape
against the existing operation-batch / proposal vocabulary, identify owners, and
recommend the smallest correct next slice.

Out of scope (R5.4.3.1): any code change; extending `DocumentOperationBatch`;
adding a Composer persistence path; replacing the standalone Composer navigation;
redesigning Composer UI; changing R5.4.2 handoff; mounting editor infrastructure
in Composer.

## 2. Existing pieces

### 2.1 Composer pipeline and output

`views/Compose.tsx` runs two explicit server phases and keeps all workflow state
locally (`brief`, `format`, `phase`, `plan`, `document`, `tab`, `creating`):

```text
brief
  -> POST /projects/:id/composition/plan    -> CompositionPlan (structure only)
  -> POST /projects/:id/composition/compose -> filled CanonicalDocument
  -> CanonicalRenderer                      -> preview
  -> POST /projects/:id/content             -> persisted draft (R5.4.2 handoff)
```

Server side (`apps/api/src/services/compositionService.ts`):

- `compileComposition(plan)` (`packages/contracts/src/compositionPlan.ts:456`)
  deterministically emits a `CanonicalDocument` skeleton plus a `CompositionSlotMap`.
- the AI writer may only fill slots; `applyCompositionSlotFills`
  (`compositionWriter.ts:242`) applies copy to a clone and proves the structure is
  unchanged (`structure_changed` on any drift).
- media slots are deliberately **not writable** (`NON_WRITABLE_ROLES` /
  `compositionSlotKindOf`, `compositionWriter.ts:82-97`): a composed image block
  has no `mediaId`.

So the Composer output is a **full canonical document** (skeleton + copy), built
with no knowledge of any base document. Only the last step persists, by creating
a brand-new content row (R5.4.2).

### 2.2 Canonical shared document model

The workspace operates on exactly one document at a time:

- identity: `useDocumentSession` `DocumentIdentity` `{ documentId, creating }`
  plus a frozen `boundary` and `generation`
  (`apps/web/src/components/content/session/useDocumentSession.ts:138-214`).
- content + revision: the editor holds the live Tiptap document; `documentRevisionOf`
  (`components/content/documentRevision.ts:27`) is the editor-side token, and
  `contentRevisionOf` (`packages/contracts/src/designer.ts:389`) is the stored
  `content_json` token. Both are FNV-1a of stable-serialized JSON, so the editor
  document and the persisted row share one revision vocabulary.
- load: `useDocumentLoad` is the identity-stamped loader; `documentLifecycle`
  is the single ready/loading/error projection.
- save: one `useAutosave` with an awaitable `flush()`; the session `runBarrier`
  uses it as the document-leaving barrier.

Canonical bridge: `editorDocumentToCanonical` / `canonicalDocumentToEditorDocument`
(`packages/contracts/src/editorHandoff.ts`) round-trip the editor document and the
canonical view, preserving composition nodes (`hero`, `section`, `featureGrid`,
`featureCard`, `cta`, `button`). `canonicalFromEditorDocument`
(`components/content/editorDraft.ts:57`) throws when the edited document is not
representable as canonical.

### 2.3 Operation-batch model

`packages/contracts/src/documentOperations.ts` defines the single structural
mutation instruction, `DocumentOperationBatch` v1:

- pure, deterministic, atomic executor `applyDocumentOperations`
  (`documentOperations.ts:388`): deep-copies a base `CanonicalDocument`, applies
  ordered ops, throws on partial/invalid results;
- operations carry an operation-local `ref` (never a canonical `id`); references
  are strictly backward;
- current op vocabulary is deliberately small:
  - `insert_section` for `hero | section` only, with optional `variant`/`layout`
    and a position (`document_start | document_end | before_block | after_block`);
  - `insert_text` for `heading | paragraph` only;
  - `insert_image` targeting a `ref`/`block`, carrying a real
    `ImageInsertionCandidate` (requires `assetId`).
- `baseRevision` ties a batch to the document it was resolved against; the editor
  refuses a batch whose `baseRevision` does not match the live revision
  (`EditorContext.tsx:163-203`).

The batch is created server-side by `SectionCreationService.buildProposal`
(`apps/api/src/services/sectionCreationService.ts:75-210`), which reads the stored
document, computes `contentRevisionOf(content.content_json)` as `baseRevision`,
and wraps the batch in a `DesignerProposal` (`operations` field).

### 2.4 Proposal / review model

`DesignerProposal` (`packages/contracts/src/designer.ts:301-337`) is the single
reviewable-suggestion envelope. It already carries every shape Composer could
need:

- `document: CanonicalDocument` - the whole-document candidate;
- `plan?`, `review?` (`{ ok, errors, warnings, score }`);
- `operations?: DocumentOperationBatch` - structural suggestion the editor applies;
- `insertion?` / `acquisition?` - editor-applied single ops / confirmations.

Invariants already encoded in the comments:

- a proposal is never persisted `seo_content`; the editor is the human approval
  layer;
- `operations` and `insertion` are applied **by the editor** as its own undoable
  transaction, and `DesignerService.apply` refuses them
  (`designerService.ts:441-461`) so a batch can never masquerade as an applied
  change;
- `insertion`/`operations` are mutually exclusive with each other.

### 2.5 Apply paths (the only two)

There is no third mutation path, and both already exist:

| Path | Where | Semantics |
| --- | --- | --- |
| Whole-document replacement | `EditorContext.applyExternalDocument` (`EditorContext.tsx:127-146`); server `DesignerService.apply` (`designerService.ts:437-475`) | revision-guarded `setContent`, or `ContentService.write` after a stale check |
| Structural operation batch | `EditorContext.applyDocumentOperations` (`EditorContext.tsx:163-203`) | `canonicalFromEditorDocument` base -> `applyDocumentOperations` -> one `setContent` transaction, revision-guarded |

Composer output must use one of these. No Composer-specific write, no new
`document` owner.

## 3. The two target behaviors

"Adapt Composer output to the shared document context" is ambiguous; it splits
into two behaviors with different risk:

1. **Compose a new page.** Composer produces a complete page and it becomes the
   active document. *Already delivered in R5.4.2* through `POST /content` +
   `requestDocumentSwitch` (a new document, not a replacement). No change needed.
2. **Compose into the open document.** Composer structure/copy is added to the
   document the workspace currently has open, preserving existing content.

Behavior 2 is where the operation-batch question bites, and where a
whole-document replacement would be destructive on a non-empty document.

## 4. Composer output -> operation mapping

Legend: **Direct** = representable by an existing op; **Transform** = existing op
plus a deterministic mapping (no new vocabulary); **New op** = only representable
if the op vocabulary is extended additively; **No path** = cannot be expressed,
must be honestly reported.

| Composer canonical shape | Existing op | Class |
| --- | --- | --- |
| `hero` container | `insert_section kind:'hero'` (+ `variant`/`layout`) | Direct |
| `section` container | `insert_section kind:'section'` (+ `variant`/`layout`) | Direct |
| `heading` (in hero/section) | `insert_text` heading (level preserved) | Direct |
| `paragraph` | `insert_text` paragraph | Direct |
| `image` with real asset (`mediaId`) | `insert_image` + `ImageInsertionCandidate` | Transform |
| `image` without `mediaId` (all composed media slots) | none | No path (honest omission) |
| `list` + `listItem` | none (`insert_text` has no list) | New op |
| `quote`, `code` | none | New op |
| `badge`, `button` (leaf, incl. `href`/`variant`) | none | New op |
| `statItem`, `stats` | none | New op |
| `featureGrid`, `featureCard` | none (`insert_section` only hero/section) | New op |
| `cta`, `callout`, `testimonial`, `mediaText`, `footer` | none | New op |
| nested composition deeper than one level | only within a created `hero`/`section` via `ref` | New op |
| update copy of an existing block | none (op model is insert-only) | New op |
| `meta.designSystem` | n/a (doc-level; carried by the base document) | Not in scope |
| whole composed document | `DesignerProposal.document` + replacement apply | Existing path |

Two structural observations:

- **Insertion order vs path indices.** A batch can append sections reliably with
  sequential `document_end` inserts, preserving order. Inserting *mid-document*
  via `after_block` paths shifts later indices, and refs only target created
  containers, so multi-section anchored insertion is not safely expressible today.
- **Base document gap.** The op model requires a `baseRevision` and a base
  canonical document. Composer currently composes from a brief with *no* base, so
  building a valid batch against the open document requires supplying that base
  (current editor revision + canonical form) to the Composer path.

Net: a pure operation mapping today would cover only hero/section + heading/paragraph
+ real-asset images - i.e. it would silently drop most of a landing page
(`featureGrid`, `cta`, `list`, `stats`, ...). That is not acceptable, so either the
op vocabulary must grow additively or the whole-document replacement path must be
used where it is safe.

## 5. Ownership analysis

| Concern | Single owner | Composer must not |
| --- | --- | --- |
| Active document identity/boundary | `useDocumentSession` (shared session) | hold a document id or a second boundary (R5.4.1) |
| Live content + revision | editor (`EditorContext` + `documentRevision.ts`) | persist `seo_content` or keep a document copy |
| Structural mutation | `DocumentOperationBatch` executor via `EditorContext.applyDocumentOperations` | apply ops itself or add a Composer write |
| Whole-document replacement | `applyExternalDocument` / `DesignerService.apply` | create a new replacement channel |
| Reviewable suggestion | `DesignerProposal` | introduce a second proposal envelope |
| Composition workflow state | `Compose` (brief/format/phase/plan/preview) | move it into the shared session |
| Project identity / role | `WorkspaceSessionValue` (`useWorkspaceSessionContext`) | read them from a Composer-local source |

Verdict: everything Composer needs already has a single owner. R5.4.3 is a
**mapping/wiring** slice, not a new-model slice.

## 6. R5.4.2 handoff compatibility

The two behaviors do not conflict if kept explicit:

- New page (R5.4.2): `POST /content` -> `requestDocumentSwitch(id)` -> editor.
  Unchanged.
- Into open document (R5.4.3): batch/replacement built against the **open**
  document's revision, applied inside the editor, guarded by the existing
  `useOperationBoundary` + `expectedRevision` checks.

Both use the shared session and the existing boundary, so neither introduces a
second identity. The stale-result guard already proven in R5.4.2
(`beginHandoff` -> `useOperationBoundary` + unmount) is the same pattern a
Composer apply task should use. The two paths are mutually exclusive at the UI
level (new page vs add to current page), so a composition run never triggers both.

## 7. Recommended R5.4.3 boundary

Deliver "Composer output in the shared document context" in two small,
independent slices, both reusing existing mutation paths:

1. **R5.4.3.2 - Compose into an empty/new current document (whole-document
   replacement).** When the shared document is brand new/empty, the composed
   `CanonicalDocument` can be applied through the existing whole-document
   replacement path (`applyExternalDocument` or the `DesignerProposal.document`
   server apply), guarded by `baseRevision` = the open document revision and the
   existing proposal/review step. Full composer fidelity (featureGrid, cta,
   list, ...) because the editor already renders those composition nodes. No new
   operation type, no new mutation model.

2. **R5.4.3.3 - Append Composer structure to a non-empty document (operation
   batch).** Derive a `DocumentOperationBatch` from the composed document against
   the base snapshot, restricted to the currently representable subset
   (hero/section + heading/paragraph + real-asset image). Anything not
   representable is surfaced in review as "not added" (honesty rule, no silent
   drop). If full structural fidelity on append is required later, that is an
   additive op-vocabulary slice (`DocumentOperationBatch` v1 -> vN), explicitly
   out of scope here.

Recommended first implementation slice: **R5.4.3.2**, because it is the smallest
change that makes a composed page real in the unified workspace, covers the whole
composer vocabulary through an existing path, and cannot be destructive (the
target is empty). R5.4.3.3 follows once the review/apply UI for a
`DocumentOperationBatch` is confirmed against the shared chrome.

Explicitly **not** recommended: a Composer-specific `POST /content` write into the
open document, a Composer-owned revision, or a parallel batch executor.

## 8. Open questions

- Should "into the open document" be exposed at all in R5.4.3, or is "compose a
  new page" (R5.4.2) sufficient for the roadmap's done-when ("compose a page and
  immediately switch to Designer or Editor")? The new-page path already satisfies
  it; behavior 2 may belong to a later slice.
- If append is in scope, do we accept the representable-subset limitation with
  honest "not added" reporting, or is extending `DocumentOperationBatch`
  (additively) acceptable in the same milestone?
- Where does the review/apply affordance live: inside Composer mode, or in the
  shared chrome (R5.3.2)? Must stay one surface to satisfy "one brain, two
  mouths".
- Does applying a composed document at the open document's position need
  selection-aware placement, or is `document_end` sufficient for v1?

## 9. Non-goals

- No new operation type in this recon slice.
- No new proposal framework; `DesignerProposal` is the envelope.
- No Composer-specific persistence or document identity.
- No change to R5.4.2 handoff or the standalone Composer navigation.
- No editor infrastructure mounted in Composer mode (R5.3.3 isolation holds).
- No whole-document replacement of a **non-empty** document (destructive).
