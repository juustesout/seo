# R5.2.1 - Session boundary and document-switch save barrier

Status: **implemented, awaiting review** (not committed).

This is the first R5.2 slice and the first gate locked in
`docs/r5.1-workspace-decisions.md`. It makes unsaved-changes safety real before
the workspace route and mode switching are built on top of it.

## Scope

In:

- One authoritative current-document identity owned by a shared session layer.
- `requestDocumentSwitch(nextDocumentId): Promise<SwitchResult>` with the
  documented blocked/switched contract.
- An awaitable save primitive that reuses the existing autosave.
- Every document-leaving action (switch, new document, back to list) passes
  through the barrier.

Out (deliberately untouched): workspace routes, mode switcher/shell, provider
lifts, `EditorContext`/`EditorSelectionContext`, the loader, the save service,
and the existing dirty-state model.

## Where it lives

- Session boundary: `apps/web/src/components/content/session/useDocumentSession.ts`.
  It owns `DocumentIdentity` (`{ documentId, creating }`) and exposes
  `requestDocumentSwitch`, `requestNewDocument`, `requestCloseDocument`,
  `adoptDocumentId` and `discardDocument`. `adoptDocumentId` is the only path
  that changes identity without a barrier (the first save of a new document
  gains a server id, it does not leave a document); `discardDocument` is used
  after a delete, when there is nothing left to flush.
- Consumer: `apps/web/src/views/Content.tsx` no longer keeps `editingId` /
  `creating` in local state. It derives them from `session.identity` and routes
  `open` / `startNew` / `goList` through the barrier. Destination-only state
  (clearing errors, resetting AI, bumping the editor key, seeding a new title)
  is applied by the `after` callback only after the barrier reports `switched`.

## How the barrier waits

`useAutosave` gained `flush(): Promise<boolean>`; `saveNow` and the debounce
timer now share one `runSave` loop:

- clean or no baseline -> resolves `true` without persisting;
- dirty -> persists the latest snapshot immediately (clearing the pending
  debounce) and loops until the workspace stops changing;
- a `flush` that arrives while a save is in flight joins the running chain and
  marks it for a rerun, so newer edits are included before it settles;
- a failed persist -> resolves `false` and leaves the workspace dirty.

The session calls the latest autosave through a ref
(`flushRef.current = auto.flush`), which avoids a hook-ordering cycle between
the identity state and the autosave that depends on it. A concurrent switch
while the barrier is running is refused with `save_in_progress`.

## How failure prevents replacement

`runBarrier` only calls `setIdentity(next)` after the flush resolves `true`.
On `false` or a thrown flush it returns `blocked: save_failed` and the current
identity is unchanged, so the editor is never remounted and dirty state is never
cleared. `Content.tsx` surfaces a retryable error banner; the existing autosave
"failed" banner and the Save button remain the retry path.

## Tests

- `session/useDocumentSession.test.ts` (7): clean switch, dirty flush ordering
  (A stays current while saving, then B), save failure keeps A, deferred
  rejection keeps A, concurrent switch refused while saving, new/close through
  the barrier, adopt/discard without a flush.
- `useAutosave.test.ts` (9, +4): flush on a clean workspace saves nothing, flush
  persists pending edits immediately, flush waits for an in-flight save and
  includes edits that land during it, flush resolves `false` and stays dirty on
  failure. The five original autosave tests are unchanged and green.
