# R5.10.6 - Publishing usage instrumentation

Delivered behavior for recording publication requests (WordPress and X) in the
R5.10.2 append-only usage ledger. The repository analysis this builds on is
`docs/r5.10.6-publishing-usage-recon.md`; this document records the delivered
design and decisions, not the call-graph discovery.

Contract: `packages/contracts/src/usageEvent.ts` (R5.10.1, category `publishing`,
unit `publish_attempt`). Ledger:
`supabase/migrations/20260101000031_usage_events.sql` (R5.10.2). No migration,
vocabulary change or ledger schema change is required or made.

## 1. What counts as one `publish_attempt`

One actual HTTP request that creates, updates or deletes a remote publication is
one `publish_attempt` fact. Local work is never counted. The rule resolved by the
recon (section 17) is implemented literally:

| Provider | Counted method | Operation token |
| --- | --- | --- |
| WordPress | `WordPressClient.createPost` | `publish` |
| WordPress | `WordPressClient.updatePost` | `publish_update` |
| WordPress | `WordPressClient.deletePost` | `publish_delete` |
| X | `XOAuthClient.createPost` (`POST /2/tweets`) | `publish` |

Not counted: local validation/payload building, `whoami`, OAuth/token requests,
X identity (`/2/users/me`), local publication/history persistence, schedule or
job enqueue, and `mock_social` (it performs no external request at all).

## 2. Instrumentation seam

The seam is the **provider-specific client method**, not the generic adapter
layer and not `fetch`.

```text
publish executor
    -> PublisherProvider (wordpress | x)
        -> WordPressClient.create/update/deletePost   <- WordPress seam
        -> XOAuthClient.createPost                    <- X seam
            -> fetch(remote)
                -> usageEvents.append()               (best-effort)
```

WordPress ad-hoc `fetch` cannot be the seam directly because the same client
also serves `whoami`; X has token and identity calls on the same client. Wrapping
`fetch` or the generic `PublisherProvider` interface would wrongly count
`whoami`/token/identity traffic and would count `mock_social`, which must produce
zero publishing usage. Only the publication methods carry an operation.

## 3. Observer wiring

A small callback (`PublishRequestObserver = (operation, success) => Promise<void>`)
keeps the clients free of project/user/credentials scope; the adapter binds scope
in `publishUsageObserver(ctx, provider)` (`providers/publishing/providerUsage.ts`)
and passes it to the client constructor.

- `WordPressClient(baseUrl, username, appPassword, fetchFn, observe?)` -
  `request(method, path, body?, operation?)` reports once per call when an
  operation is supplied. `clientFor(ctx)` passes `publishUsageObserver(ctx, 'wordpress')`.
- `XOAuthClient(clientId, fetchFn, observe?)` - `jsonRequest(..., operation?)`
  reports once; only `createPost` passes `publish`.
  `XPublisher.client(ctx)` passes `publishUsageObserver(ctx, 'x')`.
- When `ctx.usage` is absent the observer is `undefined` and the client performs
  no usage work.

## 4. Event shape

```ts
{
  category: 'publishing',
  provider: 'wordpress' | 'x',
  operation: 'publish' | 'publish_update' | 'publish_delete',
  unit: 'publish_attempt',
  quantity: 1,
  success: boolean,
  accountId: null,          // mirrored from project by the ledger trigger
  projectId,
  userId,                   // job.created_by on the publish path (may be null)
  sourceId,                 // job id for job-originated publishes, else null
  idempotencyKey            // v1|...|sourceId|<occurrence>
}
```

`buildPublishAttemptUsageEvent` returns `null` (nothing appended) for a
non-UUID `projectId` or an invalid provider/operation token.

## 5. Failure semantics

- **Before the request** (missing `base_url`/credentials, local 280-char/title
  validation): no client call, no event.
- **Remote non-2xx** (including 401/403): one event with `success: false`; the
  original `WordPressError` / `PublisherError` propagates unchanged.
- **Transport rejection**: the request was attempted, so one event with
  `success: false`; the original error propagates.
- **2xx**: one event with `success: true`, recorded before the response body is
  parsed, so a later JSON parse error still reflects a successful HTTP exchange.

WordPress reports inside `request()` via a `try/catch/finally`-shaped guard:
the observer runs after `fetch` settles and the original error (if any) is
rethrown untouched. X reports in `XOAuthClient.createPost` with its own try/catch
so a misbehaving observer can never alter the publish outcome.

## 6. Best-effort append

`emitPublishAttemptUsage` reuses the shared `appendUsage` seam from
`services/usageInstrumentation.ts`: a missing sink or a failed append is logged
and swallowed. Usage persistence is never the publishing transaction boundary - a
successful publication still returns its result, and a failed publication still
throws its original provider error. This is covered by an executor test that runs
a successful WordPress publish against a throwing ledger and asserts the
publication still reaches `published`.

## 7. Job correlation and retry semantics

The `publish` executor builds the provider context with
`usageSourceId: job.id` and `usageOccurrenceBase: publishUsageOccurrenceBase(job.retry_count)`
(`executors.ts`). Both the WordPress and X adapters inherit that context.

Unlike the R5.10.4 single terminal `job/job` fact, publishing usage records
**actual remote attempts**, so a durable job retry that really sends another
publication request is a genuinely new `publish_attempt` and must not deduplicate
against the previous execution.

```text
retry_count 0, request #1 -> key ...|job-1|0
retry_count 1, request #1 -> key ...|job-1|1000000
```

`PUBLISH_OCCURRENCE_STRIDE = 1_000_000` seeds the per-execution occurrence
counter above every occurrence the previous execution could have produced, while
`sourceId` stays exactly `job.id`. Execution 0 re-derived (duplicate delivery of
the same execution) still dedupes to occurrence `0`; a real retry advances by the
stride and appends a new row. One execution can legitimately produce more than
one attempt (an X 401 refresh-once makes two requests, section 8), which the
same counter keeps distinct.

## 8. X refresh-once physics

`XPublisher.publish` refreshes an expired access token once and retries. Both
`POST /2/tweets` requests reach X, so both are reported:

```text
POST /2/tweets           -> publish_attempt success=false (401)
POST /2/oauth2/token     -> token endpoint, NOT reported
POST /2/tweets (retry)   -> publish_attempt success=true
```

A 401-refresh-retry therefore produces **two** `publish_attempt` facts. The token
endpoint and `/2/users/me` are on the same `XOAuthClient` but pass no operation,
so they never produce facts. `update`/`delete` throw `NotAvailable` locally and
never call X, so they emit nothing.

## 9. `mock_social` exclusion

`MockSocialPublisher` performs no request and is not wired to any observer, so a
`mock_social` publish job appends zero events even though the executor supplies a
usage context. Instrumenting the generic adapter layer or `fetch` would have
counted it; instrumenting the provider client methods does not. Pinned by an
executor test.

## 10. Idempotency / occurrence

The R5.10.2 ledger mechanism is reused verbatim; there is no application-level
dedup. `idempotencyKey` is derived by `usageEventIdempotencyKey`:

```text
v1|publishing|wordpress|publish|publish_attempt|<sourceId>|<occurrence>
```

- Job publishes: `sourceId = job.id`, so a duplicate delivery of the same
  execution derives the same key sequence and dedupes.
- A real retry raises the occurrence base (section 7), producing new keys.
- Non-job publishes (none today; connection tests never publish): `sourceId` is
  null, the key is null, and the event is honestly non-deduplicatable.
- No timestamps, random ids or response hashes are used as identities.

## 11. Test coverage

- `apps/api/src/providers/publishing/providerUsage.test.ts` - fact shape, non-UUID
  project guard, invalid provider/operation guard, occurrence-key uniqueness,
  nullable-`sourceId` behavior, `publishUsageOccurrenceBase` (0 / stride /
  invalid input), best-effort append including a throwing sink, observer binding.
- `apps/api/src/providers/wordpress.test.ts` - one fact per create/update/delete,
  remote rejection and transport failure recorded as `success=false` with
  `WordPressError` preserved, `whoami` = 0 facts, missing config = 0 facts and no
  request.
- `apps/api/src/providers/social/xPublisher.usage.test.ts` - one fact for a
  successful post, refresh-once = 2 facts (token call excluded), local 280-char
  rejection = 0 facts, `update`/`delete` = 0 facts, `XOAuthClient` reports only
  `createPost` (identity call excluded) and reports failures as `success=false`.
- `apps/api/src/jobs/executors.publish.test.ts` - job correlation
  (`sourceId=job.id`, `userId=job.created_by`), duplicate delivery dedupes,
  `retry_count=1` appends a distinct attempt, a throwing ledger cannot fail a
  successful publication, and `mock_social` emits 0 facts.

## 12. Explicit non-goals

Billing, pricing, cost calculation, quotas, credits, usage dashboard/UI, media
search / external embedding usage, `contentImages` direct `media.generate`
accounting, instrumentation of generic transport (`fetch`) or the generic
`PublisherProvider` interface, OAuth/token telemetry, `whoami`/identity metering,
new retry or caching infrastructure, schedule/publication orchestration redesign,
usage vocabulary changes, usage ledger schema changes.
