# R5.2.2 - Canonical document session context

Status: **implemented, awaiting review** (not committed).

Extends the R5.2.1 document-switch barrier into the single shared session
context for the active editing experience. No workspace UI, no route work, no
editor redesign.

## Where the canonical boundary lives

- Owner: `apps/web/src/components/content/session/useDocumentSession.ts`. It is
  still the only place that holds document identity and runs the save barrier.
- Distribution: `apps/web/src/components/content/session/documentSessionContext.tsx`
  (`DocumentSessionProvider`, `useDocumentSessionContext`,
  `useRequiredDocumentSession`) plus a small `session/index.ts` barrel.
- The content view (`views/Content.tsx`) owns the session hook and the autosave,
  assembles one `DocumentSessionValue` from them, and provides it around the
  editor workspace. The provider only makes the one authority readable; it does
  not create a second identity.

## Which identity is authoritative

`useDocumentSession` remains the single source of truth. `DocumentIdentity`
(`{ documentId, creating }`) is the only stored identity. The session also
derives `hasDocument` (`creating || documentId !== null`). No consumer keeps its
own document id; there is no second `currentDocumentId` anywhere.

The context value is a read contract, not state:

```
projectId, documentId, isNew, hasDocument, ready, dirty, saveState
requestDocumentSwitch / requestNewDocument / requestCloseDocument
adoptDocumentId / discardDocument
```

`ready`/`dirty`/`saveState` are surfaced from the existing loader
(`workspaceReady`) and autosave (`auto.dirty`, `auto.status`); those stay the
owners, the session only re-exposes them so consumers do not re-derive them.

## Consumers that now derive identity from the session

- `components/content/workspace/EditorWorkspace.tsx` no longer takes a
  prop-drilled `context` object. It reads the session via
  `useRequiredDocumentSession()` and feeds `projectId` / `documentId` / `ready` /
  `dirty` into `EditorContextProvider`.
- Everything below the editor then reads the same authority: `EditorContext`
  snapshot (`contentId`), and through it `EmbeddedAgentEntry` and the in-editor
  agent (they use `useEditorContextSnapshot`).
- `views/Content.tsx` derives `editingId`/`creating` from the session and routes
  `open`/`startNew`/`goList`/`delete` through the lifecycle contract.

## Duplicate identity removed

- `Content.tsx` no longer has `useState` for `editingId`/`creating`; they are
  derived (`session.identity`). (Removed in R5.2.1, kept here.)
- `EditorWorkspace`'s `context={{ projectId, contentId, dirty, ready }}` prop is
  gone; identity is consumed from the session instead of prop-drilled.
- `EditorContextProvider`'s `contentId`/`ready`/`dirty` props are unchanged as a
  low-level API, but are now sourced from the session by its only production
  caller, so there is one path, not two.

## R5.2.1 barrier semantics preserved

Unchanged: `requestDocumentSwitch` / `requestNewDocument` / `requestCloseDocument`
all go through `runBarrier`, which flushes via the reused `useAutosave.flush`,
refuses concurrent switches (`save_in_progress`), and only advances identity on
success. On failure the current identity stays authoritative and the destination
state (error/notice/AI reset/editor key/title) is still applied only in
`Content.tsx`'s `switchTo` `after` callback, i.e. after `switched`.

## Architectural constraint discovered

The provider cannot own the session hook: the autosave (which the barrier
flushes) must be created where the document/metadata state lives, and it depends
on identity/`ready` from that same scope. So the session hook stays the owner in
the content view and the context is a distribution seam. This is the reason
`ready`/`dirty`/`saveState` are surfaced through the session rather than
re-implemented there - one owner, one read contract.
