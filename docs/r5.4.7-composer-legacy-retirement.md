# R5.4.7 - Composer legacy retirement

Status: **delivered**. The unified workspace is now the *only* way to reach
Composer. The retired account `/compose` area and the retired `content`/`compose`
project views redirect to the canonical workspace route; the standalone Composer
surface and its compatibility wrapper are gone. R5.4.3-R5.4.6 behavior is
unchanged.

This milestone is cleanup only. It adds no Composer features, no second router,
no second document id/loader/autosave/history, and no new workspace state
provider.

## 1. Reconnaissance findings

1. **Canonical route.** `/p/:projectId/workspace/:mode` (mode `editor | composer
   | designer`) mounted by `ProjectWorkspaceShell`; `Composer` is a mode, entered
   via `WorkspaceModeSwitcher` -> `onModeChange`.
2. **Account `/compose` area.** `App.tsx` rendered the standalone `Compose` for
   the user's first project (`composeProject = me.projects[0]`), with its own
   page header and an `onOpenEditor` hand-off to the workspace editor.
3. **Project `compose` view.** `view === 'compose'` ran the shell in composer
   mode. Project `content` view ran the shell in editor mode.
4. **`Content.tsx` wrapper.** The R5.3 compatibility shell that predated direct
   workspace routing. A repository-wide search found **no importers** (only two
   historical doc comments referenced it), so it was orphaned dead code.
5. **Chrome duplication.** Because the shell is the single chrome layer (R5.4.6),
   the standalone Composer's `PageHeader` and its `showHeader` escape hatch only
   existed to keep that legacy surface working.
6. **No duplicate implementations.** There was exactly one `Compose`
   implementation, but it was mounted from two places (shell + account area), so
   the retirement is a routing change, not a refactor of Composer internals.

## 2. Route classification

Each legacy entry point was classified explicitly; none is retained "because it
was convenient".

| Entry | Before | Decision | After |
| --- | --- | --- | --- |
| `/p/:id/workspace/:mode` | shell | **keep** | canonical, unchanged |
| `/p/:id/compose` | shell composer mode | **remove render, redirect** | `replaceState` -> `/p/:id/workspace/composer` |
| `/p/:id/content[/:docId]` | shell editor mode | **remove render, redirect** | `replaceState` -> `/p/:id/workspace/editor[/:docId]` |
| `/p/:id/designer` | shell designer mode | **keep** | R5.5 owns its retirement |
| `/compose` (account area) | standalone `Compose` | **remove render, redirect** | `replaceState` -> first project's `/p/:id/workspace/composer` |
| `views/Content.tsx` | unused wrapper | **remove** | deleted |

`TopArea` still includes `'compose'` on purpose: `parseRoute` must recognize
`/compose` so the redirect effect can fire. It is no longer in `TOP_NAV`, so no
in-app link produces it.

## 3. Redirect semantics

- The mapping is a pure function,
  `canonicalWorkspaceRoute(route)` in `lib/projectRoute.ts`, unit-tested for both
  retired project views and for the canonical/designer/account routes it must
  leave alone.
- `App.tsx` runs one effect that computes the target (the account area resolves
  to `me.projects[0]`; project views resolve via the helper) and uses
  `window.history.replaceState` + `setRoute`. `replaceState` means the back
  button does not bounce between the legacy and canonical URL.
- Redirects are deterministic and preserve context: the document id survives
  `content -> editor`, and the canonical target is always the workspace route.
  There is **no duplicate Composer rendering**: `App` no longer imports
  `Compose`; the only mount site is `ComposerMode` inside the shell.
- While the effect runs, the retired route renders a one-frame placeholder
  ("Opening the workspace...") rather than the old surface.

## 4. Removed compatibility code

- Deleted `apps/web/src/views/Content.tsx` (no importers).
- Removed the standalone `Compose` render branch and its `composeProject`
  resolution in `App.tsx`.
- Removed `Compose`'s `showHeader` prop, its `PageHeader`, and the unused
  `PageHeader` import. The shell's shared document header is the only top layer;
  `ComposerMode` no longer passes `showHeader={false}`.
- Removed the `Compose` entry from `TOP_NAV` and the now-unused `Sparkles`
  import.

`designer` was left untouched: it still parses, still renders, and is
intentionally outside R5.4.7 (R5.5).

## 5. What did not change

- No new router: the hand-rolled history model is unchanged.
- No new document id, loader, autosave, history or Composer context: Composer
  still reads the shared `WorkspaceSessionValue` and produces proposal data
  (`CanonicalDocument` / `CompositionOperationBatch`) that reaches the unified
  document only through `CompositionApplyBridge`.
- R5.4.3-R5.4.6 flows (apply/append, review dialog, stale-boundary guard,
  workspace chrome, review navigation hold) are untouched.

## 6. Tests / verification

- New `projectRoute.test.ts` cases (2 added): retired project views map to the
  canonical workspace route with context preserved; canonical, `designer` and
  account routes are left unchanged. Total file tests: 8.
- `Compose.test.tsx`: the former `showHeader={false}` test now asserts Composer
  renders no page header at all (the shell owns chrome) — 23 tests.
- Remaining web suites green, including the shell chrome/isolation/composerNav
  tests and `ComposerMode.{test,handoff}`.

## 7. Remaining gaps

- Browser history (`popstate`) can still change workspace mode without the
  switcher, bypassing the R5.4.6 review hold. Retirement did not expose a new
  concrete bug here, so no fix was applied (recorded hardening item).
- Designer still renders its own header and has its own route; converging it is
  R5.5.
- Preview remains an editor pane toggle, not a workspace mode.
