# R5.10.7 - Media and embeddings usage instrumentation

Delivered behavior for recording external embeddings requests and external media
(search/generation) requests in the R5.10.2 append-only usage ledger. The
repository analysis this builds on is
`docs/r5.10.7-media-embeddings-usage-recon.md`; this document records the
delivered design and decisions, not the call-graph discovery.

Contract: `packages/contracts/src/usageEvent.ts` (R5.10.1). Ledger:
`supabase/migrations/20260101000031_usage_events.sql` (R5.10.2). No migration,
vocabulary change or ledger schema change is required or made: category `ai` /
`media` and units `input_token` / `request` / `image_generation` already existed
(R5.10.1/R5.10.3).

## 1. Two accounted paths

Only two paths are instrumented in this slice:

| Path | Category | Operation | Unit | Counted physical request |
| --- | --- | --- | --- | --- |
| External embeddings | `ai` | `embed` | `input_token` | one `POST /embeddings` |
| Media search | `media` | `media_search` | `request` | one `GET api.unsplash.com/search/photos` |
| Media generation | `media` | `image_generate` | `image_generation` | one `POST /images/generations` |

Not counted: Qdrant operations, chunking/normalization/local preprocessing,
lexical retrieval, RRF/rerank, caching, CDN downloads, local media persistence,
image metadata/provenance handling, Jina fetch.

## 2. Embeddings seam

`OpenAiCompatibleEmbedder.embed` (`providers/knowledge/embedding.ts`) is the only
production embeddings path. It splits its input into batches of 8 and issues one
`POST /embeddings` per batch. The seam is the **physical request**, so a 20-text
embed records 3 facts, never 1 summed fact.

The provider response's authoritative `usage.prompt_tokens` is the quantity. It
was previously discarded; it is now captured and handed to an optional observer
once per batch, after the provider has answered and before the vector-count
validation (the request was really issued and really consumed tokens):

```text
KnowledgeProvider.index -> embedder.embed(chunks, observer)   (per document)
KnowledgeProvider.search -> embedder.embed([query], observer)
opportunityTopicService -> embedder.embed(texts, observer)
                                  -> one observation per POST /embeddings
                                      -> usageEvents.append()   (best-effort)
```

No token count is ever estimated. A response with no positive
`usage.prompt_tokens`, or an HTTP/transport failure that happens before a token
count exists, records nothing for tokens.

Scope is threaded from the callers, never looked up globally:

- `QdrantKnowledgeProvider.index(ctx, ...)` builds the observer from the
  `ProviderContext` usage (job id as `sourceId`, `userId = job.created_by`).
- `QdrantKnowledgeProvider.search(opts)` builds it from `opts.usage`
  (`sourceId`/`occurrence` from `KnowledgeSearchOptions.usage`, `userId` null on
  the read path).
- `KnowledgeService.search` builds a read-path scope
  (`usageScopeContext({ sink, sourceId: null })`) and threads it through the
  retrieval pipeline (`knowledge/retrieval/pipeline.ts` + `vector.ts`).
- `opportunityTopicService.getTopicRecommendations` builds the same read-path
  scope for its relevance batch.
- Knowledge `ingest`/`refresh` executors thread the job usage context into
  `KnowledgeService.ingestSource`/`refreshSource`, which pass it into the
  provider context.

`ProjectEmbedder` (`services/embeddingService.ts`) is retained but not
instrumented: it has no production caller.

## 3. Media seam

The seam is the concrete **provider method**, not a generic `fetch` wrapper and
not the `MediaProvider` interface's callers:

```text
imageInsertionService / content_images job
    -> MediaProvider.search | generate
        -> UnsplashMediaProvider.search     <- media_search seam
        -> OpenAiMediaProvider.generate     <- image_generate seam
            -> fetch(remote)
                -> usageEvents.append()     (best-effort)
```

Instrumenting the two concrete methods means one implementation covers every
caller (the image insertion service and the `content_images` job) with no
per-caller duplication, and a provider that performs no external request cannot
produce media usage. The CDN download of an already-returned URL
(`externalImageAcquisition.ts`, `imageGenerationAcquisition.ts`) and local
persistence are not provider methods and are not counted.

`contentImages` may fan out up to the configured cap (default 4, max 6) searches
and/or generations; every physical request is its own fact and they are never
collapsed into one.

## 4. Migration of the existing generation meter

Before this slice, `acquireGeneratedImage` recorded the `media/image_generate`
fact itself. That meter was removed: the fact is now owned by
`OpenAiMediaProvider.generate`, the single place that actually issues the
external request. The service continues to pass a `MediaUsageScope` down
(`generate({ ..., usage })`) but never appends, so one physical generation is
exactly one fact regardless of caller - there is no double count. A download or
local persistence failure after a successful generation no longer rewrites the
`success` outcome.

## 5. Observer wiring

Two small best-effort emitters keep provider clients free of scope lookup:

- `providers/knowledge/embeddingUsage.ts`
  - `EmbedUsageObservation = { model, inputTokens, batchSize }`,
    `EmbedUsageObserver = (observation) => void`.
  - `buildEmbeddingUsageEvent` / `emitEmbeddingUsage` /
    `embeddingUsageObserver(ctx, provider?)`.
- `providers/media/mediaUsage.ts`
  - `buildMediaUsageEvent` / `emitMediaUsage` / `mediaUsageUnit`.
  - `MediaUsageScope = { projectId, userId, usage }` is carried on
    `MediaSearchOptions.usage` / `MediaGenerateOptions.usage`.

When there is no usage context the observer is `undefined` and the provider
performs no usage work at all.

## 6. Event shapes

Embeddings (one per physical `POST /embeddings`):

```ts
{
  category: 'ai',
  provider: 'openai',          // the OpenAI-compatible provider identity
  operation: 'embed',
  unit: 'input_token',
  quantity: <provider usage.prompt_tokens>,   // never estimated
  success: true,
  accountId: null,             // mirrored from project by the ledger trigger
  projectId,
  userId,                      // job.created_by on the index path, null on read paths
  sourceId,                    // job id on index, null on read paths
  metadata: { model, batchSize },
  idempotencyKey               // v1|...|sourceId|<occurrence>, null when no sourceId
}
```

Media search / generation:

```ts
{
  category: 'media',
  provider: 'unsplash' | 'openai_media',
  operation: 'media_search' | 'image_generate',
  unit: 'request' | 'image_generation',
  quantity: 1,
  success: boolean,
  accountId: null,
  projectId,
  userId,                      // job.created_by on job paths, else null
  sourceId,                    // job id for job-originated work, else null
  metadata: { model }          // image_generate only
}
```

`buildEmbeddingUsageEvent` / `buildMediaUsageEvent` return `null` (nothing
appended) for a non-UUID `projectId`, an invalid provider token, or (embeddings)
a non-positive token count. A malformed fact is never emitted.

## 7. Failure semantics

- **Embeddings**: HTTP non-2xx or transport rejection -> 0 facts (no token count
  exists and must not be invented). Success -> one fact per batch with the real
  `prompt_tokens`. A malformed body that still reports tokens records the fact
  before the vector-count error is raised.
- **Media search/generation**: a request that was actually attempted records one
  fact; a remote non-2xx, a transport rejection, and an empty generation response
  record `success: false`. A local guard (provider not configured / bad input)
  issues no request and records nothing.

## 8. Retry semantics

The R5.10.6 physical-attempt model is reused through two shared helpers in
`services/usageInstrumentation.ts`:

- `retryOccurrenceBase(retryCount) = retryCount * 1_000_000`.
- `usageScopeContext({ sink, sourceId, occurrenceBase })` - returns `undefined`
  without a sink; otherwise a `ProviderUsageContext` whose per-operation
  occurrence counter is seeded at the base.

A durable job retry that really issues another external request is a new
occurrence and must not deduplicate against the previous execution:

```text
retry_count 0, batch #1 -> key ...|job-1|0
retry_count 1, batch #1 -> key ...|job-1|1000000
```

`sourceId` stays exactly `job.id`. Duplicate delivery of the same execution
re-derives the same keys and dedupes; a real retry advances by the stride. No new
global retry system is introduced.

## 9. Best-effort append

Both emitters reuse `appendUsage` from `services/usageInstrumentation.ts`: a
missing sink or a failed append is logged and swallowed. Usage persistence is
never the transaction boundary of an embeddings or media request - a successful
request still returns its result and a failed one still throws its original
error. The observers are fire-and-forget.

## 10. Idempotency / occurrence

The R5.10.2 ledger mechanism is reused verbatim; there is no application-level
dedup. Keys are derived by `usageEventIdempotencyKey`:

```text
v1|ai|openai|embed|input_token|<sourceId>|<occurrence>
v1|media|<provider>|media_search|request|<sourceId>|<occurrence>
v1|media|<provider>|image_generate|image_generation|<sourceId>|<occurrence>
```

Job-originated work (`knowledge_index`, `knowledge_reindex`,
`knowledge_source_ingest`, `knowledge_source_refresh`, `content_images`) has
`sourceId = job.id` and a retry-aware base, so it dedupes and stays retry-safe.
Read-path work (semantic search, topic relevance) has `sourceId = null`, a null
key, and is honestly non-deduplicatable. No timestamps, random ids or response
hashes are used as identities.

## 11. Test coverage

- `providers/knowledge/embeddingUsage.test.ts` - fact shape/unit/quantity, guards
  (non-UUID project, non-positive tokens), occurrence uniqueness, retry-aware
  base, best-effort append, observer binding, and the physical-batch behavior of
  `OpenAiCompatibleEmbedder.embed` (20 texts -> 3 observations with the real
  per-batch `prompt_tokens`; no usage -> no observation; failing request -> no
  observation).
- `providers/media/mediaUsage.test.ts` - unit mapping, fact shape, guards,
  occurrence uniqueness, retry-aware base, null-`sourceId` behavior, best-effort
  append.
- `providers/media/media.test.ts` - Unsplash: one `media_search`/`request` fact
  per external search, `success=false` on HTTP and transport failure, 0 facts when
  not configured, one occurrence per search. OpenAI: one
  `image_generate`/`image_generation` fact with the applied model,
  `success=false` on HTTP error and empty response, 0 facts when not configured,
  a throwing sink cannot fail generation.
- `jobs/executors.contentImages.usage.test.ts` - the executor meters each
  physical search once, seeds the occurrence base from `job.retry_count` (a retry
  is not deduplicated), and records nothing when the provider is not configured.
- `services/imageGenerationAcquisition.test.ts` - the meter has moved to the
  provider: the service forwards the `MediaUsageScope` into `generate`, never
  appends itself, and generation success is independent of usage-store or
  persistence failure.
- `jobs/executors.knowledge.test.ts` - the refresh executor delegates the usage
  context to `KnowledgeService.refreshSource`.

## 12. Explicit non-goals

Billing, pricing, cost calculation, quotas, credits, usage dashboard/UI; Qdrant
operation accounting, chunking/local preprocessing, lexical retrieval, rerank or
cache metering; CDN download or local media persistence metering; Jina/Cohere
metering; instrumentation of unreachable `ProjectEmbedder`/`AIProvider.embed`;
new retry/caching infrastructure; provider or acquisition behavior changes; usage
vocabulary changes; usage ledger schema changes.
