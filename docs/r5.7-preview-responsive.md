# R5.7 - Preview / Responsive

Status: **implemented.** R5.7 adds a preview/inspection layer to the Unified
Creative Workspace: the current document can be viewed as a rendered page across
desktop/tablet/mobile viewports without leaving the editor or losing the
document session.

Baseline at the start of this step: `0b9a1b7` on `origin/main`, worktree clean.
This record follows the actual repository, not the roadmap wording. It consumes
`docs/r5.6.5-closeout.md` and the R5.2 session/UI-state contracts.

The core invariant:

> Preview changes how the current document is viewed, not what document exists.

---

## 1. Preview architecture

Preview is a rendering surface, not a second editor.

- `PreviewPane`
  (`apps/web/src/components/content/workspace/PreviewPane.tsx`) projects the
  live Tiptap document through the existing bridge
  (`canonicalFromEditorDocument`) and the existing `CanonicalRenderer` - the same
  renderer used by Compose, Designer and the review dialog. There is no
  preview-only document representation.
- The renderer is serialized to static markup
  (`react-dom/server`'s `renderToStaticMarkup`) into a sandboxed `srcdoc`
  iframe. Only the canonical renderer's own stylesheet is injected; the resolved
  Cosmos tokens travel inline on `.cosmos-doc`, so the frame needs no
  application CSS.
- The editor stays mounted and authoritative while preview is shown: the canvas
  is hidden (not unmounted) and the preview renders beside the same session.
- When the document cannot be represented canonically, the pane reports it
  plainly (`preview-fallback`) instead of showing a diverging render. The
  honesty rule applies to previews too.

Why an iframe (Step 8): the canonical renderer owns its responsive behaviour with
**viewport** media queries at 640 / 768 / 1024 px. A width-constrained `<div>`
cannot re-trigger those queries without either duplicating the renderer's
breakpoint rules in the workspace or converting the shared renderer to container
queries (which would change the existing Compose/Designer preview surfaces). An
isolated frame gives a real per-mode viewport, reuses the renderer unchanged, and
satisfies the isolation invariant:

> Preview styling cannot corrupt the workspace UI, and workspace styling cannot
> corrupt the rendered page.

The frame is `sandbox=""`: scripts, forms, popups and top-navigation are blocked;
the document is display-only.

## 2. Preview / document relationship

```text
Document Session
      |
      v
Current Document Revision   (the live Tiptap doc the editor owns)
      |
      v
Rendered Preview            (canonical projection, same revision)
      |
      v
Viewport                    (workspace UI state, not document data)
```

- Preview reads the same `doc` the editor mutates. It never writes.
- No preview state is stored in the document, and no viewport state is part of
  document content.
- Re-rendering the preview never creates a revision, dirties the document,
  triggers autosave, changes identity, increments generation or alters editor
  history.

## 3. Viewport state ownership

- The shell owns the preview viewport with the existing document-scoped
  mechanism: `useDocumentScopedState<PreviewViewport>(DEFAULT_PREVIEW_VIEWPORT)`
  in `ProjectWorkspaceShell.WorkspaceBody`, next to `previewOpen` / `railOpen` /
  `toolsOpen`.
- It is passed down as a controlled value
  (`shell -> EditorMode -> EditorView -> EditorWorkspace -> PreviewPane`). The
  pane reports changes up; it never owns the state.
- Because it is document-scoped, a successful document switch resets the
  viewport to the default and a failed/blocked switch leaves it intact - the
  same boundary semantics as the other workspace toggles. No new state
  architecture and no new reset mechanism were introduced.

## 4. Responsive viewport model

`apps/web/src/components/content/workspace/previewViewport.ts` defines a small,
explicit model derived from the renderer's own breakpoints (640 / 768 / 1024):

| Mode | Width | Band |
| --- | --- | --- |
| desktop | 1280 | `>= 1024` |
| tablet | 834 | `768 - 1023` |
| mobile | 390 | `< 640` |

These are inspection widths, not devices. Adding a mode is a UI-only change; the
document and renderer are unaware of it. The widths are the only new numeric
values introduced, and they are documented here because the repository has no
separate device-token contract.

## 5. Editor <-> preview transition

The preview toggle is the existing header `Preview` / `Editing` button
(shell-owned `previewOpen`).

- Toggling preview hides the canvas and shows `PreviewPane`; it does not remount
  the editor. `EditorWorkspace` keeps the `EditorShell`/`RichTextEditor` subtree
  mounted under a `hidden` wrapper, so the `.ProseMirror` instance and its
  history survive the round trip.
- Opening preview does not reload the document, create a session or reset the
  editor. `ProjectWorkspaceShell.preview.test.tsx` pins this by comparing the
  DOM node identity of `.ProseMirror` before, during and after preview.

## 6. Isolation strategy

- The rendered page lives in an isolated `srcdoc` iframe, so neither side can
  perturb the other's CSS/layout.
- The preview injects only `canonicalRenderer.css`; design tokens are inlined on
  `.cosmos-doc` by the renderer. No workspace CSS is copied into the frame and no
  `:root` application theme is required.
- The canonical renderer's global CSS continues to be scoped under `.cosmos-doc`,
  unchanged.

## 8. Known limitations

- Fonts: the frame loads only the renderer stylesheet, so web fonts resolved
  through application CSS (e.g. Inter) fall back to the token's system stack
  inside the preview. No layout semantics depend on this.
- `react-dom/server` is imported statically, so the server renderer is part of
  the (already single) web bundle. The >500 kB chunk warning predates R5.7;
  code-splitting the preview was intentionally not introduced here.
- Viewport is inspection-only and resets with the document boundary, matching
  the other workspace toggles; it is not persisted as a user preference.

## 9. Handoff to R5.8

- Preview and responsive inspection are in place; R5.8 contextual UI work can
  treat `PreviewPane` as the stable preview surface and `previewViewport` as the
  workspace-owned inspection state.
- No R5.6 regression was found. The session/editor/preview identity guarantees
  from R5.6.5 still hold and are now additionally covered by the preview
  round-trip test.
