# R5.3.3 - Mode dispatch and editor-only infrastructure

Status: **delivered**. Third slice of R5.3 (`docs/phase-5-roadmap.md:86-118`),
following the locked ADR (`docs/r5.1-workspace-decisions.md`). It is a structural
slice: the shell now dispatches exactly one active mode and editor-specific
infrastructure is instantiated only by the editor mode.

## 1. What changed

`ProjectWorkspaceShell` no longer owns the editor. It keeps the shared workspace
infrastructure and dispatches exactly one mode from the canonical `:mode`:

```text
ProjectWorkspaceShell
|- shared: one document session (identity, loader, lifecycle, autosave,
|          save barrier), document-scoped workspace state, WorkspaceChrome
`- exactly one active mode
     |- editor   -> EditorMode   -> editor instance, selection/context
     |                              providers, keymap, AI state, assistant entry,
     |                              EditorView
     |- composer -> Compose      (compatibility body, no editor infra)
     `- designer -> Designer     (compatibility body, no editor infra)
```

New `workspace/EditorMode.tsx` is the editor branch. It owns everything that only
the editor needs:

- the live Tiptap editor instance (`useState<Editor>`)
- `EditorSelectionProvider` (single selection owner) and
  `EditorContextProvider`
- the editor keymap (Ctrl/Cmd+S, Ctrl/Cmd+K, Escape)
- editor-specific AI state (`aiConfigured` from `/projects/:id/ai`,
  `assistantBusy` reported up by the editor)
- the document-scoped `assistantOpen` state, the `InlineAssistantSlot` and the
  editor-coupled `EmbeddedAgentEntry`

`WorkspaceChrome` is now shared-only: `DocumentHeader` (title, status, save
indicator, actions) and the save-failure banner. The assistant entry was removed
from it (R5.3.2 had incorrectly placed it with the chrome). The shell still owns
the preview/rail toggles and passes them to `EditorMode`.

## 2. Why the infrastructure is editor-only

- Recon confirmed neither `Compose.tsx` nor `Designer.tsx` reads editor infra:
  no `RichTextEditor`, `EditorContext`, `EditorSelection`, `.ProseMirror` or
  Tiptap reference exists in either body. They are still compatibility bodies
  that do not read the shared document.
- The assistant entry needs `useEditorContext`/`useEditorSelection`, so it cannot
  render in Composer/Designer. Keeping it in `WorkspaceChrome` would have mounted
  editor context even when the mode was not the editor.
- Mounting a Tiptap instance, the selection owner, the editor keymap and a
  project AI request for Composer/Designer is wasted work and a second source of
  editor state. `EditorMode` scopes all of it to the editor branch.

## 3. Ownership preserved (no new state)

- One document session, boundary, lifecycle, autosave and save barrier: still
  `useWorkspaceSession` in the shell, read by the mode through
  `useWorkspaceSessionContext`.
- One editor instance and one copy of each editor provider: created inside
  `EditorMode`, which unmounts with the mode, so there is never a second editor.
- One selection owner and one editor keymap: registered only while the editor
  mode is mounted and owns a ready document.
- Assistant ownership unchanged: `assistantOpen` stays document-scoped
  (`useDocumentScopedState`), and `useEmbeddedAgent` still owns the interaction.
- `documentScopeKey`, `editorHistoryKey` and the session `boundary`/generation
  semantics are untouched.

## 4. Mode dispatch

- `normalizeWorkspaceMode(mode)` maps any input to `editor | composer | designer`
  (default `editor`).
- The body renders exactly one of `EditorMode`, `Compose`, `Designer`; there is
  no overlapping mount.
- A Compose draft still opens the editor without a route change: Compose calls
  `onOpenEditor(contentId)`, the shell records `composedDraftId` and switches to
  the editor mode, and the id is passed to `EditorMode` as `initialContentId`.
- The shared `WorkspaceChrome` renders only when the editor mode owns a ready,
  editable document; Composer/Designer keep their own legacy headers until
  R5.4/R5.5 converge them onto the shared document.

## 5. Non-goals (unchanged)

No Composer/Designer implementation, no route or route-model change, no
mode-switcher redesign, no editor redesign, no assistant redesign, no
autosave/session redesign, no workspace-state redesign, no beforeunload handling,
and no database or migration work. G3 (browser-exit / route-unmount protection)
remains deferred to a later slice.

## 6. Tests

- `workspace/ProjectWorkspaceShell.isolation.test.tsx` (new): the editor mode
  renders `EditorView` and mounts the editor infrastructure (`.ProseMirror`,
  `EditorContextProvider`, `EditorSelectionProvider`); Composer/Designer mount no
  editor infrastructure and never request `/projects/:id/ai`; the editor keymap
  is not registered for Composer/Designer; switching editor -> composer removes
  the infrastructure without mounting another provider; composer -> designer and
  designer -> editor behave as expected.
- `workspace/WorkspaceChrome.test.tsx`: updated - the chrome renders no assistant
  entry; header/save indicator/save-failure behaviour unchanged.
- `workspace/ProjectWorkspaceShell.chrome.test.tsx`,
  `workspace/ProjectWorkspaceShell.test.tsx`,
  `components/content/workspace/EditorWorkspace.test.tsx`: unchanged and green,
  still covering the shared header/save indicator/assistant in editor mode and
  the chrome-less canvas.
