# R5.11.5 - Publishing / Composer Defensive Cleanup (H7+H8+H9)

Slice H7+H8+H9 of the R5.11 hardening plan (`docs/r5.11-hardening-recon.md`,
sections B/E.5). Three small defensive fixes in the publishing executor and the
Composer handoff; none closed a reachable defect, each removed a latent hazard
or a misleading expression.

## H7 - project-scoped publication updates in the executor

The publish executor read the publication with a project filter, then updated it
by id alone. No IDOR was reachable (the preceding read is project-scoped), but
the update itself was not boundary-filtered. All four publication updates in
`apps/api/src/jobs/executors.ts` now also filter by `job.project_id`:
the delete completion, the update completion, the already-created repair, and
the create completion. Defense in depth, consistent with the rest of the
project-scoped data access.

## H8 - no-op status ternary in the action route

`publications.ts` set the row's status with
`body.action === 'delete' ? 'queued' : 'queued'` - both branches identical, a
misleading expression whose intent was lost. `queued` is in fact the pending
state for both publish and delete (the status check constraint has no
delete-in-progress value), so the ternary is replaced by a plain `'queued'` with
a one-line why-comment, and the update now also filters by `project_id`.

## H9 - a stale Composer handoff is reported

When "Open in Editor" created a draft but the workspace boundary had moved while
the create was in flight, `Compose.openInEditor` returned silently: the draft
was persisted but the user was neither taken to it nor told. Now:

- `Compose` sets a local notice ("The draft was created but not opened because
  the workspace changed. It is saved in your content list.") rendered next to
  the create error, and calls a new optional `onHandoffStale` callback.
- `ComposerMode` supplies `onHandoffStale`, bumping the workspace `refresh`
  counter so the content list is refetched and the orphaned draft is
  discoverable.
- The draft is never deleted server-side, and the `createdIdRef` duplicate
  guard is untouched (a stale result does not set it, so a later retry is a
  fresh create).

## Tests

- `apps/web/src/views/Compose.test.tsx`: the stale-boundary handoff test now
  also asserts `onHandoffStale` is called once and the created-but-unopened
  notice is rendered; it still asserts no handoff.
- `apps/web/src/workspace/ComposerMode.handoff.test.tsx` (+1): `onHandoffStale`
  invokes the workspace `setRefresh`, so the content list is reloaded when a
  handoff is abandoned.
- API publish suites (`executors.publish.test.ts`, `publications.test.ts`)
  pass unchanged with the added `project_id` filters.
