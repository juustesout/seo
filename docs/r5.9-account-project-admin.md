# R5.9 - Account / Project Admin

R5.9 connects the Unified Creative Workspace to the account and project
administration model that already exists in the repository. It is an
integration/ownership/navigation phase: it does not add an account system, a
project system, a permission system or a second unsaved-change mechanism.

The core invariant:

> The workspace consumes account/project identity. It does not own or duplicate it.

## 1. Account / project ownership model

The repository already has one authoritative hierarchy:

```text
seo_accounts
  |  (seo_ensure_account: one user = one account)
  seo_projects
  |  (seo_project_members: user_id + project_id + role)
  seo_content  (and every other seo_* project-scoped table)
```

- An account is resolved from the caller, never from a URL parameter
  (`AccessService.requireAccount(userId)` -> `seo_ensure_account`). One user maps
  to one account today; there is no account switcher in the UI.
- A project is reached through membership. `AccessService.requireRole(userId,
  projectId, minRole)` reads the caller's role from `seo_project_members` and is
  the single project authorization implementation shared by REST, the worker and
  MCP.
- A document (`seo_content`) is a project-scoped row. Its session (identity,
  loader, lifecycle, autosave, editor history, selection, preview viewport) is
  owned by the workspace shell below the project it belongs to.

Recon note: no `/api/accounts/:id` or `/api/projects` CRUD surface is the
workspace's entry point. The workspace is mounted at `/p/:projectId/...` and
gets its `projectId` and `role` from `App.tsx`, which derives both from `/me`.

## 2. Canonical project identity

`GET /api/me` is the only project identity source for the web app. It returns
`{ user_id, email, projects[] }`, where each project carries `id`, `name`,
`role`, `website_url`, and aggregate counts (`member_count`, `domain_count`,
`integration_count`, `connected_count`, `job_count`, `last_sync_at`).

`App.tsx` resolves the active project by matching `route.projectId` against
`me.projects`. Only known memberships render; an unknown id renders the "Project
not found" screen. The canonical id (`project.id`) is what is passed to every
project view, including `ProjectWorkspaceShell`.

The workspace does not mint, store or re-derive a project id. `workspaceSession`
receives `projectId` as a prop; `WorkspaceStateProvider` keys document-scoped UI
state by the document boundary, not by the project. R5.9 adds a read-only
`WorkspaceProjectInfo` (name, website, integration counts) that is passed down
from `me.projects`, so the header shows canonical metadata without a second
fetch.

## 3. Workspace / project relationship

```text
App (route + /me)
  ProjectWorkspaceShell projectId role project
    WorkspaceSessionProvider                    (one document session)
      DocumentSessionProvider                   (identity + save barrier)
        WorkspaceStateProvider documentKey      (document-scoped UI state)
          WorkspaceChrome + active mode body
```

`ProjectWorkspaceShell` is a thin, project-keyed wrapper:

```tsx
export function ProjectWorkspaceShell(props) {
  return <ProjectWorkspaceSession key={props.projectId} {...props} />;
}
```

Keying the session subtree by the canonical `projectId` means a project change
remounts the session and every document-scoped state below it instead of reusing
them. This is the existing project/session boundary applied at the right level;
it adds no second provider and no "workspace project id".

## 4. Project switching behavior

The project switcher is the `<select>` in the shared `AppHeader`. It calls
`onOpenProject(id, 'dashboard')`, which routes through `App.navigate` and lands
on the new project's dashboard, unmounting the previous workspace.

Two cases are now covered:

1. Route change to another project. `navigate` awaits the navigation barrier
   (section 9) and then pushes the route. Because `key={projectId}` changes, the
   old session unmounts and the new project mounts a fresh one. Project P's
   document, selection, preview, contextual rail and project-scoped UI state
   cannot survive into Project Q.
2. Project id changes while the shell stays mounted (browser back/forward between
   two workspace deep links). The key change forces the same remount, so a stale
   document is never shown under the wrong project.

An explicit same-project workspace **mode** change (`/p/:id/workspace/editor` ->
`/p/:id/workspace/composer`) is not a project switch. The shell stays mounted and
shares the session, so `navigate` skips the barrier for it; the document is not
abandoned and no flush is needed.

## 5. Account / project setting boundaries

Established from the actual routes, not assumed:

Account-level (`/api/account*`, derived from the caller):

- account identity (`GET /api/account`)
- Google Search Console connection + property registry (`/api/account`,
  `/api/account/gsc/registry`, `/api/account/gsc/disconnect`)
- account AI / BYOK keys (`/api/account/ai`)
- account API keys (`/api/account/api-keys`)
- account overview / metering (`/api/account/overview`)

Project-level (`/api/projects/:projectId/*`, authorized by `requireRole`):

- project identity / website (from `/me`), GSC property attach
  (`/gsc/state`, `/gsc/attach`, `/gsc/link`)
- project integrations + DataForSEO credentials (`/integrations`)
- project AI status + optional per-project BYOK override (`/ai`; the key write
  is admin-only)
- knowledge sources and Qdrant collection (`/knowledge`)
- media (`/media`), publishers/publications/schedules
- project API keys (`/api-keys`, admin-only)
- Cosmos brand guidance (`/cosmos`)

Important exception: AI/BYOK exists at both levels. The account key is the
primary BYOK surface; the project scope reports the effective status
(`GET /api/projects/:id/ai`) and can hold a project override. The workspace
consumes the project status and never treats the account key as project-scoped.

## 6. Integration ownership

| Integration | Owned by | Workspace view |
| --- | --- | --- |
| Google Search Console | Account connects (OAuth), project attaches a property | Link to project Settings |
| DataForSEO | Project credentials (`/integrations`) | Link to project Integrations |
| AI / BYOK | Account key primary, optional project override | Editor AI status; link to Account -> Integrations |
| Knowledge / Qdrant | Project (own collection per project) | Knowledge rail panels |
| Media | Project | Media rail panel |

No document-level ownership was introduced. GSC and account AI remain
account-scoped; everything else already lives under a project.

## 7. Authorization model

Authorization is server-side and unchanged by R5.9:

- Account routes: `requireAuth` + `AccessService.requireAccount(user.sub)`; the
  account is derived from the caller, never from a request parameter.
- Project routes: `requireAuth` + `AccessService.requireRole(user.sub,
  projectId, minRole)` on every operation (viewer / editor / admin / owner).
- The API uses the Supabase service-role client, which bypasses RLS, so
  `requireRole` is the required defense-in-depth check before any project row is
  read or written. RLS remains the database boundary.
- The web app gates visibility only as UX. Hiding a button is not
  authorization; the server refuses regardless.

R5.9 changed no authorization code and added no permission system. The workspace
receives the caller's `role` from `/me` and uses it only for UI affordances
(`canEdit`, `canDelete`), exactly as before.

## 8. Navigation

The workspace and project administration are two rooms in the same building:

- Shared `AppHeader` (always visible): account areas (Overview, Projects,
  Integrations, API keys), the project switcher, the account email and sign out.
- `ProjectSidebar` (project routes): Dashboard, Keywords, Integrations, Knowledge
  Base, **Workspace**, Calendar, Publications, Publishing, **Settings**. This is
  the existing path from project admin back to the workspace and vice versa.
- `DocumentHeader` (R5.9): a small, read-only project context row showing the
  project name (links to project Settings) and an integrations link with the
  `connected/total` count from `/me` (links to project Integrations). The user
  can see "I am editing Document X in Project Y" and reach administration
  without the header becoming an admin dashboard.

The workspace intentionally does not duplicate the switcher or the per-project
navigation; it reuses the AppHeader and sidebar and only adds two links.

## 9. Save-barrier behavior

R5.6 owns one document save barrier (`useDocumentSession`) whose flush is the
live `useAutosave`. Document switches already cross it. R5.9 makes **route**
navigation cross the same barrier:

- `apps/web/src/lib/navigationBarrier.ts` holds one registered barrier.
- `useWorkspaceSession` registers `() => flush()` while mounted and clears it on
  unmount; on unmount it also fires one final flush, so navigation that cannot be
  intercepted (browser back/forward, window close) still attempts to save a dirty
  document.
- `App.navigate` and `lib/nav.openProjectView` await the barrier before pushing a
  route. If the barrier refuses (the save failed), the navigation is dropped and
  the workspace stays mounted and authoritative; its existing save-failure banner
  is shown and the user can retry.
- `navigate` skips the barrier only for a same-project workspace mode change
  (the session stays mounted) and while another navigation is in flight.

This is not a second unsaved-change mechanism: it exposes the existing autosave
to navigation and owns no document state.

## 10. State isolation

Isolation is guaranteed by remounting the session subtree on the canonical
project id, which resets:

- document identity, loader, lifecycle and autosave (`useDocumentSession`,
  `useDocumentLoad`, `useAutosave`)
- the document boundary, and therefore `WorkspaceStateProvider` UI state
  (preview, rail, tools, preview viewport)
- editor history and selection, which are keyed by the same boundary

Project-scoped data (content list, integrations, knowledge, media) is fetched
per project by each view and never carried across the remount.

## 12. Known limitations

- Account switching is not supported in the UI. One user is one account; a
  different account requires a different signed-in user and a full rebootstrap.
- Browser back/forward cannot be pre-blocked by the navigation barrier, so it
  falls back to the unmount flush (fire-and-forget). A failed save there is not
  retried automatically.
- `WorkspaceProjectInfo` reflects the `/me` snapshot (name, website, integration
  counts). It refreshes when `/me` reloads; it is not a live integration status
  feed. Per-integration status stays on the canonical Integrations/Settings
  surfaces.
- The `integration_count`/`connected_count` are coarse `seo_integrations` row
  counts; they are presented as a link label, not as a per-provider health
  indicator.
- Migration `supabase/migrations/20260101000030_media_provenance.sql` remains
  runtime-unverified from earlier phases (unchanged here).

## 13. Handoff to R5.10

The ownership chain Account -> Project -> Workspace -> Document is explicit and
enforced by one key (`projectId`) and one session boundary. R5.10 can build on:

- `navigationBarrier` as the single hook for any future route transition that
  must respect document state.
- `WorkspaceProjectInfo` as the read-only project context contract; extend it
  rather than fetching project metadata in the workspace.
- The existing `requireRole`/`requireAccount` service for any new admin
  capability. Do not add UI-visible-but-unauthorized operations.

Success criterion met: the workspace consumes account/project identity, project
switching cannot retain the previous project's document or state, and the user
can move naturally between creative work and project administration.
