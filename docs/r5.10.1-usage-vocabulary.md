# R5.10.1 - Usage Event Vocabulary

R5.10 introduces an append-only usage ledger. R5.10.1 is the contract-only
slice: it defines the canonical vocabulary that ledger will store. It adds no
migration, no persistence, no provider instrumentation, no API surface, no UI,
and no pricing/billing/credit/quota logic.

The contract lives in `packages/contracts/src/usageEvent.ts` and is re-exported
from the `@seo/contracts` barrel.

## 1. Why usage events exist

The platform consumes external resources - AI tokens, DataForSEO tasks and
SERPs, GSC requests, publish attempts, media acquisitions, worker executions -
across many providers and code paths. Each of those paths already keeps its own
domain record. What does not exist is one provider-neutral, machine-readable
*fact* stream that says "this measurable resource was consumed" in a single
vocabulary.

The usage ledger is that stream. Its value is that new providers and new
operations can be accounted for without a new table, a new billing concept or a
new query language: they emit events in the shared vocabulary.

## 2. Domain record vs usage fact

The distinction is the core invariant of the slice:

```text
domain record = what happened to the application object
usage event   = what externally measurable resource was consumed
```

A usage event is an **evidence projection**, never a replacement or a
duplicate. Existing records stay authoritative:

| Domain record | Authoritative for | Usage event adds |
| --- | --- | --- |
| `seo_sync_jobs` (`JobRecord`) | job lifecycle, retry budget, outcome | "one job execution happened" |
| `seo_publications` | one publish/update/delete attempt, status, remote id | "one publish attempt was made" |
| `seo_media` + `source_meta` | asset identity, provenance, reuse | "one image generation / stock request / asset was acquired" |
| AI provider `usage` (`AIChatResult.usage`) | per-call token counts | normalized `input_token` / `output_token` facts |
| DataForSEO task ids | endpoint/task/keyword specifics | normalized request/task/keyword facts |
| `seo_accounts` / `seo_projects` | ownership and scope | the scope the consumption is attributed to |

A domain record is mutable (a job transitions `queued -> running -> completed`;
a publication transitions status). A usage event is immutable and append-only:
it describes one already-observed consumption.

## 3. Categories

Closed vocabulary for the first version (`USAGE_CATEGORIES`):

```text
ai
dataforseo
job
publishing
media
```

`dataforseo` is the platform's external SEO data-API category. The first
external data providers are DataForSEO (`provider = dataforseo`) and Google
Search Console (`provider = gsc`, `unit = gsc_request`). No speculative
categories were added; a category is only added by an explicit, reviewed
change.

## 4. Units

Closed vocabulary for the first version (`USAGE_UNITS`):

```text
request
task
keyword
serp_request
gsc_request
input_token
output_token
image_generation
asset
publish_attempt
job
```

The rule is that `quantity + unit` must be unambiguous. Input and output tokens
are separate units, so `1200 input tokens` is never flattened into a generic
`"tokens"`. A SERP request is distinct from a generic request. Duration is
deliberately not a unit: `durationMs` is evidence, not cost.

## 5. Provider and operation semantics

`provider` is an open string identifying the external/internal resource
provider. Reuse the existing `PROVIDER_IDS` tokens where they apply (`openai`,
`dataforseo`, `gsc`, `wordpress`, `unsplash`, `openai_media`) so the vocabulary
stays aligned with provider registration.

`operation` is an open string identifying the actual operation (`chat`,
`generate`, `embed`, `serp_live`, `serp_task`, `keyword_research`,
`competitor_discovery`, `keyword_gap`, `publish`, `media_search`,
`image_generate`, ...). It is intentionally not a global enum: operation names
are provider-specific and must be free to grow without a contracts change.
Both fields are validated as bounded lowercase tokens (`^[a-z0-9_]+$`).

## 6. AI token semantics

AI usage is represented with category `ai` and distinct token units, so partial
provider usage is representable (some providers expose only input tokens):

```text
AI chat input:
category = ai
provider = openai
operation = chat
unit = input_token
quantity = 1200

AI chat output:
category = ai
provider = openai
operation = chat
unit = output_token
quantity = 350

AI embedding:
category = ai
provider = openai
operation = embed
unit = input_token
quantity = 800
```

No token cost or price is stored. A provider that exposes only input tokens
simply emits only an `input_token` event.

## 7. DataForSEO semantics

Data category events cover endpoint/request usage, task usage, keyword-volume
usage, SERP request usage and GSC request usage. The vocabulary does not model
DataForSEO's vendor billing formula; provider-specific detail goes in
`metadata`.

```text
DataForSEO live SERP:
category = dataforseo
provider = dataforseo
operation = serp_live
unit = serp_request
quantity = 1

DataForSEO keyword volume (50 keywords):
category = dataforseo
provider = dataforseo
operation = keyword_research
unit = keyword
quantity = 50
metadata = { "keywordCount": 50 }

GSC request:
category = dataforseo
provider = gsc
operation = gsc_sync
unit = gsc_request
quantity = 25
```

## 8. Failed-operation semantics

`success` describes whether the measured operation completed. Failed external
attempts are still meaningful usage facts and must remain representable:

```text
category = publishing
provider = wordpress
operation = publish
unit = publish_attempt
quantity = 1
success = false
```

`quantity` may be `0` when a failed attempt consumed nothing measurable. A
failed event is never silently discarded. Retries must not produce duplicate
events unless the underlying external attempt actually occurred again; the
semantics are defined here, instrumentation belongs to a later slice.

## 9. Account / project scope

`accountId`, `projectId` and `userId` are the canonical identifiers:
`seo_accounts.id`, `seo_projects.id` and `auth.users.id`. Any of the three may
be `null` when the operation genuinely has no such scope - worker/background
work has no acting user, and some consumption (for example a shared
account-level credential check) has no project. Account ids are never derived
from project ids; the existing hierarchy stays authoritative.

## 10. Metadata rules

`metadata` is contextual evidence, not an escape hatch for core semantics.
Recommended keys include `model`, `jobId`, `taskCount`, `keywordCount`,
`durationMs`, `retryCount`. Rules:

- It is a plain JSON object (`Record<string, unknown>`), validated as such.
- Primary semantics (`category`, `provider`, `operation`, `quantity`, `unit`,
  `success`, scope) must never be encoded only in metadata.
- It must never contain secrets, API keys, credentials, or prompts containing
  credentials.
- It must stay bounded and secret-free - provenance `source_meta` is the
  precedent for the same rule.

## 11. Correlation / idempotency decision

The contract adds one correlation field:

```text
sourceId: string | null
```

`sourceId` points back to the originating domain record or provider attempt
(job id, publication id, media id, DataForSEO task id, AI call id, ...). Its
purpose is traceability, debugging, and de-duplication for the R5.10.2 ledger.
R5.10.2 can derive a deterministic idempotency key from stable event identity -
for example `(accountId, projectId, category, provider, operation, unit,
sourceId)` - rather than storing an extra key on every event.

Decision: no deduplication logic is implemented in this slice. `sourceId` is
nullable because not every external attempt has a stable upstream id; when it
is absent, idempotency for that event is a R5.10.2 concern.

## 12. Non-goals

Explicitly out of scope for R5.10.1:

- no subscription plans, credits, wallets, invoices, payment state;
- no quotas, limits or throttles;
- no pricing tables or calculated monetary cost (cost is a future derivation
  from usage facts + pricing rules);
- no database migration, table, RPC or RLS policy;
- no persistence, provider instrumentation or event emission;
- no API endpoints or MCP surface;
- no UI;
- no changes to existing contracts or runtime behavior.

## Representative examples

```ts
// 1. AI chat reaches the token budget (input + output are separate facts).
{
  id: '...', occurredAt: '2026-01-01T00:00:00.000Z',
  accountId: 'acc', projectId: 'proj', userId: 'user',
  category: 'ai', provider: 'openai', operation: 'chat',
  quantity: 1200, unit: 'input_token', success: true,
  sourceId: null, metadata: { model: 'gpt-4o-mini' },
}

// 2. A DataForSEO SERP request.
{
  category: 'dataforseo', provider: 'dataforseo', operation: 'serp_live',
  quantity: 1, unit: 'serp_request', success: true,
  metadata: { location: '2840' },
}

// 3. A worker-run background job (no acting user).
{
  category: 'job', provider: 'dataforseo', operation: 'keyword_research',
  userId: null, quantity: 1, unit: 'job', success: true,
  sourceId: '<seo_sync_jobs.id>',
  metadata: { jobId: '<uuid>', durationMs: 1234, retryCount: 0 },
}

// 4. A failed publish attempt is still a usage fact.
{
  category: 'publishing', provider: 'wordpress', operation: 'publish',
  quantity: 1, unit: 'publish_attempt', success: false,
  sourceId: '<seo_publications.id>', metadata: { http_status: 502 },
}

// 5. An image generation.
{
  category: 'media', provider: 'openai_media', operation: 'image_generate',
  quantity: 1, unit: 'image_generation', success: true,
  sourceId: '<seo_media.id>', metadata: { model: 'gpt-image-1' },
}
```
