# R5.11.2 - H3 Publishing Idempotency

Slice H3 of the R5.11 hardening plan (`docs/r5.11-hardening-recon.md`,
section E.2). The defect: a "Publish" action was not idempotent, so a duplicate
click, a concurrent request or an at-least-once worker retry could create two
remote posts on WordPress/X. This slice makes one logical publish operation
resolve to at most one durable job and one remote create, without redesigning
publishing, adding a second idempotency store or changing usage semantics.

## Logical publication identity

Identity is taken from the existing publishing model, not invented:

- **Lifecycle action** (publish/update/delete of an existing publication row):
  the publication row is the logical operation, e.g.
  `publish:action:update:<publicationId>`.
- **Direct composer create**: the publish intent is the logical operation - the
  publication target plus a SHA-256 fingerprint of the payload snapshot
  (`content_id`, `title`, `slug`, `content`, `excerpt`, `scheduled_for`). Two
  identical submissions therefore share an identity while a changed or new
  document is a genuinely new operation.

Each identity is suffixed with an **attempt generation** (the number of jobs
already recorded for that identity). A terminal (`failed`/`completed`) operation
can therefore be deliberately re-run instead of being blocked forever by the
unique key. Scheduled publishing keeps its existing schedule-bound key
(`schedule:<scheduleId>:publish`, `scheduleService.ts:62`) and is untouched.

## Existing idempotency mechanism reused

No schema change. The slice uses the `seo_sync_jobs.idempotency_key` unique
constraint (`20260101000005_jobs_publishing.sql:37`) as the persistent boundary,
which `JobStore.enqueue` already accepts (`jobs/types.ts:42`,
`supabaseJobStore.ts:80`) and which the PostgREST store surfaces as a 409
conflict. The new `publicationJobs.ts` service derives the key and performs the
reuse/conflict recovery; both route enqueue sites depend on it.

## Duplicate / concurrent behaviour

- **Repeat before completion**: `enqueuePublicationJob` reads the durable job
  table for the identity and reuses a still `queued`/`running` job. Because the
  check reads Postgres (not process memory), it holds across tabs, API instances
  and worker restarts.
- **Concurrent duplicate**: two requests that both miss the reuse check race on
  the unique key; the loser re-reads and reuses the winner. A direct-create
  follower that already inserted a publication row is recorded honestly as
  `failed` with a "collapsed" message rather than left stuck `queued`.
- **Later deliberate publish**: once an operation is terminal, the next
  submission gets a fresh generation key, so a changed document (or a retry of a
  failed one) is a new operation.
- **Lifecycle gates**: `publish` on a row that already has a `remote_id` and
  `delete` on an already-`deleted` row are refused with 409 at the route edge.
  The Publishing view disables the Publish button for any row that is not
  `failed`. The API is the enforcement point; the UI is feedback.

## Worker retry behaviour

The `publish` executor short-circuits on a confirmed remote id: when a retry,
stale-running re-queue or re-enqueued duplicate finds `remote_id` set, it does
not call the adapter again, repairs the row status to `published` if needed and
returns the existing result. `publish_delete` short-circuits when the row is
already `deleted`. A retry whose previous attempt failed *before* a remote id
was persisted still calls the adapter - that is a legitimate physical retry.
`publish_update` is left to run: an update against the same remote id is
idempotent at the remote and re-issuing it is a real physical attempt.

## Provider failure-window behaviour (no exactly-once claim)

The window where the provider creates the remote post but the process dies
before `remote_id` is persisted is **not** closed: the next attempt sees no id
and issues a second create. WordPress and X expose no client-supplied
idempotency key, so exactly-once cannot be guaranteed without inventing a
provider-specific remote API. The executor documents this explicitly; the slice
claims "at most one remote create per confirmed-local-state publication", not
exactly-once.

## Usage metering compatibility

R5.10.6 semantics are preserved unchanged. The usage observer stays on the
provider-specific client method and the occurrence base still advances per
`retry_count`. A prevented duplicate never reaches the adapter, so it produces
no `publish_attempt` fact. A real retry that reaches the adapter still produces
its own `publish_attempt`, and the terminal `job` fact (R5.10.4) remains keyed by
`job.id` so worker retries of one logical job do not multiply it. No vocabulary
was changed and the observer was not moved.

## Scheduling

`ScheduleService` still enqueues exactly one `publish` job per schedule with the
`schedule:<scheduleId>:publish` key and mutates that job on reschedule; the
scheduled identity is unchanged and its existing test (`scheduleService.test.ts`)
still passes. The direct composer's `schedule_for` path now carries the same
deterministic key + `run_after` as before.

(`scheduleService.test.ts:258,286`), the publish happy paths and the R5.10.6
physical-attempt accounting.
