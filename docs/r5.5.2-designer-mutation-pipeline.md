# R5.5.2 - Designer proposal -> shared mutation pipeline

Status: **delivered**. A Designer proposal is no longer written through the
legacy whole-document server route. The shell now classifies a reviewed proposal,
stages the representable forms and applies them through the **same** editor
mutation pipeline the unified workspace already uses
(`applyDocumentOperations` / `applyImageInsertion`). No second Designer mutation
architecture was introduced.

This milestone is integration only. It adds no new router, document id, loader,
autosave, history, context or workspace-state provider, and no new provider,
contract, migration or agent/planner change.

## 1. Reconnaissance findings (R5.5.0, confirmed in code)

1. **Two mutation mouths.** The workspace had exactly two external mutation
   entry points in `EditorContext`: `applyExternalDocument` (whole-document
   replacement) and `applyDocumentOperations` (operation batch), plus the R3.1
   `applyImageInsertion`. The Composer already used them through
   `CompositionApplyBridge`.
2. **Designer was out-of-band.** `views/Designer.tsx` called
   `POST /content/:contentId/designer/apply`, a server-side whole-document
   `ContentService.update`. It could overwrite unsaved workspace edits, because
   it reasoned about stored content, not the live editor document.
3. **A proposal is an envelope, not an instruction.** `DesignerProposal` carries
   `document` plus optional `review`, `visual`, `insertion`, `acquisition` and
   `operations` (`DocumentOperationBatch`). Only `operations` and `insertion` are
   already executable by the editor.
4. **Two identity guards are needed.** `session.boundary` pins the open document
   across asynchronous runs, but two empty documents can share a revision, so a
   Designer apply also needs the exact `targetDocumentId`.
5. **Server apply refuses operations/insertion** with
   `422 designer_operations_require_editor`, which confirmed that operations are
   editor-only by design.

## 2. What changed

- **New `apps/web/src/workspace/designerMutation.ts`** - a pure, React/Tiptap-free
  adapter. `planDesignerMutation(proposal)` classifies in order:
  `operations` -> `insertion` -> `acquisition` (`generation_required`) ->
  bare `document` (`canonical_document_only`). `isDesignerMutationRepresentable`
  reports whether a plan can reach the pipeline. `DESIGNER_MUTATION_UNSUPPORTED_COPY`
  holds the shared user copy. A canonical-document-only proposal is **never**
  silently turned into a whole-document replace.
- **`CompositionApplyBridge.tsx` generalized** to a single staged-mutation bridge:
  - `PendingComposition` now carries `mode: 'replace' | 'operations' | 'insertion'`
    and `origin: 'composer' | 'designer'` (plus optional `targetDocumentId`);
  - `pendingDesignerMutation(proposal, mode, boundary, targetDocumentId)` stages a
    Designer proposal without re-wrapping it;
  - `applyPending` dispatches by `mode` to the existing
    `applyExternalDocument` / `applyDocumentOperations` / `applyImageInsertion`.
    A mode whose proposal lacks that instruction is a `failed` result, never a
    fallback to whole-document replacement;
  - the `boundary` guard and the `targetDocumentId` guard both resolve to
    `stale-document` before any editor write.
- **`ProjectWorkspaceShell.tsx`** adds `applyDesignerProposal(proposal, targetDocumentId)`:
  ordered guards (representable -> open document id matches -> live
  `documentRevisionOf(ws.doc)` equals `proposal.baseRevision`), then
  `setPendingComposition(pendingDesignerMutation(...))` and `onModeChange('editor')`.
  `onCompositionResult` is now origin-aware so Designer notices read "The
  Designer change ...".
- **`DesignerMode.tsx`** forwards `onApplyProposal` and renders the shell `err`
  banner (the Designer, like Composer, renders no shared chrome until R5.5.3).
- **`views/Designer.tsx`** no longer imports `api`/`ApiRequestError` and no longer
  calls the legacy apply route. It derives `mutationPlan`, `representable`,
  `unsupportedReason` and `canApplyNow`, and `apply()` is a synchronous handoff
  via `onApplyProposal(proposal, runContentId)`. `EditReview` shows explicit
  staging/rejected/conflict/unsupported states and hides Apply when the proposal
  is not representable.

## 3. Apply routing matrix (after R5.5.2)

| Proposal form | Plan kind | Applied through | Notes |
| --- | --- | --- | --- |
| `operations` present | `operations` | `applyDocumentOperations` | reused verbatim |
| `insertion` present | `insertion` | `applyImageInsertion` | reused verbatim |
| `acquisition` only | `unsupported` | - | `generation_required`; confirm + re-run |
| `document` only | `unsupported` | - | `canonical_document_only`; review only |
| creation-mode proposal | not staged | - | no document to apply to |

Every representable apply goes through the same revision-guarded editor
transaction, so it reuses the existing autosave/history machinery and starts no
save of its own.

## 4. What did not change

- No new router, document id, loader, autosave, history, context or
  workspace-state provider.
- No new server route, contract, migration or agent/planner change. The legacy
  server `POST /content/:contentId/designer/apply` and `DesignerService.apply`
  remain in place for API/MCP callers but are no longer called by the view.
- `CompositionOperationBatch` stays document-independent; the revision is bound
  only when staging/apply.
- No duplicate rendering: the Designer still composes its view from the existing
  `CanonicalRenderer` and shared session document.

## 6. Known gaps deferred to later R5.5 milestones

- **Shared chrome + review**: Designer still renders its own `PageHeader`; the
  shared chrome and a common review presentation are R5.5.3.
- **Single run controller**: `useDesignerRun` (Designer view) and
  `useEmbeddedAgent` (editor-native) still exist as two clients of the one
  `/designer/runs` endpoint; converging them is R5.5.4.
- **Legacy `/p/:id/designer`** view and the `DesignPackage` decision are R5.5.5.
- **popstate bypasses the review hold** for an in-flight apply; recorded as a
  hardening item, not fixed here.
