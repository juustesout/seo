# R5.4.3.2 - Composer output into the open document

Status: **delivered**. First implementation slice of R5.4.3 (per the R5.4.3.1
recon): a composed page can be applied to the currently open workspace document.
This is a wiring slice - the composed `CanonicalDocument` reaches the editor
through the existing whole-document replacement path. No new proposal, mutation,
or persistence model is introduced.

## 1. Flow

```text
Composer planning/preview              (document-independent, R5.4.1)
        |
        v
 composed CanonicalDocument            (existing composition pipeline)
        |
        v
 shell stages a DesignerProposal       (document + baseRevision + boundary)
        |
        v
 onModeChange('editor')                (composer -> editor, shell stays mounted)
        |
        v
 CompositionApplyBridge (inside the editor context)
        |  boundary check + expectedRevision check
        v
 applyExternalDocument                 (the single editor mutation path)
        |
        v
 one setContent transaction            (undoable, onDocChange + autosave persist)
```

One path, using the existing `DesignerProposal` envelope and the existing
`EditorContext.applyExternalDocument`. No second mutation channel, no
Composer-owned document identity, no `/content` create for this path.

## 2. Why whole-document replacement, and only when empty

The Composer emits a full `CanonicalDocument` with no base document, so it cannot
be expressed as an operation batch against an existing document. The one existing
mechanism that installs a whole document is `applyExternalDocument`, whose server
twin (`DesignerService.apply`) refuses insertion/acquisition/operations and is
`baseRevision`-guarded. That mechanism is safe only when the target carries no
meaningful content: a whole-document replacement must never destroy a document
the user already wrote. R5.4.3.2 therefore replaces the open document **only when
it is empty**; appending into a non-empty document is R5.4.3.3.

The new-document path (R5.4.2) is unaffected: "Open in Editor" still creates a
persisted draft and switches to it. "Apply to current document" is a distinct
affordance for the case where a new/empty document is already open.

## 3. Emptiness predicate

`isCanonicalDocumentEmpty(document)` is added to `@seo/contracts` next to
`canonicalEmptyDoc()`. It returns true only when the document has no blocks, or
only empty paragraph blocks (no children and, at most, blank text). It is
deliberately conservative: any non-paragraph block, nested child, or non-text
inline node makes the document non-empty. This mirrors the shape of
`canonicalEmptyDoc()` / `tiptapEmptyDoc()` rather than guessing at raw editor
state, and it is the shared definition used by both the eligibility check (shell)
and any future caller.

## 4. Staging and the bridge

- `ComposerMode` forwards `onApplyToDocument` / `canApplyToDocument` to
  `Compose`. `Compose` shows an outline "Apply to current document" button,
  disabled unless the open document is an eligible target, with an explanatory
  hint when it is not.
- The shell's `applyComposition(document)` re-checks emptiness against the live
  editor document (not only the memoized eligibility), sets the workspace notice
  and stages `pendingCompositionOf(document, documentRevisionOf(openDoc),
  session.boundary)` as a `DesignerProposal`, then moves to the editor mode. It
  never posts `/content` and never switches documents.
- `EditorMode` renders `CompositionApplyBridge` from the staged pending value.
  The bridge lives inside `EditorContextProvider`, waits for the editor to be
  `ready`, and applies once through `context.applyExternalDocument({
  canonical, expectedRevision, source: 'composer' })`. The apply is a normal
  `setContent` transaction: it is undoable and emits an update, so the existing
  `onDocChange` + autosave boundary persists it. The bridge owns no Tiptap API of
  its own.

## 5. Async / stale-result safety

The composed page is produced in Composer mode where no editor is mounted, then
crosses a mode switch. Two guards make that safe without a new mechanism:

- **Boundary**: the staged value captures `session.boundary` at request time. If
  the session document changed (switch / new / close) before the bridge runs, its
  boundary differs and the apply is a no-op (`stale-document`); the content is
  never written into the wrong document.
- **Revision**: `applyExternalDocument` compares `expectedRevision` against the
  live document revision and returns `stale-revision` rather than writing when
  the document moved underneath the staged composition.

The bridge also applies each staged value at most once (a ref guard), so a
context re-render cannot turn a successful replacement into a spurious
stale-revision failure, and it waits while the editor is not yet ready instead of
dropping the composition.

## 6. Failure semantics

| Case | Result |
| --- | --- |
| Open document empty, apply succeeds | document replaced in place; notice; autosave persists it; no document switch, no `/content` create |
| Open document non-empty | apply refused before staging; error explains only empty documents are eligible; document unchanged |
| Session boundary moved before apply | `stale-document`; document unchanged |
| Live revision no longer matches the staged base | `stale-document` (editor `stale-revision`); document unchanged |
| Editor not ready yet | bridge waits; applies once ready |
| Apply transaction fails / unrepresentable | `failed`; error surfaced; document unchanged |

All outcomes clear the staged pending value, so a stale or failed apply cannot
fire again later.

## 7. Preserved / non-goals

- R5.4.2 create-new-draft handoff is behaviorally unchanged; the two paths are
  mutually exclusive affordances.
- Composer generation stays preview-only and document-independent; the result is
  still a `CanonicalDocument`.
- The session keeps sole ownership of identity, lifecycle, revision, dirty,
  autosave, the save barrier and switching; the shell keeps no editor instance
  and no second session/autosave/lifecycle.
- No append/merge into a non-empty document (R5.4.3.3).
- No new operation types (`featureGrid` / `cta` / `list` / `stats` / `button` /
  media-slot), no new proposal/review framework, no Composer persistence, no
  Composer-owned Tiptap APIs, no Composer route removal, no Designer changes.
- No Composer-specific persistence or document identity; no direct Tiptap
  mutation from Composer mode (R5.3.3 isolation holds).
- Applying does not create a review/approval step; the composition is a direct
  in-place replacement of an empty document, reported by notice.
