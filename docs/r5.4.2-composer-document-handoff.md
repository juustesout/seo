# R5.4.2 - Composer document handoff

Status: **delivered**. Follow-up to R5.4.1, hardening the Composer draft-creation
to workspace-document transition so it is explicit and race-safe.

## 1. Flow

```text
Composer planning/preview        (document-independent)
        |
        v
   POST /content
        |
        v
 persisted document ID
        |
        v
 requestDocumentSwitch(id)       (existing session boundary)
        |  save barrier (existing autosave flush)
        v
 canonical session document      (identity + new boundary)
        |
        v
   Editor mode                  (only after the switch resolved)
        |
        v
 normal Editor document loading  (useDocumentLoad through the session)
```

One path, using the existing `DocumentSessionContext` / workspace session APIs.
No second document-switch API, no `composedDraftId`, no Composer-local document
identity.

## 2. Why a switch, not adoption

The created Composer draft is a **new persisted document**, not the current
workspace document gaining its server id. It is therefore handled with
`requestDocumentSwitch`, which advances the session generation and freezes a new
boundary. `adoptDocumentId()` is reserved for the first save of the current
`new#N` document and is not used here; blurring the two would keep the previous
document's boundary (and editor history/workspace state) for an unrelated
document.

## 3. Save barrier

`requestDocumentSwitch` runs the existing autosave `flush` barrier. If the
current document is dirty and the save fails, the switch is `blocked`: the
current document and boundary stay authoritative, the error is set, and
`onModeChange('editor')` is not called (it runs only in the success callback of
the switch). No second save mechanism is introduced.

To avoid an unexplained partial result, `Compose` keeps the created draft id in a
transient ref for the current run: a retry after a blocked barrier re-opens the
same draft through `onOpenEditor` instead of posting a duplicate. A new
generation run clears it. This is a retry payload, not a document identity owner,
and it never outlives the Composer instance.

## 4. Async / stale-result safety

The Composer surface has a real invalidation risk: the create request is async,
and the user can leave Composer (or the workspace document can change) before it
resolves. `ComposerMode` therefore supplies `beginHandoff`, which captures the
shared document boundary at the moment the handoff task starts using the
existing `useOperationBoundary` (R5.2.9) and additionally treats the Composer
boundary component unmounting as invalidation:

- a late result whose captured boundary has moved is dropped - it does not
  switch the workspace to an obsolete draft;
- a current result completes normally.

No global epoch and no Composer-specific document boundary are added. The legacy
standalone Composer (account-level `compose` area) omits `beginHandoff`, so its
handoff stays immediate.

## 5. Failure semantics

| Case | Result |
| --- | --- |
| Draft creation fails | existing Composer error shown; no workspace transition |
| Creation succeeds, switch succeeds | created document becomes canonical; Editor mode opens via the normal session/load path |
| Creation succeeds, save barrier fails | current document stays authoritative; Composer stays open; error surfaced; created id kept for retry |
| Creation succeeds, stale result | handoff dropped; workspace unchanged |
| Mode transition fails | no compensating second identity; the session stays authoritative for the selected document and existing mode/route state is used |

`ComposerMode` surfaces the workspace error banner (for example a blocked save
barrier) because Composer does not render the shared document chrome.

## 6. Preserved

Composer planning/preview stays document-independent; `Compose` still owns brief,
format, phase, plan, preview, generation state, tabs and Composer-specific
errors. Editor mode is unchanged and opens through the canonical session/loading
path without a second document prop. Composer mounts no editor infrastructure
(Tiptap, editor context/selection providers, editor keymap, editor AI,
`EditorMode`). Route and mode APIs are unchanged.
