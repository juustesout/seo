# R5.4.6 - Composer workspace chrome integration

Status: **delivered**. Composer is now a native mode of the unified workspace:
the shared workspace chrome (mode switcher + document header) is the single top
layer in both Editor and Composer, and Composer no longer renders its own page
header while mounted in the shell. R5.4.3-R5.4.5 functionality is unchanged.

This milestone is integration only. It adds no Composer features, no second
navigation system and no new document/session state.

## 1. Reconnaissance findings

1. **Composer exposure.** `ProjectWorkspaceShell` renders `WorkspaceModeSwitcher`
   (`editor | composer | designer`) above the active mode and dispatches
   `activeMode === 'composer'` to `ComposerMode`. Composer was already reachable
   from the chrome; the mode switcher is the canonical entry.
2. **Mount/unmount.** `ComposerMode` is conditionally rendered by the shell, so it
   mounts when the mode becomes `composer` and unmounts when it leaves. It owns no
   document identity or lifecycle; it reads the shared `WorkspaceSessionValue`.
3. **Navigation model.** Hand-rolled history routing in `App.tsx`; the canonical
   route is `/p/:projectId/workspace/:mode`. `onModeChange` pushes
   `/p/:id/workspace/:mode`; `popstate` re-parses. There is no navigation state
   machine beyond the route + `mode` prop.
4. **Chrome components.** `WorkspaceModeSwitcher` (mode tabs) and
   `WorkspaceChrome` -> `DocumentHeader` (document title/status/save + actions).
   `WorkspaceChrome` was gated to `activeMode === 'editor'`.
5. **Mode controls.** The switcher is the only mode navigation. **Preview is not a
   mode** in this repository: it is a pane toggle inside the editor chrome
   (`DocumentHeader` Preview button + `previewOpen` document-scoped state). It is
   intentionally not promoted to a mode.
6. **State crossing the boundary.** `PendingComposition` (staged apply/append) is
   owned by the shell; `ComposerMode` forwards `onOpenEditor`,
   `onApplyToDocument`, `onAppendToDocument` and their eligibility flags. The
   review batch stays inside `Compose` (R5.4.5).
7. **Duplicated chrome in Composer.** `Compose` rendered its own `PageHeader`
   ("Compose"). No mode switcher, project selector or document selector was
   duplicated.
8. **Legacy entry points.** The account-level `/compose` area renders the
   standalone `Compose` with the user's first project; the `compose` project view
   renders the shell in composer mode. Both are retained for R5.4.7.
9. **Tests.** `ProjectWorkspaceShell.{test,chrome,isolation,handoff,composerApply}.test.tsx`,
   `ComposerMode.{test,handoff}.test.tsx`, `WorkspaceModeSwitcher.test.tsx`,
   `WorkspaceChrome.test.tsx`, `Compose.test.tsx`,
   `CompositionReviewDialog.test.tsx`.

## 2. Canonical Composer entry

The workspace owns the decision to enter Composer. The canonical entry is the
`WorkspaceModeSwitcher` `Composer` tab, which drives `onModeChange` ->
`/p/:projectId/workspace/composer`. Composer receives project identity, role and
document session from `useWorkspaceSessionContext()`; it creates no second
context, document id, revision or autosave. The legacy `/compose` area and the
`compose` project view remain compatibility entries (R5.4.7).

## 3. Workspace chrome changes

- `showChrome` in `ProjectWorkspaceShell` now covers `editor` **and** `composer`
  (still gated on `lifecycle.status === 'ready' && canEdit`). The shared document
  header is visible while composing, so the current document is anchored.
- `DocumentHeader`/`WorkspaceChrome` gained an optional `showCanvasControls`
  (default `true`). The shell passes `false` in Composer mode: the editor-only
  Insert rail and canvas Preview are hidden because the editor is not mounted.
  Document-level controls (title, status, save, Publish, More, Back) stay.
- The mode switcher is unchanged and remains rendered in every mode.

## 4. Navigation semantics

- **Enter Composer**: swaps the active body; the shared session boundary is
  unchanged (pinned by test).
- **Composer -> Editor**: uses the existing switcher/`onModeChange`; the current
  document and its identity are untouched.
- **Composer -> Designer**: uses the same mechanism; no Composer-specific
  navigation.
- **Composer with an active review**: the shell holds a boolean
  `composerReviewOpen` (reported by `Compose` via `onReviewOpenChange`). While it
  is set, `ProjectWorkspaceShell` refuses a switcher mode change with the reason
  "Finish or cancel the composition review before leaving Composer." rather than
  silently unmounting the review. The review batch stays in `Compose`; only the
  open/closed flag crosses the boundary. Apply/Cancel clear the flag, after which
  navigation proceeds. This is a hold, not a second navigation state machine.

## 5. Duplicated chrome removed/suppressed

- `Compose` now takes `showHeader` (default `true`). `ComposerMode` passes
  `showHeader={false}` so the workspace chrome is the single top layer inside the
  shell. The standalone legacy `/compose` area keeps its own header.
- No mode switcher, project selector or document selector was removed because
  Composer never had one.

## 6. Context/state ownership verification

- Project context: `ComposerMode` reads `projectId`/`role` from
  `useWorkspaceSessionContext()`.
- Document identity: the shared `useDocumentSession` boundary in the shell; the
  composer sees it and cannot move it except through the existing apply/handoff
  paths.
- Composer still owns only its composition workflow state (brief, format, phase,
  plan, generated document/preview, review). The generated `CanonicalDocument`
  and `CompositionOperationBatch` are proposal data; they reach the unified
  document only through the existing `CompositionApplyBridge`.

## 7. R5.4.3-R5.4.5 preserved

Generation, preview, `CompositionOperationBatch`, the review dialog, gap
reporting, Apply, Cancel, the stale-boundary guard and `CompositionApplyBridge`
are unchanged. R5.4.6 only wires them into the workspace chrome and adds the
review navigation hold.

## 8. Tests / verification

- New `ProjectWorkspaceShell.composerNav.test.tsx` (4): Composer reachable from
  the chrome without a new document identity; return to editor uses existing
  navigation; one identity across composer/designer/editor; a mode switch is
  refused while a review is open and allowed after cancel.
- `ProjectWorkspaceShell.chrome.test.tsx` (extended): composer shows the shared
  document header without editor canvas controls; designer still drops the chrome.
- `Compose.test.tsx` (extended): `onReviewOpenChange` true/false around
  open/cancel; `showHeader={false}` suppresses the local header.
- `ComposerMode.test.tsx`, `ProjectWorkspaceShell.isolation.test.tsx`: updated to
  identify Composer by its brief instead of the removed local heading.
- contracts tests **483 passed** (26 files, unchanged); web **609 passed**
  (59 files); API **1658 passed** (unchanged); web typecheck, root typecheck +
  build and `git diff --check` clean.

## 9. Legacy surfaces intentionally retained for R5.4.7

(Superseded by R5.4.7: these surfaces now redirect to the canonical workspace
route; see `docs/r5.4.7-composer-legacy-retirement.md`.)

- Account-level `/compose` area (`App.tsx`) rendering standalone `Compose` with
  its own page header.
- The `compose` project view mapping to the shell's composer mode, and the
  `content` view mapping to the editor mode.
- `Content.tsx` compatibility wrapper.
- `Compose`'s `showHeader` default (`true`) so the legacy surface is unchanged.

## 10. Remaining integration gaps

- Browser history (`popstate`) can still change the workspace mode without going
  through the switcher, so it bypasses the review hold. Only the canonical
  switcher navigation is guarded in R5.4.6.
- Designer still owns its own page header; converging it is R5.5.
- Preview remains an editor pane toggle rather than a workspace mode.
