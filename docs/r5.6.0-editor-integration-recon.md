## 4. Editor route and open behavior

Canonical routes:

- `/p/:projectId/workspace/editor` -> `sub='editor'`, `sub2=null`.
- `/p/:projectId/workspace/editor/:contentId` -> `sub2=contentId`.
- Legacy `/p/:projectId/content[/:contentId]` -> `canonicalWorkspaceRoute`
  returns `view:'workspace', sub:'editor', sub2:route.sub` (`projectRoute.ts:53-55`),
  applied via `replaceState` (`App.tsx:149-162`).

Question-by-question findings:

| Question | Finding | Evidence |
| --- | --- | --- |
| `contentId` present? | `EditorMode.initialContentId` -> `EditorView`; a one-shot effect calls `open(id)` exactly once per distinct id | `App.tsx:289,327`; `EditorView.tsx:213-218` |
| `contentId` absent? | `initialContentId=null`; the session starts at `INITIAL` (`idle`), so the editor shows the Content Studio list | `useDocumentSession.ts:90`; `EditorView.tsx:334-429` |
| Who decides identity? | `useDocumentSession` (via shell `open`/`startNew`/`goList`) | `useDocumentSession.ts:138`; `ProjectWorkspaceShell.tsx:205-219` |
| Who loads the document? | `useDocumentLoad` keyed by `editingId` | `workspaceSession.tsx:139`; `useDocumentLoad.ts:39` |
| Multiple documents? | Idle state renders a table of all project content; clicking a row calls `open(id)` | `EditorView.tsx:382-426` |
| No documents? | The table is replaced by an `Empty` message; no row, no auto-open | `EditorView.tsx:379-381` |
| Auto-create a document? | No. `startNew` calls `requestNewDocument` (`creating=true`); the row is POSTed only on first autosave | `ProjectWorkspaceShell.tsx:209-215`; `useDocumentSession.ts:181`; `workspaceSession.tsx:160-188` |
| Document picker? | Yes - the Content Studio list is the picker and it lives inside Editor mode | `EditorView.tsx:382-426` |
| "Current/last document" concept? | There is a *current* document (session identity) but no cross-session "last opened" concept | `useDocumentSession.ts:139` |
| Last-opened persisted? | No. The only `localStorage` uses are the Designer run bookmark and the Writer run bookmark | `workspace/designerRunClient.ts:10,34-56`; `WriterPanel.tsx:292,355` |
| Route gives deterministic identity? | Only when `sub2` is present. Without it the route is mode-only and identity is a user choice (list) or a new draft | `App.tsx:289`; `projectRoute.ts:35` |
| Redirects / implicit selection? | Legacy `content` `sub` becomes workspace `sub2` (deterministic). No implicit "pick first/last" behavior exists | `projectRoute.ts:53-55` |

Conclusion for section 4: no "last document" mechanism is required by the current
architecture. The unresolved decision is a **product** one: when a user opens
`/p/:id/workspace/editor` with no `contentId`, should they always see the list
(today's behavior), resume the last edited document, or open the most recent
document? No code assumes any of these; this is a product decision, not a defect.

## 8. Composer/Designer -> Editor handoff findings

Actual runtime path when a Composer/Designer mutation is applied:

1. The mutation is prepared in Composer/Designer mode (Editor is **not**
   mounted; only one mode body renders - `ProjectWorkspaceShell.tsx:382-409`).
2. The mode calls the shell handler: `applyComposition` (`:239`),
   `appendComposition` (`:267`), or `applyDesignerProposal` (`:314`). Each
   validates role/lifecycle, representability, target document identity, and
   revision, then stages `pendingComposition` (`:119`) and calls
   `onModeChange?.('editor')`.
3. The shell stays mounted across the mode change (`ProjectWorkspaceShell.tsx:58-84`),
   so `pendingComposition` survives; `EditorMode` mounts fresh.
4. `CompositionApplyBridge` (`CompositionApplyBridge.tsx:150-187`) waits for
   `ready` (editor exists and `context.snapshot.ready`), re-checks
   `session.boundary` and `targetDocumentId`, then dispatches through
   `applyExternalDocument` / `applyDocumentOperations` / `applyImageInsertion`.
5. The apply is one `editor.commands.setContent(...)` transaction
   (`EditorContext.tsx:140,186`), which emits a normal update, so the existing
   `onDocChange` -> autosave path persists it; the result clears
   `pendingComposition` and sets notice/err (`ProjectWorkspaceShell.tsx:344-365`).

Findings:

- **The "Editor already mounted" variant is unreachable by construction.** To
  stage a mutation the user must be in Composer or Designer, which unmounts
  Editor. Therefore the bridge always runs after Editor remounts, and its
  "wait for the editor" branch is the normal path, not an edge case
  (`CompositionApplyBridge.test.tsx:204-216`).
- **Document revision guard.** `baseRevision` is captured from the live
  document at staging (`ProjectWorkspaceShell.tsx:253,296`) and re-checked by
  `applyDocumentOperations`/`applyExternalDocument` (`EditorContext.tsx:131,168`).
- **Autosave/dirty.** The apply is a normal transaction; baseline/dirty update
  via `useAutosave` exactly as an edit (`EditorContext.tsx:137-140`).
- **Undo/history.** The editor remounts on mode switch (keyed by
  `session.boundary`, `EditorWorkspace.tsx:86`; `EditorView.tsx:531`), so history
  is per-mount; the applied batch is a single undo step within the new mount.
- **Identity.** No document switch occurs: the boundary is unchanged and the
  tests assert it (`ProjectWorkspaceShell.composerApply.test.tsx:256-257`).
- **In-editor agent.** When Editor is active, the embedded agent applies
  directly through `EditorContext` with no shell staging
  (`EmbeddedAgentEntry.tsx:45-66`), which is correct - no bridge needed.

Test coverage: `CompositionApplyBridge.test.tsx` (13 cases incl. boundary,
revision, target identity, wait-for-editor), `ProjectWorkspaceShell.composerApply.test.tsx`
(6 cases), `ProjectWorkspaceShell.designerApply.test.tsx` (5 cases). The
handoff is well covered; the only untested scenario is the intentionally
unreachable "staged while editor already mounted".

Conclusion: the current architecture already handles the handoff correctly.
There is no need to implement a live-sync mechanism for R5.6.

## 9. Document-scoped Editor state findings

Scoping mechanism: `WorkspaceStateProvider documentKey={session.boundary}`
(`ProjectWorkspaceShell.tsx:72`) + `useDocumentScopedState`
(`workspaceState.tsx:33`). The key is `documentScopeKey(identity, generation)`
(`useDocumentSession.ts:105`).

| Editor state | Location | Scoped by | Assessment |
| --- | --- | --- | --- |
| `preview` | shell | `useDocumentScopedState` | correct |
| `railOpen` | shell | `useDocumentScopedState` | correct |
| `assistantOpen` | `EditorMode` | `useDocumentScopedState` (`EditorMode.tsx:73`) | correct |
| rail tab (`outline/seo/...`) | `IntelligenceRail` | `useDocumentScopedState` (`:43`) | correct |
| sidebar mode (`elements/settings`) | `EditorShell` | `useDocumentScopedState` (`:29`) | correct |
| inline AI suggestion/proposal/busy | `EditorView` | effect on `session.boundary` (`:200-202`) | correct |
| selection | `EditorSelectionProvider` | `documentId` (`EditorMode.tsx:128`, `EditorSelectionContext.tsx:56-58`) | correct but see note |
| undo/redo | Tiptap, keyed by `session.boundary` | `EditorWorkspace.tsx:86` | correct |
| `writerOpen` | `EditorView` | plain `useState` (`:149`) | minor: survives a document switch within editor mode |
| `useKnowledge` | `EditorView` | plain `useState` (`:138`) | minor: not doc-scoped |

Assessment of `documentScopeKey(identity, generation)`: it is sufficient for the
editor's document-scoped UI state. It advances only on a successful logical
transition and is preserved across first-save id adoption
(`useDocumentSession.ts:151-198`), which is what every boundary-scoped value
needs.

The one inconsistency: the selection owner resets on `documentId`
(`EditorSelectionContext.tsx:56-58`) rather than on `boundary`. First-save id
adoption changes `documentId` (null -> id) but preserves `boundary`, so selection
is cleared on the first save while editor history and other UI state are not.
This is a transient, self-healing difference (the selection is re-derived on the
next selection event) and not an observed defect. It is recorded as a minor
finding, not a required fix.

Known limitation (already deferred in the post-5.5 recon): the route redirect
effect does not special-case `popstate`; back/forward handling is out of scope
here.

## 12. Architecture risks

Evidence-based only.

| Risk | Present? | Evidence |
| --- | --- | --- |
| A second document/editor path | **No** | one session (`workspaceSession.tsx:105`); one editor mount (`ProjectWorkspaceShell.tsx:382-396`) |
| Bypassing `DocumentSessionContext` | **No** | only `useWorkspaceSession` creates identity; all readers consume context (`workspaceSession.tsx:341-345`) |
| Bypassing the shared mutation funnel | **No** | Composer/Designer stage -> bridge -> `EditorContext` (`CompositionApplyBridge.tsx:150-187`) |
| Whole-document replacement outside `EditorContext` | **No** | `setContent` only inside `applyExternalDocument`/`applyDocumentOperations` (`EditorContext.tsx:140,186`); legacy server `designer/apply` has no web caller (`r5.5.5` section 4) |
| Duplicate autosave/revision ownership | **No** | one `useAutosave` (`workspaceSession.tsx:190`); one revision contract (`documentRevision.ts`) |
| Editor state leaking across document boundaries | **Mostly no** | boundary-scoped UI state (`workspaceState.tsx:33`); G6 `writerOpen`/`useKnowledge` are the only unscoped flags and are presentation-only |
| Composer/Designer creating stale editor state | **No** | staging guards identity + revision (`ProjectWorkspaceShell.tsx:324-336`) and the bridge re-checks both (`CompositionApplyBridge.tsx:162-174`) |
| Route identity differing from session identity | **No** | `sub2` seeds `initialContentId`; the session owns identity thereafter (`App.tsx:289`; `EditorView.tsx:213-218`) |
| Toolbar/contextual UI acquiring its own identity | **No** | toolbar reads the shared editor and canonical selection only (`ContextualToolbar.tsx:15-51`) |

No architectural regression is present. The risks that remain are product/UX
scope (default-open target, contextualisation), not integrity risks.

## 14. Recommended R5.6 decomposition

Conservative, evidence-based, smallest verifiable slices. This is a
recommendation only; it is not approved or started.

1. **R5.6.1 - default-open decision + implementation.** Resolve the section 4
   product decision, then implement the chosen behavior for
   `/p/:id/workspace/editor` (list today; resume-last or most-recent only if the
   decision calls for it). Reuse the existing session/loader; add no second
   identity.
2. **R5.6.2 - toolbar simplification.** Reduce `ContentToolbar` to a
   canvas-dominant set; remove or fold the dead `EditorToolbar` path (G5). No
   change to session or mutation paths. Reuse `ContextualToolbar` and the
   selection boundary.
3. **R5.6.3 - contextual SEO.** Make the existing `SeoPanel`/`IntelligencePanel`
   assets appear based on canvas/selection relevance instead of always-on rail
   tabs (G2, G3). This reuses `EditorContext`/selection; it adds no new data
   source. Deeper simplification remains R5.8.
