# R5.10.8 - Usage read API and reporting surface

Delivered behavior for *reading* the append-only usage ledger built in R5.10.2
and populated by R5.10.3-R5.10.7. This is the reporting layer: an authorized
aggregate endpoint, an account-scoped variant, and a minimal web view. It adds
**no schema, no migration and no vocabulary change** - read paths reuse the
existing `UsageEventStore.aggregate`.

Directory analysis is in `docs/r5.10-closeout-recon.md`; this document records
the delivered design and decisions.

## 1. Read API

Two routes, both aggregate-only:

| Route | Scope | Authorization |
| --- | --- | --- |
| `GET /api/projects/:projectId/usage` | one project | `access.requireRole(user.sub, projectId, 'viewer')` |
| `GET /api/account/usage` | caller's own account | `access.requireAccount(user.sub)` |

The account id is never taken from the URL - it is resolved from the
authenticated user, so a caller can only read their own account. The route edge
gates the scope; `UsageEventStore.aggregate` additionally re-checks the actor's
membership in the database RPC, so authorization is defense in depth.

`services/usageReportService.ts` (`readUsageReport`) shapes the report; it never
returns raw rows and never derives cost. The shared response DTO
(`UsageReportDto`, `packages/contracts/src/usageEvent.ts`) is stable for the web
app and a future MCP tool:

```ts
{
  scope: { accountId: string | null; projectId: string | null },
  totals: UsageAggregate[]   // category, provider, operation, unit, quantity, eventCount
}
```

## 2. Filters

`usageQuerySchema` (zod, route edge) accepts:

- `category` - closed `UsageCategory` enum.
- `unit` - closed `UsageUnit` enum.
- `provider`, `operation` - bounded lowercase tokens (`^[a-z0-9_]+$`).
- `success` - `'true' | 'false'` transformed to boolean.
- `occurredFrom`, `occurredTo` - ISO-8601 datetimes.

Any invalid value is a `400` before the store is touched. The window is
`occurredFrom` inclusive / `occurredTo` exclusive, matching the store predicate.

## 3. Web view

`apps/web/src/views/Usage.tsx` is one component for both scopes: pass a
`projectId` for the project report, omit it for the account report. It renders
the four read states (loading / empty / error / populated) and a single
aggregate table - category, provider, operation, unit, quantity, event count.
There are deliberately no charts, pricing, budgets, invoices or cost columns.

The view is reached from the existing shell, not a parallel one:

- Account: `Usage` in the top navigation (`/usage`).
- Project: `Usage` in the project navigation (`/p/:projectId/usage`).

`lib/projectRoute.ts` adds `usage` to `TopArea` and to the parsed areas; the
`openProjectView` / navigation helpers are unchanged.

## 4. Interactive user attribution (C2)

Usage facts now carry the acting user for interactive work, without a global
lookup or schema change. The acting user id is threaded from the authenticated
route edge (`user.sub`) down to the usage scope:

- `AIService.resolve(projectId, actorUserId = null)` -> `usageScopeContext({ userId })`.
- `ContentAiService`, `ContentAiEditService`, `ContentAnalysisService`,
  `ContentIntelligenceService`, writer dependencies and the designer
  (`DesignerServiceOptions.actorUserId`, `createLlmDesignerPlanner`) forward it.
- `ImageInsertionService` / `SectionCreationService` pass it into the media
  `MediaUsageScope`.
- `KnowledgeService.search(projectId, input, actorUserId = null)` and
  `opportunityTopicService.getTopicRecommendations` thread it into read-path
  observers.

Resolution rule: **authenticated interactive work uses the acting user id; a
durable job uses `job.created_by`; system/background work with no actor stays
`null`.** `ProviderUsageContext.userId` is optional so existing callers that pass
no actor keep emitting `userId: null`. No global user lookup is introduced.

## 5. Embedding meter resolution (C3)

R5.10.7 counts embeddings at the physical `POST /embeddings` seam
(`OpenAiCompatibleEmbedder.embed` -> `embeddingUsageObserver`). The older logical
embed meter (`instrumentAiProvider.embed` summing tokens into `embeddingEvents`)
is superseded and would double-count if both were live.

Resolution:

- `instrumentAiProvider.embed` is now a pure passthrough (`(req) => provider.embed(req)`);
  it emits nothing. The dead `embeddingEvents` and `imageGenerationUsageEvent`
  helpers were removed from `services/usageInstrumentation.ts`.
- `EmbeddingService` / `ProjectEmbedder` (`services/embeddingService.ts`) are
  marked deprecated and remain uninstrumented; they have no production caller.
- Invariant: **embedding usage is recorded once, at the physical request, by the
  live observer.** Any future embed path must go through the physical observer,
  not a logical meter.

No vocabulary change: unit `input_token`, operation `embed`.

## 6. Documentation corrections

Only stale examples were corrected in `docs/r5.10.1-usage-vocabulary.md`:

- `keyword_gap` -> `competitor_gap` (the token the provider actually emits).
- DataForSEO keyword volume: one logical request emits **two** facts (`request`
  quantity 1 and `keyword` quantity N), not one summed fact with a
  `keywordCount` metadata key.
- GSC example: one fact per Search Console HTTP request
  (`search_analytics` / `gsc_request` / quantity 1), not one `gsc_sync` fact of
  quantity 25.
- Image generation: interactive path `sourceId: null` (job-originated work uses
  the job id), not `<seo_media.id>`.

## 7. Test coverage

- `apps/api/src/http/routes/usage.test.ts` - anonymous `401`, missing-role `403`,

- `apps/api/src/services/usageInstrumentation.test.ts` - chat/generate facts,

- `apps/web/src/views/Usage.test.tsx` - loading, populated aggregate table,
  honest empty state, surfaced read error, account-vs-project endpoint.

## 8. Explicit non-goals

Charts, pricing/cost, budgets, quotas, invoices, exports; raw event listing;
new persistence or schema; a second authentication mechanism; global user
lookup; account-level GSC / CDN / Jina / Cohere / BYOK metering; retention or
rollup policy. Cost remains a future derivation from facts plus pricing, never a
stored or invented number.
