# R5.3.2 - Shell-level workspace chrome

Status: **delivered**. Second slice of R5.3 (`docs/phase-5-roadmap.md:86-118`),
implementing the `WorkspaceChrome` layer from the locked ADR
(`docs/r5.1-workspace-decisions.md`). It is a structural extraction: the editor
mode body loses its workspace-level chrome, the shell gains it.

## 1. What moved

`ProjectWorkspaceShell` now renders `WorkspaceChrome` above the active mode:

```text
ProjectWorkspaceShell
|- shell-owned: session, editor instance, editor context providers, keymap
|- WorkspaceChrome
|    |- DocumentHeader            (title, status, save indicator, actions)
|    |- save-failure status       (workspace save lifecycle)
|    `- assistant entry           (InlineAssistantSlot + EmbeddedAgentEntry)
`- active mode
     |- EditorView                (list, inline AI, writer, canvas)
     |- Compose                   compatibility body
     `- Designer                  compatibility body
```

`EditorWorkspace` is now the editor canvas only: merged toolbar, writing canvas,
preview, intelligence rail and secondary sections. It no longer renders the
header, the save indicator, the assistant entry or the editor/selection context
providers.

## 2. Why these are workspace-level

- The document title, status, save state, Save/Publish/Delete and the document
  Back action all act on the one shared document session, not on the editor
  widget. R5.4/R5.5 will read the same document from Composer/Designer, so the
  header cannot belong to the editor alone.
- The save indicator is the `document-save-state` badge inside `DocumentHeader`;
  it reads the single `useAutosave` owned by the shell through
  `useWorkspaceSessionContext`. The save-failure banner moved with it.
- The assistant entry (the reserved `InlineAssistantSlot` and the
  `EmbeddedAgentEntry` trigger) is scoped to the open document, not to the
  editor widget: the agent already reads identity, revision, dirty state and
  selection from the editor context and applies insertions through the shared
  document pipeline.

## 3. State and context each piece consumes

| Piece | Reads | Source of truth |
| --- | --- | --- |
| `DocumentHeader` | title/status/saveState/slug/savedAt/canEdit/canDelete | `useWorkspaceSessionContext` (shell session) |
| save indicator | `auto.status`, `savedAt` | the single `useAutosave` (shell session) |
| save-failure banner | `auto.status === 'failed'` | the same autosave |
| assistant entry | `editor` context snapshot + selection + `assistantOpen` + `assistantConfigured` + `assistantBusy` | `EditorContextProvider`/`EditorSelectionProvider` (shell-owned), shell document-scoped state, project AI status |

## 4. Ownership preserved (no new state)

- One document session, boundary, lifecycle, revision/dirty model, autosave and
  save barrier: unchanged, still `useWorkspaceSession` in the shell.
- One editor instance: lifted from `EditorView` to the shell so both the chrome
  and the canvas share it; `RichTextEditor` still keys on `session.boundary`.
- One selection owner and one editor context owner: the providers moved from
  `EditorWorkspace` to the shell; no second copy was added.
- One assistant state owner: `assistantOpen` moved from `EditorWorkspace` to the
  shell's document-scoped state; `useEmbeddedAgent` still owns the interaction.
  `assistantBusy` is a display signal reported up by the editor, not a second
  operation state.
- `documentScopeKey`, `editorHistoryKey` and the session `boundary`/generation
  semantics are untouched.

Not moved (documented staging):

- Chrome renders only for the editor mode while the shared document is ready and
  editable, because Composer/Designer are still legacy bodies that do not read
  the shared document. R5.4/R5.5 converge them onto it and the chrome follows.
- `EditorView` still unmounts on a mode switch, so its in-memory editor undo
  history is not preserved across modes (already noted in R5.3.1).

## 5. Non-goals (unchanged)

No route or route-model change, no mode-switcher redesign, no Composer/Designer
refactor, no editor redesign, no assistant redesign, no autosave/session
redesign, no workspace-state redesign, no beforeunload handling, and no database
or migration work.
