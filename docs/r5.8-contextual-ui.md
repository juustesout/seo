# R5.8 - Contextual UI

Status: **implemented.** R5.8 makes the unified workspace context-aware: the
chrome and the intelligence rail now derive what to show from the current
workspace state (mode, editor-vs-preview, selection, viewport) instead of from
whichever tool happened to be opened. It adds no new state architecture - every
input already has a canonical owner.

Baseline at the start of this step: `db2549d` on `origin/main`, worktree clean.
This record follows the actual repository, not the roadmap wording. It consumes
`docs/r5.6.5-closeout.md` and `docs/r5.7-preview-responsive.md`.

The core invariant:

> Contextual UI is derived from the canonical workspace state. It does not become
> a new source of truth.

---

## 1. Context model

`apps/web/src/components/content/workspace/workspaceContext.ts` is one pure
module (no React, no network) that defines the minimum context and the
derivations built on it:

```ts
type WorkspaceSurface = 'canvas' | 'preview' | 'composer' | 'designer';

interface WorkspaceContext {
  surface: WorkspaceSurface;
  selection: EditorSelectionSnapshot; // canonical, never copied
  viewport: PreviewViewport;          // shell-owned inspection state
}
```

Derivations:

- `workspaceSurface(mode, preview)` - maps the route mode plus the preview toggle
  to the surface that is actually visible.
- `isEditingSurface(surface)` - only the canvas may mutate the document.
- `surfaceControls(surface)` - the **single** mapping from surface to which
  editor-canvas controls may render (`editor`, `insert`, `tools`, `preview`).
- `contextualSelectionType(selection)` - the resolved element type of the live
  selection snapshot, or null.
- `railTabsForContext(context, available)` - the rail areas meaningful now.
- `defaultRailTabForContext(context, tabs)` - the rail default before the user
  chooses a tab (document-level Outline; Media for an image on the canvas).

The context is a plain description assembled at the point of use from existing
owners; it is never stored.

## 2. Canonical state sources

| Context field | Canonical owner | How it is read |
| --- | --- | --- |
| mode | route `:mode` (shell prop) | `ProjectWorkspaceShell` |
| preview | shell document-scoped `previewOpen` | `ProjectWorkspaceShell` |
| surface | derived (`workspaceSurface`) | shell -> `WorkspaceChrome` -> `DocumentHeader` |
| selection | `EditorSelectionContext` (R5.2.4) | `useEditorSelection` in `EditorWorkspace`, `EditorShell`, toolbar |
| viewport | shell document-scoped `previewViewport` (R5.7) | shell -> `EditorMode` -> `EditorWorkspace` -> `PreviewPane` |

The module imports only types from the shell (`WorkspaceMode`) and existing editor
modules; it introduces no store, context provider, reducer, or reset mechanism.

## 3. Contextual rail behavior

`IntelligenceRail` now derives its areas from the context:

- Outline + SEO are always document-level and available on every editor surface.
- **Media is offered only on the editable canvas surface.** The media library can
  upload/insert/delete, so preview must never expose it (Step 12).
- Insights stays available wherever it is configured (it is inspection).

The active tab remains UI state in the existing document-scoped
`useDocumentScopedState` (`workspaceState.tsx`). R5.8 changes the type to
`RailTab | null`:

- before the user picks a tab, the rail shows `defaultRailTabForContext`;
- once the user clicks a tab, that explicit choice wins while it stays available;
- if the chosen tab becomes unavailable (e.g. Media while entering preview), the
  rail falls back to the context default instead of showing nothing.

No second rail, no rail-owned selection/viewport, and no document content is
stored - consistent with the R5.2.7 UI-state contract.

## 4. Mode-aware behavior

`ProjectWorkspaceShell` computes the one `surface` value:

```ts
const surface = workspaceSurface(activeMode, previewOpen);
```

- editor + not preview -> `canvas` (Insert + Tools + Preview)
- editor + preview -> `preview` (Tools + Preview; **no Insert**)
- composer -> `composer` (no editor-canvas controls)
- designer -> `designer` (no editor-canvas controls)

`WorkspaceChrome` passes the surface straight to `DocumentHeader`, which renders
from `surfaceControls(surface)`. The former `showCanvasControls` boolean is gone,
so control visibility is derived in one place rather than by a flag per caller.
Composer and Designer keep the shared header/mode switcher and hide editor-only
controls exactly as before.

Mode changes still never create a document identity or touch unrelated session
state: `surface` is a pure function of the existing mode and preview props.

## 5. Selection-aware behavior

`EditorWorkspace` assembles the live context from the canonical selection:
`selection: shared?.selection ?? EMPTY_EDITOR_SELECTION`. It only points at the
snapshot; the snapshot itself stays owned by `EditorSelectionContext`.

Observable effects:

- On the canvas, an image selection points the rail at the Media library
  (context default, yielded to an explicit user tab choice). This is the only
  selection-driven rail default and uses an existing capability.
- Selection-driven *editing* actions already have owners and are unchanged:
  `ContextualToolbar` gates Delete element on the live composition `NodeSelection`
  (`canDeleteComposition` + `EditorToolbarActions.deleteSelected`), and
  `EditorShell` opens the settings sidebar for the selected element. R5.8 does not
  duplicate or replace these.
- Clearing/changing the selection updates the derived context on the next
  canonical snapshot; it never leaves a stale selection type driving the rail.

No fake controls were added for selection types without a real action path.

## 6. Preview behavior

- Preview is inspection-only. The rail drops the mutating Media area and the
  header drops the editing Insert control; Tools (Outline/SEO/Insights) and the
  Editing toggle stay, so the user can still inspect and return.
- The viewport controls remain exactly where R5.7 put them: inside `PreviewPane`,
  operating on the shell-owned document-scoped viewport. R5.8 neither duplicates
  the viewport state nor adds a second set of controls.
- Preview still renders the live revision through the canonical renderer; R5.8
  changes no rendering and does not make preview editable.

## 7. Composer / Designer integration

No new cross-mode contextual action was added, because beyond the existing mode
switcher and the bodies' own review/apply flows there is no real implementation
path for one (Step 13: "Only expose actions that already have real
implementation paths").

The integration R5.8 provides is the shared context: the same workspace chrome and
mode switcher stay present across Composer/Designer, and the surface derivation
correctly suppresses editor-canvas controls there. The mutation handoffs themselves
(`CompositionApplyBridge`, designer proposal guards, run controller) are untouched.

## 8. Action execution path

There is no new command framework. Contextual actions keep reusing the existing
model:

- composition delete -> `toolbarActionsFromEditor(editor).deleteSelected` in
  `ContextualToolbar`, gated by `canDeleteComposition` on the live selection;
- settings reveal -> `EditorSelectionContext.requestReveal` + `EditorShell`;
- document-level actions (save/publish/preview/insert/tools/history/schedule) ->
  the existing `DocumentHeader` handlers, now shown per surface;
- rail areas -> the existing `ContentOutline`/`SeoPanel`/`MediaPanel`/
  `IntelligencePanel`.

R5.8 only changes *which* of these are presented in the current context, never
how they mutate.

## 9. State ownership

- Document session, identity, revision, autosave: unchanged
  (`DocumentSession`, `workspaceSession`).
- Selection: unchanged single owner (`EditorSelectionContext`).
- Preview viewport: unchanged, shell-owned document-scoped state.
- Mode: unchanged, from the route.
- Rail open/tab, insert rail, preview, tools, assistant, sidebar mode: unchanged
  document-scoped UI state in `WorkspaceStateProvider`.

`WorkspaceContext` is derived at render time and stored nowhere, so it cannot
leak across document boundaries. The existing document-scoped UI state already
resets on a successful switch.

## 11. Known limitations

- The rail's context default (image -> Media) applies only until the user picks a
  tab for the document; after an explicit choice the rail does not auto-follow
  selection. This is deliberate: the active tab is UI state, not content.
- Only the editor-canvas surfaces are differentiated. Composer and Designer keep
  their own bodies; R5.8 does not add selection-specific contextual actions inside
  them because none has an implementation path yet.
- The inline assistant entry remains mounted in editor mode during preview (it is
  editor-coupled, not preview chrome). It is not part of the preview context and
  was intentionally left as-is.
- Font/chunk notes from R5.7 are unchanged and unaffected by R5.8.

## 12. Handoff to R5.9

- `workspaceContext.ts` is the single derivation point; new contextual controls
  should read `WorkspaceContext`/`surfaceControls` rather than re-checking mode or
  preview in components.
- The rail is now surface-safe and context-defaulted; a future selection-specific
  rail area should be added to `railTabsForContext` with a real panel behind it.
- Preview remains the canonical inspection surface; any new preview control must
  read the existing shell-owned viewport rather than introducing a second one.
- No R5.6 or R5.7 regression was found. The session/editor/preview identity
  guarantees and the preview round-trip tests still hold.
