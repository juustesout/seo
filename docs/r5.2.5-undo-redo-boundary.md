# R5.2.5 - Canonical undo/redo boundary

Status: **implemented, awaiting review** (not committed as part of the R5.2
batch).

This slice closes the R5.2 gap "One undo/redo boundary" from
`docs/phase-5-roadmap.md`. It makes the existing Tiptap/ProseMirror undo/redo
behaviour explicitly part of the canonical document session boundary. It does
not build a history mechanism.

## 1. Where undo/redo history lives

Undo/redo is ProseMirror's history plugin, provided by Tiptap's `StarterKit`
(`apps/web/src/components/content/editor/extensions.ts`). The history lives in
the **editor instance's ProseMirror state**. Commands are always issued against
that instance:

- `ContentToolbar` (`Undo`/`Redo` buttons) calls `editor.chain().undo()/redo()`;
- `EditorToolbar`'s `toolbarActionsFromEditor(editor)` does the same for the
  composition toolbar;
- operation batches applied through `EditorContext` (`applyExternalDocument`,
  `applyImageInsertion`, `applyDocumentOperations`) run as normal transactions,
  so they share the same history.

There is no app-level history store, no per-document undo stack, and no history
in `DocumentSessionContext`.

## 2. Why it is editor-instance scoped

The history is owned by the editor instance and nothing else. When the editor
instance is replaced, its history is gone; when it is kept, the history is kept.
The only thing that decides which happens is the React `key` on the editor
component:

```text
EditorWorkspace.writing.editorKey -> <RichTextEditor key={editorKey} />
```

`RichTextEditor` wraps `useEditor`, which creates the ProseMirror instance on
mount and destroys it on unmount. A new key therefore means a new editor and a
new history; the same key means the same editor and history. This is the whole
undo/redo lifecycle.

## 3. The document identity boundary

The key is derived from the canonical session identity plus the session
generation, through one pure function owned by the session module
(`editorHistoryKey` in `session/useDocumentSession.ts`):

```ts
editorHistoryKey(identity, generation); // `${id|new|closed}#${generation}`
```

`useDocumentSession` advances `generation` **only** when the save barrier
resolves `switched`. `Content.tsx` uses
`editorHistoryKey(session.identity, session.generation)` as the editor key. So:

- a successful document change advances the generation -> new key -> the editor
  is remounted -> history starts clean;
- a blocked/failed switch leaves the identity and the generation unchanged -> the
  same key -> the editor and its history are untouched.

No second identity owner was introduced: the key is a pure projection of the
identity the session already owns.

There is a second, existing guard that reinforces the same boundary: while a
document is loading, `Content.tsx` renders a loading screen instead of the
workspace, so a new identity is never paired with the previous document's editor
(the same rule R5.2.3 documents for the live document).

```text
Document A                      Document B
----------                      ----------
editor instance A               editor instance B
  |  history(A)                   |  history(B)   (fresh)
  |  edit / undo / redo           |  edit / undo / redo
  |
  +-- successful switch ----------+
        generation++  => editorKey changes => A destroyed, B created
```

## 4. Behaviour on a successful switch

The barrier flushes A, the session advances to B and bumps the generation, and
the editor key changes. React destroys editor A and creates editor B from B's
seeded document. B has a fresh history: `undo`/`redo` cannot reach A's edits.
This is the R5.2 default: `document switch => new/clean editor history boundary`.

Switching back to A later creates another fresh boundary. A's old history is not
restored, even though A's content is loaded from its saved state.

## 5. Behaviour on a failed switch

A failed save blocks the switch: identity stays A, the generation does not
advance, the editor key does not change. The editor instance is kept, so A stays
authoritative and its undo/redo history remains available. History is never
discarded merely because a switch was requested.

## 6. Stale outgoing editors

The editor handed to consumers always comes from the currently mounted
`RichTextEditor`; on a switch the old instance is destroyed and the new one is
handed up. A late operation from the outgoing document cannot become
authoritative because:

- the editor instance itself is different (and the old one is destroyed);
- `EditorContext`'s apply guards compare the live document revision, so an
  operation generated against A's revision is rejected as `stale-revision` when
  applied after the switch to B;
- `useEmbeddedAgent` already invalidates in-flight responses on a document
  identity change.

No new lifecycle mechanism was added for this; the existing revision and
identity guards are the seam.

## 7. Why persistent per-document history is out of scope

ProseMirror history is intentionally not serialisable across editor instances,
and storing it would mean a second, app-owned document state that could disagree
with `content_json`. R5.2 explicitly chooses the safe default (fresh history per
document) instead of persistent per-document history. The `editorHistoryKey`
boundary keeps the option open for a future slice without adding one now.

## 8. What this slice did not touch

No changes to Tiptap/ProseMirror history, editor commands, keyboard shortcuts,
toolbar UX, autosave, revision semantics, selection ownership or persistence.
Undo/redo is still owned by the editor; the session owns only the lifecycle
boundary. `DocumentSessionContext` gained no `undo()`/`redo()` commands.

## Tests

`session/undoRedoBoundary.test.tsx` (7) composes the real `useDocumentSession`,
the real `editorHistoryKey` and a real keyed `RichTextEditor` (mirroring
`Content.tsx`) and covers:

1. undo is local to the open document;
2. undo does not cross a document boundary;
3. redo does not cross a document boundary;
4. a failed switch keeps A authoritative and preserves its history;
5. a successful switch establishes a clean boundary;
6. switching back creates a fresh boundary (no restored history);
7. an operation generated for the outgoing document is rejected as
   `stale-revision` and cannot mutate the active document.

`session/useDocumentSession.test.ts` (+4): the generation advances only on a
successful change, not on a blocked switch, adoption or discard; and
`editorHistoryKey` maps identity + generation to the boundary key.
