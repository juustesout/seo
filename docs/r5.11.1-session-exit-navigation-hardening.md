# R5.11.1 - Session exit and navigation hardening (H1 + H2)

First hardening slice from `docs/r5.11-hardening-recon.md`, implementing the two
High-severity findings that close the deferred R5.2 G3 gap:

- **H1** - browser Back/Forward (and any `popstate`) bypassed the workspace save
  barrier.
- **H2** - reload/close had no unsaved-changes protection.

No schema, migration, contract, vocabulary, provider or route change. No change
to the document session, generation, revision, selection or autosave model: both
fixes reuse the existing save barrier (`lib/navigationBarrier.ts` over
`useAutosave.flush`). H3, H4 and H5-H10 are deliberately out of scope for this
slice.

## 1. H1 - popstate crosses the save barrier

### Problem (recap)

R5.9 guarded the two programmatic navigation helpers (`App.navigate`,
`lib/nav.openProjectView`) but `App`'s `popstate` listener called
`setRoute(parseRoute())` directly. From a dirty document, Back/Forward changed the
route and unmounted `ProjectWorkspaceShell` before any save; the unmount flush was
fire-and-forget and could neither refuse nor report a failure.

### Fix

`lib/historyNavigation.ts` (`createRouteNavigation`) is now the single place that
applies a route change. It is constructed once in `App` from `getRoute`
(a ref to the committed route), `setRoute` and the barrier, and exposes:

- `navigate(next)` - cross the barrier (unless the transition stays inside the
  same project workspace), then `pushState` and commit. Keeps the R5.9
  double-click guard and the same-project-workspace skip.
- `handlePop(event)` - parse the URL the browser already moved to and, unless it
  is a document-leaving transition, cross the barrier before committing.

Behavior on a `popstate`:

| Situation | Result |
| --- | --- |
| clean | barrier resolves immediately; route commits |
| dirty, flush succeeds | route commits after the save settles |
| dirty, save in progress | `handlePop` awaits the running save chain before committing |
| dirty, save fails | route is **not** committed; the URL is restored and the workspace stays mounted with its existing "Save failed" chrome (no new banner) |
| same project workspace | commits directly (the session's own barrier guards any document switch it triggers) |

Refusal restores the URL with `replaceState` on the entry the browser already
moved to, not `pushState`: `pushState` there would add a duplicate entry on every
refused attempt (the stack would grow while the user pressed Back), while
`replaceState` restores in place with no growth and no re-entrant `popstate`. A
pop for the route already rendered is a no-op, so a refused Back/Forward cannot
loop. History entries are otherwise pushed exactly as before; the router is not
replaced.

`lib/nav.openProjectView` still crosses the barrier itself and then dispatches
its synthetic `popstate`. That event is tagged with `PRE_GATED_POP_STATE` (carried
on the event only, never written to `history.state`), so `handlePop` applies the
route without consulting the same barrier twice - a later real Back/Forward to
that entry is still gated normally.

## 2. H2 - dirty-only native exit guard

`lib/unloadGuard.ts` (`useUnloadGuard(dirty)`) installs a `beforeunload` listener
only while the workspace is dirty and removes it as soon as the document is saved
(or no document is open), so a clean exit never warns. It persists nothing and
never claims a save completed.

Browser limitations are documented, not worked around:

- modern browsers ignore a custom message and show their own generic copy;
- the prompt only appears once the page has had a user interaction;
- there is deliberately **no** `pagehide`/`sendBeacon` flush. The canonical
  persist is an authenticated JSON `fetch`, which the browser does not guarantee
  to complete during teardown; a beacon cannot express that request faithfully
  and adding one would be a second persistence path outside the canonical
  autosave.

## 3. Barrier canonicity

No second unsaved-change mechanism was introduced. `useAutosave` remains the only
persistence, `useDocumentSession.runBarrier` remains the document-switch barrier,
and both new paths call the same `useAutosave.flush`:

- `navigate` / `handlePop` -> `runNavigationBarrier` -> the registered barrier
- the barrier (registered by `workspaceSession`) -> `flushRef.current()` -> `useAutosave.flush`
- the now-gated popstate, the programmatic helpers and the document-switch
  session all settle on that one chain.

The unmount flush in `workspaceSession.tsx` is retained as a fire-and-forget
backstop for teardown that cannot be intercepted (the shell unmounting because
its parent route/project changed, or a programmatic path that did not cross the
barrier). It is explicitly not claimed to block unmount; with popstate now gated,
it is no longer the primary guard for Back/Forward.

Native `beforeunload` cannot be exercised in jsdom (it exposes no constructible
`BeforeUnloadEvent`), so the tests pin the hook's registration contract - whether
the listener is installed, what it does to the dispatched event, and when it is
removed - rather than the browser prompt itself. No implementation was weakened
for test convenience.

## 7. Acceptance

- Dirty document + Back/Forward: saves-then-navigates, or stays with the workspace
  mounted and its "Save failed" indicator - never abandons the edit silently.
- Reload/close while dirty: the browser's native prompt is shown. Clean: no
  prompt and no registry entry.
- Route and history never diverge on a refused transition; the history stack does
  not grow and popstate does not loop.
- No second persistence path; H3/H4/H5-H10 untouched.
