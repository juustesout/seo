# R5.10.7 - Media search and external embeddings usage instrumentation recon

Recon-only. No code, schema, test or behavior changes. This document is the
input to the subsequent R5.10.7 implementation brief.

Scope: the two remaining external-usage areas after R5.10.1-R5.10.6.

- Media search / external media acquisition (`MediaProvider.search`, stock
  download, image generation).
- External embeddings (`/embeddings` requests produced for knowledge and
  opportunity retrieval).

Reference pattern for the accounting contract: R5.10.6 publishing
(`docs/r5.10.6-publishing-usage.md`, `apps/api/src/providers/publishing/providerUsage.ts`),
which instruments a provider-specific client method with an optional
best-effort observer bound to the caller's `ProviderContext.usage`.

# 1. Media search findings

## 1.1 Supported media providers

Registered in `apps/api/src/providers/registry.ts` (lines 325-341):

| Provider id | Class | File | Capabilities |
| --- | --- | --- | --- |
| `unsplash` | `UnsplashMediaProvider` | `apps/api/src/providers/media/unsplash.ts` | `search` |
| `openai_media` | `OpenAiMediaProvider` | `apps/api/src/providers/media/openaiMedia.ts` | `generate` |

`ProviderRegistry.getMedia(id)` returns a fresh adapter per call
(`apps/api/src/providers/registry.ts:157`). Both adapters read a **server-side
env key** (`UNSPLASH_ACCESS_KEY`, `OPENAI_API_KEY`); there is no per-project
BYOK or per-account resolution for media providers today.

## 1.2 External request boundaries

### Unsplash search (`unsplash.ts:59`)

- One `GET https://api.unsplash.com/search/photos?...` per `search()` call,
  auth via `Client-ID` header.
- Returns metadata only (urls, dimensions, attribution). It never downloads or
  persists bytes (`unsplash.ts:9-11`).
- Not configured when `UNSPLASH_ACCESS_KEY` is absent; throws, never
  fabricates (`unsplash.ts:60-63`).

### OpenAI image generation (`openaiMedia.ts:57`)

- One `POST {OPENAI_BASE_URL|https://api.openai.com/v1}/images/generations` per
  `generate()` call.
- Returns either a provider-hosted `url` or a `b64_json` data payload
  (`openaiMedia.ts:75-87`).
- Not configured without `OPENAI_API_KEY`.

### Stock asset download (`externalImageAcquisition.ts:87`, `downloadExternalImage`)

- One `GET <images.unsplash.com url>` per attempt, restricted to
  `EXTERNAL_IMAGE_HOST_ALLOWLIST = ['images.unsplash.com']`
  (`externalImageAcquisition.ts:38`), with a 15s timeout and 8 MiB cap.
- This is **asset acquisition** (CDN delivery), not an `api.unsplash.com` API
  request. Unsplash's rate-limited/billable surface is the search endpoint; the
  image host is a plain CDN.

### Generated-image download (`imageGenerationAcquisition.ts:131`, `downloadGeneratedImage`)

- One `GET <provider url>` when the generation returned a URL instead of inline
  base64. This is provider asset delivery, not a generation request.

## 1.3 Callers and entry points

| Entry point | Path | External media requests |
| --- | --- | --- |
| Designer image insertion | `designerService.ts:419` -> `ImageInsertionService.buildProposal` -> `acquireImage` | external search (if allowed) and/or generation (if confirmed) |
| Section creation image | `sectionCreationService.ts:152` -> `acquireImage` | same as above |
| `content_images` job | `jobs/executors.ts:874` (`contentImages`) | direct `media.search` per placeholder, else `media.generate` |
| `content_images` route | `http/routes/content.ts:99-116` (`POST /:id/images`) | enqueues the job (`image_provider`, `limit`) |
| MCP | `mcp/server.ts:336` (`content_resolve_images`), `602` (`designer_execute`) | same as above via enqueue |

Key call-graph detail in `imageInsertionService.acquireImage` (`:287`):

- Local-first: library selection, then, only when
  `context.sourcePolicy?.allowExternalSearch`, calls `acquireExternalImage`
  with `provider: this.container.registry?.getMedia('unsplash')`
  (`:321-328`). **No usage scope is passed** - this module has no usage param.
- Then, when generation is allowed/confirmed, calls `acquireGeneratedImage`
  with a real usage scope (`:366-379`), which is the only media path already
  metered (R5.10.3).

`acquireExternalImage` (`externalImageAcquisition.ts:146`):

1. Guards provider/`isConfigured` (`:148-157`).
2. One `provider.search({ query, limit: 8, orientation })` (`:171`).
3. Iterates up to `EXTERNAL_IMAGE_MAX_ATTEMPTS = 3` results (`:51`, `:180`),
   downloading the first usable one (`:184`) and persisting it via
   `mediaService.importExternal` (`:193`). So one acquisition can be **1 search
   + up to 3 download attempts**.

`contentImages` (`jobs/executors.ts:874`):

- Resolves `container.registry.getMedia(providerId)` (`:897`); default
  `unsplash`, or `openai_media` when requested.
- For each image placeholder (cap default 4, max 6): one `media.search`
  (`:910`) and, only if search yields nothing and the provider supports
  generation, one `media.generate` (`:913-919`).
- A search result URL is written straight into `content_json` (`:926-934`); the
  `content_images` path does **not** download external assets (except when the
  provider returns a `data:` image, which is decoded locally by
  `storeImageDataUrl`). The OpenAI generate path here **bypasses**
  `acquireGeneratedImage` and therefore its usage recording.
- So one `content_images` job can make up to 6 search requests and/or up to 6
  generation requests.

## 1.4 Sync/queue/retry/batch

- All media work is synchronous inside the calling request/job; there is no
  provider-side batching.
- `content_images`, `knowledge_*` and publishing run as durable jobs and can be
  retried by the worker (`job.retry_count`); `acquireImage` on the
  Designer/section path runs inside an agent run/request.
- `acquireExternalImage` has an internal bounded retry over candidate results
  (the download loop); `acquireGeneratedImage` has a hard timeout
  (`IMAGE_GENERATION_TIMEOUT_MS = 60_000`) and no retry.

## 1.5 Provenance and existing hooks

- `seo_media.source` (`upload`|`unsplash`|`openai_generated`) and
  `seo_media.source_meta` (bounded, secret-free: `provider`, `sourceAssetId`,
  `author`, `authorUrl`, `sourceUrl`, `model`) from
  `supabase/migrations/20260101000030_media_provenance.sql`; contract
  `packages/contracts/src/mediaSource.ts`.
- The only media usage hook today is
  `imageGenerationUsageEvent` (`services/usageInstrumentation.ts:133`), called
  by `acquireGeneratedImage` (`imageGenerationAcquisition.ts:231-255`): one
  `media/openai_media/image_generate/image_generation` event per actual
  `provider.generate()` attempt.
- Unsplash search, stock download and the `content_images` generate path have
  **no usage hook**.

## 1.6 Answer: what is one media usage event

- One **Unsplash search request** (`api.unsplash.com/search/photos`): one
  `media_search` fact, `quantity 1`.
- One **image generation request** (`/images/generations`): one
  `image_generate` fact, `quantity 1` (existing).
- **Asset acquisition** (persist bytes): the CDN download is not a provider
  API request; the persisted `seo_media` row is already the domain record. If
  an acquisition fact is wanted, it must be a **separate** operation from the
  search (they are distinguishable in code: `search` vs the download loop), and
  must not be inferred from a search.

## 2.2 Resolution and BYOK

- `AIService.resolve(projectId)` (`services/aiService.ts:162`) merges
  account BYOK -> project BYOK -> server `OPENAI_API_KEY` and returns an
  `AIProvider` wrapped by `instrumentAiProvider` (`aiService.ts:185`).
- `EmbeddingService.embedderFor` (`services/embeddingService.ts:44`) wraps that
  provider in `ProjectEmbedder`, so the AIProvider `embed` path **is** metered
  (`usageInstrumentation.ts:193`, unit `input_token`, operation `embed`).
- **But `EmbeddingService`/`ProjectEmbedder` has no production caller.** Grep
  shows it referenced only in `aiService.ts:19` (a comment) and its own file.
  Every real embedding flows through `embedderFromConfig`.
- `embedderFromConfig` is **server-env only** and is called in:
  - `QdrantKnowledgeProvider` constructor (`providers/qdrantKnowledge.ts:63`),
    config from `buildRegistry` which passes `EMBEDDINGS_*` from
    `process.env` and `OPENAI_*` from parsed env (`context.ts:140-149`).
  - `opportunityTopicService.getTopicRecommendations`
    (`services/opportunityTopicService.ts:288-299`), reading
    `process.env.EMBEDDINGS_*` + `container.config.env.OPENAI_*` directly.

So project/account BYOK is **not** honored on the real embedding path, and the
R5.10.3 embed instrumentation is effectively dead code in production.

## 2.3 External request boundaries

## 2.4 Scope propagation and hooks

- `KnowledgeService.context(projectId)` (`knowledgeService.ts:568-582`) builds
  a `ProviderContext` with **no `usage` field** and `userId: null`.
- The `knowledgeIndex`/`knowledgeReindex` executors build their own
  `ProviderContext` (`executors.ts:602-608`, `:621-627`) also with **no
  `usage`**.
- `opportunityTopicService` builds no `ProviderContext` at all; it holds a bare
  `Embedder`.
- Therefore **no external embedding request is instrumented today**, and the
  authoritative `usage.prompt_tokens` returned by OpenAI-compatible endpoints
  is thrown away by `OpenAiCompatibleEmbedder`.

## 2.5 Local vs external (must not count)

- Qdrant operations (`ensureCollection`, `upsertPoints`, `deleteByFilter`,
  `search`, `setPayloadByFilter`; `providers/knowledge/qdrantClient.ts`) are
  the vector DB, not an embedding/LLM provider. They must **not** produce usage
  events under this slice.
- Lexical retrieval (`knowledge/retrieval/lexical.ts`), chunking
  (`knowledge/chunker.ts`) and reranking are local or separate concerns
  (reranker is a distinct external provider, see gaps).

## 2.6 Answer: what is one embedding usage event

- One physical `POST /embeddings` request. Quantity = the provider-reported
  `usage.prompt_tokens` for that request (`input_token`). Do **not** infer
  tokens from text length; the endpoint already returns authoritative usage.
- A logical `embed(texts)` call is `ceil(len/8)` physical requests; representing
  each request (with its own token count) is the faithful boundary and also
  makes retries/batches unambiguous.
- Qdrant operations and lexical work produce nothing.

# 3. Existing R5.10 accounting contract relevant to both

From `packages/contracts/src/usageEvent.ts`, `services/usageInstrumentation.ts`,
`services/usageEventRepository.ts`, `supabase/migrations/20260101000031_usage_events.sql`.

- **Event shape**: `{ accountId, projectId, userId, category, provider,
  operation, quantity, unit, success, sourceId, metadata, idempotencyKey? }`.
  `category` is closed (`ai|dataforseo|job|publishing|media`); `unit` is closed
  (`request|task|keyword|serp_request|gsc_request|input_token|output_token|`
  `image_generation|asset|publish_attempt|job`). `provider`/`operation` are open
  tokens. The vocabulary already anticipates this slice: `media` category,
  `request`/`asset`/`image_generation` units, `input_token`, and a
  `media_search` operation example in `usageEvent.test.ts:158`.
- **Reusable writers** (`usageInstrumentation.ts`):
  - `appendUsage(sink, events)` - best-effort, swallows append failure
    (`:49-59`).
  - `embeddingEvents` - one `ai/<provider>/embed/input_token` event from an
    `AIEmbeddingResult.usage.inputTokens` (`:107-127`).
  - `imageGenerationUsageEvent` - `media/<provider>/image_generate/`
    `image_generation`, `quantity 1` (`:133-150`).
  - `instrumentAiProvider` - wrapper recording chat/generate/embed after a real
    provider call (`:162-199`).
- **Scope**: existing writers use `UsageScope { accountId, projectId, userId }`.
  Publishing/GSC additionally carry `sourceId` (job id) and an occurrence
  counter via `ProviderContext.usage` (`ProviderUsageContext`:
  `{ sink, sourceId, nextOccurrence(operation) }`).
- **Idempotency**: deterministic key
  `v1|<category>|<provider>|<operation>|<unit>|<sourceId>|<occurrence>`; `null`
  when `sourceId` is null (`usageEvent.ts:300`). The ledger treats a unique
  violation as a duplicate. R5.10.6 raises the occurrence base per retry so a
  genuinely new external attempt is not deduplicated
  (`PUBLISH_OCCURRENCE_STRIDE`).
- **Error handling**: usage is never a transaction boundary - record only after
  a real external call; a failed append is logged and swallowed.
- **Retry expectation**: per-external-request consumption (GSC, publishing)
  records each physical request and counts retries; per-logical-operation
  consumption (DataForSEO, job) records one terminal fact. Media search and
  embeddings are per-request external consumption, so they follow the
  GSC/publishing "physical attempt" model.

Both new areas fit the existing contract without new categories or units:

- Media search: `category='media'`, `provider='unsplash'`,
  `operation='media_search'`, `unit='request'`, `quantity=1`.
- Media acquisition (optional, separate): `category='media'`,
  `operation='media_acquire'`, `unit='asset'`, `quantity=1`.
- Image generation: unchanged (`image_generate`/`image_generation`) but must be
  emitted on **all** generation paths.
- Embeddings: `category='ai'`, `provider='openai'` (or the configured
  provider), `operation='embed'`, `unit='input_token'`,
  `quantity=provider prompt_tokens`.

# 5. Risks and gaps (not fixed here)

1. **Single knowledge embedding path bypasses the meter.** `QdrantKnowledgeProvider`
   is the only knowledge provider and embeds via `embedderFromConfig`
   (server env), not `AIService`. The instrumented `AIProvider.embed` path is
   unreachable in production because `EmbeddingService`/`ProjectEmbedder` has no
   caller. Fixing the meter requires touching the `Embedder` seam, not the AI
   wrapper.
2. **Provider-reported embedding usage is discarded.**
   `OpenAiCompatibleEmbedder` ignores `json.usage.prompt_tokens`
   (`embedding.ts:77`). The authoritative quantity exists but is not surfaced,
   so any token accounting needs a small contract change (return or report
   usage).
3. **No usage scope reaches knowledge embedding.** `KnowledgeService.context`
   (`knowledgeService.ts:568`) and the knowledge executors
   (`executors.ts:602-627`) build `ProviderContext` without `usage`; project and
   user are available at those call sites but not threaded.
4. **Media search has no accounting input at all.** `acquireExternalImage`
   accepts no usage param and every caller (imageInsertionService, contentImages)
   supplies none. Adding one requires touching both callers.
5. **`contentImages` is a second, unmetered media road.** It calls
   `media.search`/`media.generate` directly (`executors.ts:910-919`),
   bypassing `acquireGeneratedImage`'s generation event. Instrumenting only the
   acquisition service would leave this gap; instrumenting only the provider
   would double count the designer generation path (see 6).
6. **Double-count risk on the `MediaProvider` interface.** `generate` is
   already counted at the `acquireGeneratedImage` call site. Adding a
   provider-level observer without removing the call-site event would count one
   generation twice. The implementation must choose exactly one seam for
   `generate`.
7. **BYOK resolution is far from the provider call.** Media (`UNSPLASH_ACCESS_KEY`,
   `OPENAI_API_KEY`) and embeddings (`embedderFromConfig`) read env/config
   directly; a future per-project media/embedding credential would not be seen
   by the meter unless scope/credentials are threaded to the embedder/provider.
8. **No stable `sourceId` on non-job paths.** Designer image insertion, section
   creation and opportunity topics run outside a durable job, so there is no
   `job.id`. Without an execution identity (e.g. the agent run id), duplicates
   cannot be deduplicated (`sourceId = null` -> null key). The implementation
   should use `job.id` where it exists and decide an id for agent-run paths.
9. **One user action fans out into many requests.** `content_images` (up to 6
   searches/generations), `acquireExternalImage` (1 search + up to 3
   downloads), embeddings (`ceil(n/8)` batches). A per-execution occurrence
   counter is required to keep events distinct.
10. **Retry semantics are unset for these areas.** A retried job re-issues
    real external requests. Per the R5.10.6 precedent these should be counted
    as new attempts (retry-aware occurrence base), not deduplicated like the
    R5.10.4 terminal job fact.
11. **Adjacent external providers remain unmetered**: the Cohere reranker and
    the Jina URL fetcher are external consumption but outside this slice. They
    should be recorded as explicit follow-ups, not silently folded in.
12. **`EMBEDDINGS_*` is not in the zod env schema** (`config.ts`), so the
    registry receives it only because `context.ts:146-149` forwards
    `process.env` explicitly. Any instrumentation that identifies the embedding
    provider must account for this split (custom endpoint vs OpenAI).

# 6. Recommended implementation boundaries for R5.10.7

Recon only; this names where the next step should change code.

## 6.1 Embeddings

1. **Surface authoritative usage from the embedder.** Change
   `OpenAiCompatibleEmbedder.embed` to capture the per-request
   `usage.prompt_tokens` it already receives (`providers/knowledge/embedding.ts:77`)
   and either return it (`{ vectors, usage }`) or invoke an optional
   `EmbeddingRequestObserver(operation, promptTokens, success)` supplied to the
   constructor/`embed`. Keep `Embedder` backward compatible (optional report).
2. **Instrument at the provider call sites that already hold project scope.**
   Record per physical batch request inside `OpenAiCompatibleEmbedder.embed`
   (one event per `POST /embeddings`, `quantity = that request's
   prompt_tokens`), attributed with the project scope passed down from
   `QdrantKnowledgeProvider.index`/`search` (via `ctx.projectId`) and from
   `opportunityTopicService`.
3. **Thread scope.** Add `usage` to the provider context used for knowledge
   embedding:
   - `KnowledgeService.context(projectId)` (`knowledgeService.ts:568`): bind
     `container.usageEvents` with a sourceId for job-backed ingestion.
   - `knowledgeIndex`/`knowledgeReindex` executors (`executors.ts:602-627`):
     pass `usageSourceId: job.id` and a retry-aware occurrence base, mirroring
     R5.10.6/R5.10.4.
   - `opportunityTopicService` (`services/opportunityTopicService.ts:288`):
     build a usage scope from `container.usageEvents` + `projectId` (route
     userId), sourceId null unless a stable id exists.
4. **Provider identification.** Resolve a provider token from
   `embedderFromConfig` (e.g. `openai` for the OpenAI branch; a stable token for
   a custom `EMBEDDINGS_BASE_URL`, or a new `EMBEDDINGS_PROVIDER` env), reusing
   `PROVIDER_IDS` where applicable.
5. **Do not** record Qdrant ops, chunking, lexical retrieval, or the per-logical
   `embed()` aggregate in addition to per-request events.

## 6.2 Media

1. **Choose one seam for `MediaProvider` search and generation.** Recommended:
   an optional best-effort observer on the concrete provider methods
   (`UnsplashMediaProvider.search`, `OpenAiMediaProvider.generate`), exactly
   like `WordPressClient`/`XOAuthClient` in R5.10.6, with the caller supplying
   scope. This covers both the acquisition service and `contentImages` with one
   implementation.
2. **Migrate the existing generation event.** Move
   `imageGenerationAcquisition`'s manual `imageGenerationUsageEvent` call
   (`imageGenerationAcquisition.ts:231-255`) onto the shared media observer so
   the `content_images` generate path (`executors.ts:913`) is counted once by
   the same code, never twice (gap 6).
3. **Add scope to the media call sites.** `acquireImage`
   (`imageInsertionService.ts:287`) already resolves the generation scope;
   extend it to the external-search call (`:321-328`) and reuse it for
   generation. `contentImages` (`executors.ts:874`) passes `job.id` +
   `job.created_by` and a retry-aware occurrence base.
4. **Count search requests, not fetches.** Emit `media_search`/`request` per
   `api.unsplash.com` search. Decide explicitly whether the CDN byte download
   should also emit a separate `media_acquire`/`asset` fact; if yes, emit it at
   `downloadExternalImage` only after a successful, persisted download and keep
   it distinct from the search. The generated-image URL download should stay
   uncounted (asset delivery of an already-counted generation).
5. **Do not count** local-library reuse, `isConfigured` guards, local
   validation, `seo_media` persistence, or data-URL decoding.

- No new vocabulary is required: `media` category and `request`/`asset`/
