# R5.10.3 - AI and Image Generation Usage Instrumentation

R5.10.1 defined the usage-event vocabulary and R5.10.2 gave it an append-only
ledger. R5.10.3 makes the ledger truthful: real AI chat/generation, AI
embeddings and OpenAI image generation now record usage events from the actual
provider calls. It does not redesign AI resolution, the provider contracts, image
generation, the ledger, or add any billing/pricing/credit/quota logic.

## 1. What was built

| Piece | Location |
| --- | --- |
| Provider wrappers + event builders | `apps/api/src/services/usageInstrumentation.ts` |
| AI seam (single resolved provider) | `apps/api/src/services/aiService.ts` (`resolve`, `resolveImageGeneration`) |
| Image-generation seam | `apps/api/src/services/imageGenerationAcquisition.ts` (`acquireGeneratedImage`) |
| Image-generation caller wiring | `apps/api/src/services/imageInsertionService.ts` |
| Unit + integration tests | `apps/api/src/services/usageInstrumentation.test.ts`, `apps/api/src/services/imageGenerationAcquisition.test.ts`, `apps/api/src/services/aiService.test.ts` |

## 2. The two seams

**AI text and embeddings - one wrapper at the resolution gate.** Every text and
embedding caller reaches a provider through `AIService.resolve(projectId)`, so
wrapping the resolved `AIProvider` there (`instrumentAiProvider`) records exactly
one event per actual provider operation with no per-caller double counting.
Callers do not change. `chat` and `generate` are wrapped separately because the
adapter implements `generate` on top of its own (unwrapped) `chat`, so the
wrapper still sees a single logical operation. `embed` wraps the logical call
once; the provider may batch internally but returns summed usage, so no per-batch
double counting.

**Image generation - the existing confirmed path.** `acquireGeneratedImage()`
gains an optional `usage: { sink, scope }`. A configured-but-failing generation
records a failed attempt; a not-configured provider records nothing because no
external call was made. The successful external generation is recorded before
download/persistence, so a later download or persistence failure cannot rewrite
the fact that the image was generated.

## 3. Event shapes

All events use the resolved scope (`accountId` from the project row, `projectId`,
`userId: null` at this seam - the resolution gate and worker callers have no
acting user) and the provider's real id.

| Operation | category | provider | operation | unit(s) | quantity | success |
| --- | --- | --- | --- | --- | --- | --- |
| AI chat | `ai` | provider id | `chat` | `input_token`, `output_token` | present tokens (one event per unit) | `true` |
| AI generate | `ai` | provider id | `generate` | `input_token`, `output_token` | present tokens | `true` |
| AI embed | `ai` | provider id | `embed` | `input_token` | summed tokens | `true` |
| Image generation | `media` | media provider id | `image_generate` | `image_generation` | `1` | `true`/`false` |

`metadata.model` carries the model for every event (the OpenAI image path uses
the media provider id `openai_media`, so the model is the only place the applied
`OPENAI_IMAGE_MODEL` is visible). Token events are only emitted for present,
`> 0` usage values - token counts are never estimated or invented, and the error
path (provider threw) records nothing for `chat`/`generate`/`embed`.

## 4. Best-effort, never a transaction boundary

```text
AI/media operation succeeds
  -> usage append fails
       -> log the persistence failure
       -> do NOT fail the operation
```

Every append goes through `appendUsage`, which swallows (and logs) persistence
errors. A usage-evidence failure must never turn a successful AI/media operation
into a user-visible failure, and a missing sink is a no-op.

## 5. Non-goals

- no change to the public `AIProvider` contract (the neutral
  `usage: { inputTokens?, outputTokens? }` shape already existed);
- no second image-generation path and no change to the generation provider;
- no instrumentation of direct `media.generate` callers (the `contentImages` job
  executor is out of scope for this slice), nor of DataForSEO, publishing, jobs
  or external embeddings - those are later R5.10.x slices;
- no HTTP route, UI or MCP surface;
- no billing, credits, quotas, pricing or stored cost.
